## 一、要解决的问题

### 1.1 用户可见的三个症状

| # | 症状 | 现在的行为 |
|---|---|---|
| 1 | 普通聊天刷新后看不到已生成内容 | `messages.content` 只在流结束写一次，中途为 `""` |
| 2 | 深度研究刷新后要手动等 | 有事件表但前端只在「点击会话」时连流 |
| 3 | 长任务阻塞短任务 | worker 单协程串行，一个 40 分钟的深度研究挡住所有聊天 |

### 1.2 根因

| 根因 | 位置 | 后果 |
|---|---|---|
| **`/chat` 的任务活在 HTTP 生命周期里** | `chat.py:484` `enqueue=False` | API 进程重启 → 聊天彻底消失，无 worker 接手 |
| **worker 单协程串行** | `run_worker.py:121` 单个 `create_task` | 长任务阻塞队列 |
| **`session_events` 无 `run_id`** | `006_run_queue.sql` | 重试时两次尝试的事件混在一起，游标失效 |
| **`sweep()` 失败不写事件** | `run_queue.py:182` | 订阅中的前端干等 `event_tail_timeout`（600 秒）|

### 1.3 明确不做

| 不做 | 理由 |
|---|---|
| **断点续跑（checkpoint）** | BISHENG 试过并放弃（`save_workflow_object` 被注释掉）。工具中间态无法序列化，恢复后答案可能不同——投研场景确定性优先。先度量再决定 |
| 两张独立的队列表 | PostgreSQL 里队列是查询 + 部分索引，不是表结构 |
| Redis pub/sub 直推 | 先用 PG 轮询，实测延迟不够再上 |
| prefill 自动续写 | 交用户决定 |
| 事件表分区归档 | 数据量未到 |

## 二、目标架构

### 2.1 一句话

**任务从第一毫秒起就不在 HTTP 生命周期里；HTTP 只是「观战」的一条线，可以断无数次。**

```
POST /chat 或 /research
  ├─ 事务：user消息 + assistant占位 + run(status=queued, run_type=?)
  ├─ commit
  └─ 订阅 run_events(after_seq=0)，转发 SSE
       └─ chat 30 秒后吐 run_detached 并 break（只断这条响应）

worker（与 HTTP 无关，跑到底）
  ├─ claim(run_type) → 执行 → 写 session_events
  └─ 终态自己收尾（message + run + terminal 事件）

GET /api/v1/runs/{run_id}/events?after_seq=N
  └─ 读 session_events 回放 → 接直播 → 终态关闭
```

### 2.2 两条链路同构，只差资源画像

| 维度 | `run_type='chat'` | `run_type='research'` |
|---|---|---|
| 任务归属 | 队列 | 队列 |
| 事件写入 | 每 200ms 一条 `snapshot`（全文） | 逐条（`thinking`/`tool_call`/`delta`）|
| `after_seq=0` 时 | 只吐最后一条 snapshot | 全量重放 |
| 观战断流 | 30 秒 | 300 秒 |
| worker 并发额度 | 8 | 2 |
| checkpoint | 不需要 | 不需要（明确不做） |

**`run_type` 由前端传**（用户点按钮）。接受误判：聊天里问难题就按 chat 的资源画像跑，超时后前端可提示「转深度研究」。

## 三、数据模型

### 3.1 三张表的职责

| 表 | 一行代表 | 生命周期 |
|---|---|---|
| `conversations` | 一个会话 | 长期 |
| `messages` | **一条消息（结果）** | 长期 |
| `chat_runs` | **一次生成尝试（过程）** | 长期（审计） |
| `session_events` | **一条事件（过程细节）** | 临时（`expires_at` 清理） |

**`messages` : `chat_runs` = 1 : N**

```
messages id=A                    ← 前端渲染的节点，永不换
  ├─ chat_runs run=r1 attempt=1 failed
  └─ chat_runs run=r2 attempt=2 done
```

**为什么必须分开**：
- `message.id` 稳定 → 前端 DOM 不闪
- `run_id` 可变 → 新一次尝试的事件编号从 1 开始，挂在 message 上会互相覆盖

### 3.2 迁移 `009_run_type_and_events.sql`

```sql
begin;

-- ① chat_runs 加 3 列（不加 detached_at，暂不需要）
alter table chat_runs
  add column if not exists run_type text not null default 'research',
  add column if not exists last_seq integer not null default 0,
  add column if not exists priority integer not null default 100;

-- ② session_events 加 run_id（重试时区分两次尝试）
alter table session_events
  add column if not exists run_id uuid;

-- 回填历史：现有每个 message 只有一次 run（chat 不写 run，research 一对一）
update session_events e
   set run_id = r.id
  from chat_runs r
 where e.message_id = r.message_id
   and e.run_id is null;

-- ③ 索引
create index if not exists session_events_run_seq_idx
  on session_events (run_id, id) where run_id is not null;

-- 按 run_type 抢占的部分索引（比全表小一个数量级）
create index if not exists chat_runs_pick_chat_idx
  on chat_runs (priority, created_at)
  where status = 'queued' and run_type = 'chat';

create index if not exists chat_runs_pick_research_idx
  on chat_runs (priority, created_at)
  where status = 'queued' and run_type = 'research';

commit;
```

**注意 `chat_runs_one_active` 保持不变**：同会话仍然只允许一个活跃 run（含 queued + running）。这保证了 `agent_state` 不被并发覆盖。

### 3.3 为什么 `seq` 用现有 `id` 而不新增列

`session_events.id` 是 `bigserial`，在同一个 `run_id` 内天然递增且全局唯一。

**加 `seq` 列等于维护第二个计数器**，没有收益。前端传的 `after_seq` 就是 `id`。

## 四、接口设计

### 4.1 统一回放入口

```
GET /api/v1/runs/{run_id}/events?after_seq=N
Accept: text/event-stream
```

**实现要点**：

```python
async def run_events(run_id, request, after_seq: int = 0):
    principal = require_principal(request)
    cursor = max(0, after_seq, _last_event_id(request))

    run = run_queue.load_run(principal.tenant_id, principal.user_id, run_id)
    if run is None:
        raise HTTPException(404, {"code": "NOT_FOUND", "message": "任务不存在"})

    return StreamingResponse(_replay(run, cursor), media_type="text/event-stream")

async def _replay(run, cursor):
    # meta 带 run_id，前端可校验游标归属
    yield _sse("meta", {
        "run_id": str(run.id),
        "run_type": run.run_type,
        "message_id": str(run.message_id),
    })

    # chat 首次恢复：只吐最后一条 snapshot，避免逐条重绘
    if run.run_type == "chat" and cursor == 0:
        snap = run_queue.last_snapshot(run.id)
        if snap is not None:
            cursor = snap["id"] - 1        # 退一格，让下面的重放吐出它

    async for chunk in _tail(run, cursor):
        yield chunk
```

**`_tail` 就是现有 `_stream_events`**，只把 `read_events(message_id, ...)` 换成 `read_events_by_run(run_id, ...)`。

### 4.2 现有端点处置

| 端点 | 处置 |
|---|---|
| `GET /research/{run_id}/stream` | 保留为别名，内部转 `run_events` |
| `GET /messages/{message_id}/events` | 保留为别名，内部先查 `run_id` 再转 |

**保留而非删除**：前端两处已在使用，且它们是同一份 `_replay` 的薄包装。

### 4.3 `POST /chat` 与 `POST /research` 统一

```python
@router.post("/chat")       # 前端 mode='chat'
@router.post("/research")   # 前端 mode='research'
```

**两者唯一区别**：

```python
# chat: 建 run 后立即返回流
_, prepared = _start_turn(..., enqueue=True, run_type="chat")
return StreamingResponse(_proxy_stream(prepared), ...)

# research: 建 run 后返回 run_id
_, prepared = _start_turn(..., enqueue=True, run_type="research")
return {"run_id": ..., "message_id": ..., "stream_url": "/api/v1/runs/{id}/events"}
```

**`/chat` 从 `enqueue=False` 改为 `enqueue=True`** —— 这是本方案最核心的一处改动。

### 4.4 30 秒断流

```python
async def _proxy_stream(prepared) -> AsyncIterator[str]:
    started = time.monotonic()
    async for ev in _replay(run, 0):
        yield ev
        if time.monotonic() - started > CHAT_DETACH_SECONDS:      # 30
            yield _sse("run_detached", {
                "run_id": str(prepared.run_id),
                "last_seq": last_yielded_seq,
                "stream_url": f"/api/v1/runs/{prepared.run_id}/events",
            })
            break          # ← 只结束这条响应，worker 不受影响
```

**不要用 `asyncio.wait_for(整个循环, 30)`** —— 那会 cancel 协程，把订阅也杀掉。**用「每条事件后检查计时」。**

### 4.5 `messages.meta.run_id`

**建 turn 时写入**（`/chat` 和 `/research` 都要）：

```python
assistant_message.meta = {
    **(assistant_message.meta or {}),
    "run_id": str(run_id),
    "run_type": run_type,
}
```

**前端刷新后从 `GET /conversations/{id}/messages` 拿到 `meta.run_id`，直接连流。**

## 五、Worker 改造

### 5.1 并发化（最关键）

**现状**：

```python
self._task = asyncio.create_task(self._loop())    # 单协程
```

**改为 N 个协程**：

```python
CHAT_CONCURRENCY = 8
RESEARCH_CONCURRENCY = 2

async def start(self):
    self._tasks = [
        asyncio.create_task(self._loop("chat"), name=f"worker-chat-{i}")
        for i in range(CHAT_CONCURRENCY)
    ] + [
        asyncio.create_task(self._loop("research"), name=f"worker-research-{i}")
        for i in range(RESEARCH_CONCURRENCY)
    ]

async def _loop(self, run_type: str):
    while not stopping:
        # 维护类操作只让 chat-0 做，避免重复
        if self._is_maintenance_lane():
            await self._maintenance()

        ticket = await asyncio.to_thread(claim, self.worker_id, lease, run_type)
        if ticket is None:
            await self._sleep(poll_seconds)
            continue
        await self._execute(ticket)
```

**`claim` 加 `run_type` 参数**：

```python
def claim(worker_id, lease_seconds, run_type):
    ...
    " where status = 'queued' and run_type = :run_type"
    " order by priority, created_at"
```

### 5.2 轮询间隔

| 配置 | 现值 | 改为 | 理由 |
|---|---|---|---|
| `RUN_QUEUE_POLL_SECONDS` | 0.2 | **0.05** | 首字延迟从 200ms 降到 50ms |
| `EVENT_POLL_SECONDS` | 0.15 | **0.05** | 观战延迟降到 50ms |

**代价**：空闲时多 4 倍查询。**8+2 个协程 × 每秒 20 次 = 200 QPS 的 `claim` 查询**——对单机 PG 无压力，但要监控。

### 5.3 重试语义：chat 不重试，research 重试 1 次

**现状**（`run_queue.py:154`）：

```python
state = "failed" if ticket.attempt >= limit else "queued"
```

`RUN_MAX_ATTEMPTS` 默认 **2**，含义是「最多执行 2 次」：

| 阶段 | `attempt` | 结果 |
|---|---|---|
| 首次执行 | 1 | — |
| 首次崩溃 | 1 | `1 >= 2` 为假 → **重新入队** |
| 第二次执行 | 2 | — |
| 第二次崩溃 | 2 | `2 >= 2` 为真 → **判 failed** |

**但普通聊天不该重试**：

| 维度 | chat | research |
|---|---|---|
| 单次成本 | 3 秒 + 1-2 次工具 | 40 分钟 + 20 次工具 |
| 重试收益 | 小（用户自己重问一句）| 大（省 40 分钟）|
| 最坏代价 | 多占一次队列槽 | 2 倍配额 + 80 分钟 |

**决策：`run_type='chat'` 首次崩溃直接判 `failed`。**

#### 判定改一处

**`sweep()` 的 `select` 加 `run_type`**（现在没有这个字段）：

```python
"select id, tenant_id, user_id, conversation_id, message_id,"
"       request_id, attempt, worker_id, run_type"
```

**判定改为：**

```python
if run_type == "chat":
    state = "failed"          # 聊天：一次机会
elif ticket.attempt >= limit:
    state = "failed"
else:
    state = "queued"
```

**`QueueTicket` 加 `run_type: str = "research"` 字段**，`_ticket()` 里 `row.get("run_type", "research")`。

#### 异常与崩溃的语义不同

| 情况 | 重试 | 理由 |
|---|---|---|
| worker 崩溃 / 租约过期 | ✅ research 重试 1 次，❌ chat 不重试 | 可能是瞬时故障 |
| **Agent 抛异常** | ❌ **都不重试** | 确定性失败，重试也白搭 |

**Agent 异常的路径**（`run_worker.py:229`）已经是直接 `finish(..., "failed")`，不改。

### 5.4 `sweep()` 判失败时必须通知用户

**现在的缺口**：`sweep` 只改数据库状态，**不写事件**。订阅中的前端收不到通知，只能等 `EVENT_TAIL_TIMEOUT_SECONDS`（600 秒）。

#### 三条通知渠道都要写

| 渠道 | 用户在哪看 | 时效 |
|---|---|---|
| `session_events` 写 `error` + `done` | 正在观战的前端 | 立即 |
| `messages.status = 'failed'` + `content` | 刷新后的前端 | 立即 |
| `messages.meta.retryable` | 走轮询的前端 | 立即 |

**少任何一条，就有一类用户看不到通知。**

#### 实现

```python
if state == "failed":
    is_chat = run_type == "chat"
    code = "WORKER_LOST" if is_chat else "LEASE_EXPIRED"
    message = (
        "回答生成中断，请重新提问。"
        if is_chat
        else "执行中断，请重试。"
    )
    mark_assistant_failed_in_session(
        db, ticket.message_id, "failed", code, message,
        retryable=not is_chat,          # ← 见下
    )
    # 同一事务写事件，观战中的前端立刻收到
    append_event_in_session(db, ticket, "error", {"code": code, "message": message})
    append_event_in_session(db, ticket, "done", {
        "status": "failed",
        "message_id": str(ticket.message_id),
        "conversation_id": str(ticket.conversation_id),
        "retryable": not is_chat,
    })
```

#### `retryable` 字段

| 值 | 前端行为 |
|---|---|
| `false`（chat） | 显示「重新提问」按钮，**不自动重试** |
| `true`（research） | 显示「重试」按钮 |

**必须同时写进 `messages.meta`**，因为轮询路径读不到事件：

```python
content, meta = failed_message_payload(code, message)
meta["retryable"] = not is_chat
```

#### 需要新增 `append_event_in_session`

**现有 `append_event` 自己开事务**：

```python
def append_event(ticket, event, data):
    with tenant_scope(ticket.tenant_id, ticket.user_id) as db:   # ← 独立事务
        db.execute("insert into session_events ...")
```

**改成两层**：

```python
def append_event_in_session(db, ticket, event, data) -> None:
    """在调用方事务内写事件。"""
    db.execute(text(
        "insert into session_events "
        "(tenant_id, user_id, conversation_id, message_id, run_id, event, data) "
        "values (:tenant_id, :user_id, :conversation_id, :message_id, :run_id, :event, cast(:data as jsonb))"
    ), {...})

def append_event(ticket, event, data) -> None:
    """独立事务写事件（worker 执行路径用）。"""
    with tenant_scope(ticket.tenant_id, ticket.user_id) as db:
        append_event_in_session(db, ticket, event, data)
```

**为什么必须同事务**：先改状态再写事件，中间宕机 → 状态是 `failed` 但前端收不到事件 → 用户干等 600 秒。

### 5.5 心跳续租（前置依赖）

**「崩溃后 60 秒内通知」要求租约足够短**：

| `RUN_LEASE_SECONDS` | 崩溃发现延迟 |
|---|---|
| 900（现状） | **15 分钟** |
| **120** | **2 分钟** |

**但租约降到 120 秒，必须有心跳续租** —— 否则所有超过 2 分钟的任务被误判崩溃并重跑。

```python
async def _heartbeat(ticket, lease_seconds: float) -> None:
    """执行期间定期续租；续租失败说明已被回收。"""
    interval = max(5.0, lease_seconds / 3)
    while True:
        await asyncio.sleep(interval)
        ok = await asyncio.to_thread(
            renew_lease, ticket.run_id, ticket.worker_id, ticket.attempt, lease_seconds,
        )
        if not ok:
            raise RunFenced()          # 已被回收，主动退出
```

**`renew_lease` 必须带 fencing**：

```sql
update chat_runs
   set lease_until = now() + (:lease * interval '1 second')
 where id = :id
   and worker_id = :worker_id        -- ← fencing
   and attempt = :attempt            -- ← fencing
   and status = 'running'
```

**`rowcount == 0` 就返回 `False`** —— 说明这个 run 已经被别的 worker 接手。

**启动方式**：在 `_execute` 里用 `asyncio.create_task` 起心跳，`finally` 里取消。

### 5.6 埋点

```python
logger.warning("run_recovered", extra={
```

**然后两周后跑一次查询**：

```sql

       run_type,
       count(*) filter (where attempt > 1) as reruns,
       avg(extract(epoch from (finished_at - started_at))) as avg_duration
  from chat_runs

```

**用这个数字决定要不要做断点续跑。**

### 5.7 `queued` 任务永久等待（新增检测）

**现状**：`sweep` 只看 `running`，`queued` 任务如果 worker 全挂就永远等。

**加一个轻量检测**（复用 `sweep`，不建 `workers` 表）：

```sql
-- 有排队超过 30 分钟的任务，且过去 30 分钟没有任何 run 进入 running
update chat_runs
   set status = 'failed',
       error_code = 'QUEUE_STALLED',
       error_message = 'no worker available'
 where status = 'queued'
   and created_at < now() - interval '30 minutes'
   and not exists (
       select 1 from chat_runs r2
        where r2.status = 'running'
          and r2.started_at > now() - interval '30 minutes'
   )
```

**误杀风险**：深夜无人使用 + 恰好有人排队。**所以只在「同时满足两个条件」时才杀**——有 running 说明系统活着。

## 六、实施顺序

| 阶段 | 内容 | 可独立验收 | 工时 |
|---|---|---|---|
| **1** | 迁移 009：`run_type` / `last_seq` / `priority` / `session_events.run_id` + 回填 | 迁移幂等，旧数据不丢 | 0.5 天 |
| **2** | worker 并发化（N 协程 + `claim(run_type)` + 轮询降频） | 长任务不再阻塞短任务 | 1 天 |
| **3** | 心跳续租 + 租约降到 120 秒 | 超过 2 分钟的任务不被误判崩溃 | 0.5 天 |
| **4** | `append_event_in_session` + `sweep` 分流判定 + 补事件 + `retryable` | chat 崩溃即 failed 且前端立即收到 | 1 天 |
| **5** | `/chat` 改 `enqueue=True` + 终态从 API 移到 worker | 杀掉 API 进程，聊天仍能跑完 | 2 天 |
| **6** | 统一 `GET /runs/{run_id}/events` + 两个别名 | 两条链路共用同一回放 | 1 天 |
| **7** | 30 秒 `run_detached` + 前端重连 | 用户无感切换 | 0.5 天 |
| **8** | 前端：`meta.run_id` 连流 + `snapshot` 整体替换 + `retryable` 按钮 | 刷新 100ms 内看到内容 | 1 天 |
| **9** | `queued` 停滞检测 | worker 全挂时用户不等死 | 0.5 天 |

**合计约 8 天。**

**阶段 1-4 可独立上线**（不动 `/chat`，只修「长任务阻塞」「崩溃无通知」「心跳」）。

**阶段 1-4 之后系统已经健康**，5-9 是为「刷新恢复」这个目标服务的。

### 关键依赖

```
阶段 1（迁移，加 run_type）
   ├─→ 阶段 2（按 run_type 分队列）
   └─→ 阶段 4（按 run_type 分流重试）

阶段 3（心跳 + 短租约）
   └─→ 阶段 4（"崩溃后 60 秒内通知" 依赖短租约）

阶段 5（/chat 投队列）
   └─→ 阶段 6（统一回放才有意义）
         └─→ 阶段 7、8
```

**阶段 3 必须在 4 之前** —— 否则降租约会误杀长任务。

## 七、验收标准

### 7.1 刷新恢复（核心）

| # | 检查 | 期望 |
|---|---|---|
| 1 | 聊天生成到一半刷新 | **100ms 内看到已生成内容** |
| 2 | 刷新前后内容 | **不重复、不丢失** |
| 3 | 连续刷新 10 次 | **模型 token 消耗不增加**（这条最硬，证明是重放不是重跑） |
| 4 | 深度研究刷新 | 步骤列表重建 + 继续接收新事件 |
| 5 | APP 杀进程再回来 | 看到完整终态 |

### 7.2 长任务不阻塞

| # | 检查 | 期望 |
|---|---|---|
| 6 | 深度研究跑着时发聊天 | 聊天**立即开始**（不等 research） |
| 7 | 8 个聊天并发 | 全部并行执行 |
| 8 | 深度研究并发上限 | 2 个，超出的排队 |

### 7.3 崩溃可见与重试语义

| # | 检查 | 期望 |
|---|---|---|
| 9 | kill -9 worker（chat 任务） | 前端 **2 分钟内**看到「回答生成中断，请重新提问。」 |
| 10 | kill -9 worker（research 任务） | 前端看到「执行中断，请重试。」 |
| 11 | 崩溃后事件表 | 有 `error` + `done` 两条 |
| 12 | **`chat` 首次崩溃** | **判 `failed`，不重新入队** |
| 13 | **`research` 首次崩溃** | 判 `queued`，重跑一次 |
| 14 | `research` 第二次崩溃 | 判 `failed` |
| 15 | **`done.retryable`** | chat 为 `false`，research 为 `true` |
| 16 | 前端按钮 | `retryable=false` 时显示「重新提问」，不自动重试 |
| 17 | 点「重新提问」 | 发送同一问题，**新建 run**（不复用死掉的 run）|

### 7.4 心跳与租约

| # | 检查 | 期望 |
|---|---|---|
| 18 | 跑 5 分钟的 research 任务 | **不被误判崩溃**（心跳持续续租）|

| # | 检查 | 期望 |
|---|---|---|
| 24 | 重试时事件 | 不混在一起（`run_id` 区分） |

## 八、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **租约 900 秒太长** | worker 崩溃后，任务 15 分钟才被回收 | **降到 120 秒**，配合心跳续租（阶段 3）|
| **降租约但不做心跳** | 所有 >2 分钟的任务被误判崩溃并重跑 | **阶段 3 必须在阶段 4 之前** |
| 8+2 协程抢同一条任务 | 都空转 | `SKIP LOCKED` 已保证安全，但 `claim` QPS 升高 |
| 轮询 50ms 增加 DB 压力 | 空闲时 200 QPS | 监控 `pg_stat_statements`；真不够再上 `LISTEN/NOTIFY` |
| **`/chat` 改队列后首字延迟 +50ms** | 用户感知 | 实测；人眼阈值约 100ms |
| `snapshot` 整体替换可能闪烁 | 视觉 | 前端只在长度增长时重绘 |
| 迁移回填 11267 行 | 一次性锁表 | 用 `update ... from` 单条 SQL，秒级 |
| **误判 `run_type`** | 难题按 chat 资源跑，30 秒断流 | 前端超时后提示「转深度研究」 |
| **chat 不重试导致偶发失败** | 用户需手动重问 | 埋点统计 chat 崩溃率，超阈值再考虑重试 |

## 十、明确不做的清单

| 不做 | 原因 |
|---|---|
| 断点续跑（checkpoint） | BISHENG 试过并放弃（`save_workflow_object` 被注释掉）。工具中间态无法序列化，恢复后答案可能不同——投研场景确定性优先。**先埋点度量，两周后看数据再决定** |
| 两张独立队列表 | PostgreSQL 里队列是查询 + 部分索引，不是表结构 |
| Redis pub/sub | 先 PG 轮询，实测延迟不够再上 |
| `workers` 心跳表 | 用「有无 running」间接判断 worker 是否活着 |
| prefill 自动续写 | 交用户决定 |
| 事件分区归档 | 数据量未到 |
| 多设备 client_id | 未触发 |
| `after_len` 字符游标 | 事件序列撑不住字符语义 |
| **chat 重试** | 3 秒任务重试收益低于复杂度；改为「不重试 + 立即通知 + 手动重问」 |
| **Agent 异常重试** | 确定性失败（同输入必同错），重试无意义 |
