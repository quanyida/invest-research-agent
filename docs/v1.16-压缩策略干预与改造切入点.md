## 1. 本文解决什么问题

v1.15 记录了 AgentScope 压缩机制本身的源码分析。本文补两块：

1. **本项目对 AgentScope 压缩做了哪些干预**（有哪些、在哪、是否生效）；

## 2. 项目自身的压缩逻辑：五处

先区分「项目自己的压缩」和「借用框架的压缩」。

| # | 名称 | 归属 | 触发时机 | 是否生效 |
|---|---|---|---|---|
| ① | `compact_agent_state()` | 项目 | **每轮落库前无条件** | ✅ 必然执行 |
| ② | 512KB 体积检查 | 项目 | 状态序列化超限 | ⚠️ 极罕见（需约 80 轮） |
| ③ | `ContextPruningMiddleware` | 项目 | 框架压缩被触发时 | ❌ 不触发 |
| ④ | `_summarize_history()` | 项目 | 状态重建时 | ✅ 重建时执行 |
| ⑤ | `tool_result_limit` | 框架 | 单次工具结果超限 | ✅ 每轮 |

### 2.1 ① compact_agent_state：确定性剥离

位置：`app/agent/agent_state_store.py:27`

```python
released = compact_agent_state(agent.state)   # 每轮落库前无条件调用
```

剥离规则：

| 块类型 | 处理 |
|---|---|
| `tool_call` / `tool_result` / `thinking` / `hint` | 删除 |
| assistant 的 `text` | 剥掉引用标记，空则删 |
| `summary` | 剥掉引用标记 |

**这是唯一「每次都跑」的压缩**，把工具原文全部剥光，只留问答文本。

性质：确定性、不调模型、零成本。

### 2.2 ② 512KB 检查：项目自设上限

位置：`app/agent/agentscope_runtime.py:439-452`

```python
try:
    state_payload = state_store.serialize(agent.state)   # 内部检查 512KB
except AgentStateTooLarge:
    try:
        await agent.compress_context()                    # 借框架压缩
        state_payload = state_store.serialize(agent.state)
    except Exception:
        state_skipped = True
        skip_reason = "compression_error"
```

**`AgentStateTooLarge` 是项目自定义异常**（`agent_state_store.py:20`），父类是 `RuntimeError`，携带 `size_bytes` 属性（但当前无人读取）。

**注意：写空 payload 的行为已于 2026-11-21 移除**，现在失败时不写，保留上次成功状态。

### 2.3 ③ ContextPruningMiddleware：中间件包装

位置：`app/agent/context_pruning.py`

```python
async def on_compress_context(self, agent, input_kwargs, next_handler):
    self._prune(agent.state, self.keep_recent_tool_results)   # 前置裁剪
    if self.fallback_mode is not None:
        return
    for attempt in range(2):
        try:
            await next_handler()          # 调框架压缩
            return
        except Exception:
            if attempt == 0:
                self._prune(agent.state, 1)   # 裁更狠再试
                continue
    self.fallback_mode = "keep_context"   # 两次失败，接管降级
```

**它是包装，不是重写。** 详见第 3 节。

### 2.4 ④ _summarize_history：重建时摘要

位置：`app/agent/agentscope_runtime.py:240`

仅在 `state_rebuilt=True` 时执行，把早期轮次压成摘要作为 `state.summary`。

**这是唯一真正会跑起来的语义压缩。**

### 2.5 ⑤ tool_result_limit：框架层截断

```python
ContextConfig(tool_result_limit=max(6000, settings.tool_result_limit))   # 32000
```

单次工具结果进上下文的上限（32000 字符），由框架执行截断，**不是抛异常**。

## 3. ContextPruningMiddleware 是包装而非重写

### 3.1 机制

AgentScope 的 `compress_context()` 走中间件链：

```
compress_context()
  └─ ContextPruningMiddleware.on_compress_context()
       ├─ 前置：裁工具原文
       ├─ 调用 next_handler()
       │    └─ AgentScope._compress_context_impl()   ← 真正的压缩在这
       └─ 后置：失败重试 / 接管降级
```

**`_compress_context_impl` 完全未被改动。**

### 3.2 next_handler 是关键

中间件有两条路：

1. **调用它** → 框架照常压缩，只是输入已被裁剪；
2. **不调用它** → 框架压缩根本不执行。

**所以是「拦截」，不是「替换」。**

### 3.3 唯一真正接管的地方

```python
self.fallback_mode = "keep_context"
```

项目配置了 `compression_fallback_to_truncation=False`，框架本来会抛异常；
中间件捕获它，转换成「保留上下文不截断」。

**准确表述**：它没有重写压缩，而是**接管了压缩失败后的降级处理**。

### 3.4 与「重写」的对比

| | 重写 | 本项目做法 |
|---|---|---|
| 改动框架源码 | 是 | **否** |
| 替换压缩算法 | 是 | 否 |
| 依赖私有方法 | 可能 | **否**（只用 `MiddlewareBase` 公开钩子） |
| 上游升级影响 | 大 | **小** |

## 4. 项目对框架压缩的四个干预点

| # | 干预方式 | 位置 | 生效时机 | 实际效果 |
|---|---|---|---|---|
| 1 | 配置覆盖 | `_context_config()` | 每轮 | ✅ 生效 |
| 2 | 中间件拦截 | `ContextPruningMiddleware` | 框架压缩时 | ❌ 不触发 |
| 3 | 主动触发 | `_persist()` 里 `await agent.compress_context()` | 512KB 超限 | ⚠️ 基本无效 |
| 4 | 观测探针 | `ContextProbeMiddleware` | 每次模型调用 | ✅ 生效 |

### 4.1 干预 1：配置覆盖

```python
def _context_config(self) -> ContextConfig:
    return ContextConfig(
        tool_result_limit=max(6000, self.settings.tool_result_limit),   # 32000
        trigger_ratio=0.7,                                              # 上游默认 0.8
        compression_fallback_to_truncation=False,                       # 上游默认 True
    )
```

两个关键改动：

| 参数 | 上游默认 | 项目值 | 影响 |
|---|---|---|---|
| `trigger_ratio` | 0.8 | 0.7 | 阈值降低（但基数 1M，实际无感） |
| `compression_fallback_to_truncation` | True | **False** | **压缩失败抛异常，不静默截断** |

第二个是重要干预：**宁可这轮失败，也不静默丢上下文**。

### 4.2 干预 3 的逻辑漏洞

| 触发点 | 单位 | 阈值 |
|---|---|---|
| 中间件 | token | 70 万 |
| 主动调用 | 字节 | 512KB ≈ 47 万 token |

**512KB 比 70 万 token 更早到。**

所以主动调 `compress_context()` 时，框架内部检查判定「没到阈值」直接返回——
**压了个寂寞**，第二次序列化仍超限，标记 `compression_error`。

**结论：干预 3 基本无效，因为两个阈值不同步。**

### 4.3 干预 4：ContextProbeMiddleware（值得肯定）

位置：`app/agent/context_probe.py`

```python
class ContextProbeMiddleware(MiddlewareBase):
    """Record what the model actually receives on the first call of a turn.

    This uses the public ``on_model_call`` hook, so it does not depend on
    AgentScope internals. The snapshot proves whether the rebuild summary and
    the recent questions really reached the prompt.
    """
```

它不修改任何行为，只验证：

| 字段 | 证明什么 |
|---|---|
| `summary_present` | 重建摘要真的进了 prompt |
| `recent_questions_present` | 近期问题真的进了 prompt |
| `prompt_chars` | 实际 prompt 长度 |

**这解决了「字段写了但框架没使用」这类隐性失败**，是「验证优先」的实践。

## 5. 当前的真实状态

| 逻辑 | 是否真的会执行 | 原因 |
|---|---|---|
| ① `compact_agent_state` | ✅ 每次 | 无条件调用 |
| ② 512KB 检查 | ⚠️ 几乎不触发 | 10 轮约 60KB，需约 80 轮 |
| ③ `ContextPruningMiddleware` | ❌ 不触发 | 依赖框架压缩，阈值 70 万 token |
| ④ `_summarize_history` | ✅ 重建时 | 状态缺失/缺口过大时 |
| ⑤ `tool_result_limit` | ✅ 每轮 | 框架执行 |

**实际生效的只有 ①④⑤。**

②③ 是为极端情况准备的防御，当前使用强度够不到。

## 6. 如果要重写压缩策略：五个切入点

按侵入性从低到高。

### 切入点 1：配置参数（最轻）

```python
ContextConfig(
    trigger_ratio=0.7,
    reserve_ratio=0.1,
    tool_result_limit=32000,
    compression_prompt="...",
    summary_template="...",
    summary_schema={...},
    compression_fallback_to_truncation=False,
    compression_tool_enabled=False,
    max_image_num=5,
)
```

**上限**：只能调数值和提示词，流程不变。**当前已用。**

**让压缩真正生效的最直接办法**：改 `LLM_CONTEXT_SIZE` 而非 `trigger_ratio`。

```python
LLM_CONTEXT_SIZE: 1_000_000 → 200_000
```

阈值变成 14 万 token，单轮峰值 25 万就能触发。

### 切入点 2：中间件完全接管

```python
class MyCompressionMiddleware(MiddlewareBase):
    async def on_compress_context(self, agent, input_kwargs, next_handler):
        if should_custom_compress(agent.state):
            await my_own_compress(agent)
            return                          # ← 不调 next_handler
        await next_handler()
```

**理论上可以用中间件完全替换压缩**——只要不调 `next_handler()`。

**限制**：钩子无返回值，只能改 `agent.state`。需要自己实现切分、摘要、更新 `state.summary` 和 `state.context`。

**这等于重写一遍 `_compress_context_impl`，只是挂载在公开钩子上。**

### 切入点 3：自定义摘要结构（性价比最高）

```python
ContextConfig(
    summary_schema={"type": "object", "properties": {...}},
    summary_template="...{your_field}...",
    compression_prompt="...",
)
```

**「改内容不改流程」。**

投研场景建议的四段（替代默认的 Task Overview / Current State / Important Discoveries / Next Steps）：

```
# 分析对象     {entity}
# 已确认事实   {confirmed_facts}     带引用
# 关键数据     {data_points}
# 数据缺口     {data_gaps}           ← 投研最需要，默认模板没有
# 未完成追问   {pending_questions}
```

**投研最需要的是「数据缺口」——哪些数据没取到。默认模板里没有这个字段。**

### 切入点 4：重写 Agent 子类（真正的替换）

```python
from agentscope.agent import Agent

class InvestmentAgent(Agent):
    async def _compress_context_impl(self, context_config=None, instructions=None):
        ...
```

**唯一能真正重写算法的方式。**

**风险**：`_compress_context_impl` 是私有方法，上游改名或改签名就断。

`docs/v1.8` 已警告：

> 上游 `app` 层迭代很快（v2.0.x 仍在变），fork 即锁定。

**但压缩逻辑对业务足够重要时，这是合理代价。**

### 切入点 5：fork 源码

**不推荐**。除非要改框架整体架构，切入点 4 已够用。

## 7. 建议的推进顺序

```
1. 改 LLM_CONTEXT_SIZE，让压缩真正触发
   ↓ 验证：meta.context_compression 里 compression_attempts > 0

2. 观察默认摘要在投研场景下的质量
   ↓ 预期问题：丢失数据缺口、引用失效

3. 改 summary_schema + summary_template（切入点 3）
   ↓ 验证：摘要包含投研必需字段

4. 仍不够 → 中间件完全接管（切入点 2）
   ↓ 验证：完全不用 next_handler

5. 最后才考虑子类重写（切入点 4）
```

**不要跳到 4、5 步。** 改配置解决 80% 问题，改 schema 解决剩余 15%，
真需要重写算法的场景很少。

---

## 8. 决策前必须明确的问题

**「重写压缩策略」到底要解决什么问题？**

当前状况是「压缩不触发」。不同诉求对应不同切入点：

| 诉求 | 切入点 |
|---|---|
| 想让它更早压缩 | 改 `LLM_CONTEXT_SIZE`（不需要重写） |
| 想压缩后保留更多细节 | 改 `reserve_ratio` + `summary_schema` |
| 想压缩时保留特定信息 | 改 `summary_template` |
| 想要完全不同的压缩逻辑 | 切入点 4 |

**先明确目标再选切入点，否则容易过度设计。**
