# v1.4 AgentScope 全链路方案（Agent 直接成文 + PG 状态）

日期：2026-11-17

状态：方案待确认，本轮不改业务代码

取代：`v1.3-AgentScope改造方案.md`。本版只改三处决策（成文、状态、链路），工具层 / 权限 / 事件桥接 / 异步 / 验收沿用 v1.3。

## 0. 本版相对 v1.3 的变更

| 项 | v1.3 | v1.4 |
|---|---|---|
| 成文 | Agent 只取数，现有 compose 写答案 | Agent 直接写最终答案，删除 compose |
| 状态 | 不持久化 AgentState，每轮从 `messages` 重建 | AgentState 持久化到 Postgres，与消息同事务提交 |
| 链路 | legacy / agentscope 双引擎 | 单一 AgentScope 链路，flag 只作 P1-P2 回滚开关 |
| 校验 | verify 在 compose 之后 | verify 在 Agent 输出之后；失败触发 Agent 自我修订一轮 |
| 引用修复 | `repair_citations` | 保留，前移到 verify 之前（确定性、无 LLM） |

## 1. “全链路”的边界定义

一次请求内，所有 LLM 推理和所有工具调用都由同一个 AgentScope `Agent` 实例驱动：没有 plan 调用、没有 compose 调用、没有 repair 调用，不存在第二条 LLM 链路。

不走 Agent 的只有基础设施：

- 鉴权 / 配额 / RLS / 限流
- 工具网关（iFinD 传输、缓存、熔断、parser）
- `evidence / tool_calls / llm_calls / usage_daily` 落库
- `verify`（确定性规则，不是 LLM）
- SSE 编码与发送

明确不进入 Agent 上下文：`tenant_id` / `user_id` UUID、数据库连接、MCP token、其他租户的工具。

## 2. 目标链路

```text
POST /api/v1/chat
  -> 鉴权 / 配额 / RLS / 写入 user + assistant 占位
  -> AgentScopeRunner.stream(run)
       |- AgentStateStore.load(conversation_id)          # PG JSONB
       |- CapabilityResolver -> 允许工具集（纯规则）
       |- Agent(model, toolkit, state, react_config)
       `- reply_stream(UserMsg(question))
            |- Model -> ToolCall -> IfindTool.call() -> gateway -> parser -> facts
            |            `- EvidenceCollector: evidence / audit / fact_id
            |- 工具结果压缩成 observation 回给模型
            `- 最终 Msg（Agent 写的答案）
       |- AnswerGuard: extract -> repair_citations -> verify
       |    |- pass -> 采用
       |    `- fail -> 同一 state 新建无工具 Agent 修订一轮 -> 再校验
       |         `- 仍 fail -> evidence_digest_answer（模板，无 LLM）
       `- 一个事务写入: assistant message + evidence + tool_calls
                       + llm_calls + usage_daily + agent_state
  -> SSE: meta/plan/tool_start/tool_end/evidence/verify/delta/usage/done
```

关键点：`agent_state` 与 `assistant message` 在同一事务提交，避免“消息写了但状态没落”或反之。

## 3. Agent 直接成文

### 3.1 提示词

沿用现有 25 条规则（`app/agent/context.py` 的 `SYSTEM_PROMPT`），只改三处：

1. 数据来源从 `<evidence>` 改为 `<tool_observation>` 里带 `fact=` 的行。
2. 增加 ReAct 约束：取数充分才写答案；工具调用之间不要输出答案；不要重复同参数调用；预算是硬约束。
3. 增加“最终答案一次性输出四段”的约束。

以下内容不能删：

- 四段格式：`结论：` / `关键数字：` / `正文：` / `边界：`
- 每个数字后必须跟 `[E7-1]` 形式的 fact 级引用
- 金额统一亿元两位小数、股本亿股/万股、比率两位小数
- 累计口径不得写成单季、不得自行算同比/环比/差值

原因：`verify_answer()` 硬性检查四段标签、引用存在性和数字可追溯性。删掉任何一条，verify 会全量失败。

### 3.2 只取最终消息

ReAct 过程中模型可能输出“我先查一下……”，这些不是答案。

- 用 `reply_stream(..., yield_final_msg=True)` 产出的最后一条 `Msg` 作为答案。
- 不拼接全部 `TextBlockDelta`。
- `extract_answer()` 从第一个 `结论：` 处截断，丢掉前面的过程说明。

### 3.3 AnswerGuard（确定性闸门）

顺序固定，不跳步：

1. `evidence_count == 0` -> `no_evidence_answer()`，status=degraded，不进 verify。
2. `repair_citations(text, evidences)` -> 自动补/改引用（无 LLM）。
3. `verify_answer(text, evidences)` -> issues。
4. issues 非空 -> 修订轮：
   - 用**当前 state** 新建一个 Agent，`Toolkit(tools=[])`，`ReActConfig(max_iters=1)`。
   - 输入 `UserMsg`，内容是 issues 原文 + “只修这些问题，不要重新取数”。
   - 只取最后一条 Msg 的文本。
   - 最多 1 轮。
5. 仍失败 -> `evidence_digest_answer()`：纯模板列出已校验 fact（entity / period / metric / value / unit / fact_id），声明“自动生成，未经模型组织”。

修订轮用无工具 Agent 的原因：预算此时通常已耗尽，给工具只会让模型反复重试；无工具 + 单次迭代能保证它只重写文本。

`verify` 不改成 LLM 裁判：规则校验可复现、零成本、不引入新的幻觉源。

### 3.4 降级与状态

| 情况 | status | 答案 |
|---|---|---|
| verify 通过 | ok | Agent 答案 |
| 修订后通过 | ok，`meta.repaired=true` | 修订后答案 |
| 两轮都不通过 | degraded | `evidence_digest_answer` |
| 无 evidence | degraded | `no_evidence_answer` |
| 工具全失败 | degraded | `tool_error_answer` |

`finished_reason != completed`（暂停等 HITL / 外部执行）时，直接按 `AGENT_PAUSED_UNSUPPORTED` 失败，不落半成品答案。

## 4. Postgres 持久化

### 4.1 为什么不用内置 `AsyncSQLAlchemyStorage`

AgentScope 提供 `AsyncSQLAlchemyStorage`（`pip install agentscope[sql]` + `asyncpg`），确实能落 PG。但：

- 它自己建表（Alembic 迁移），表上没有我们的 `tenant_id / user_id` 列和 RLS 策略。
- 契约覆盖 agents / credentials / sessions / messages / schedules / teams / knowledge，我们只用得到一小部分。
- 直接用它，租户隔离会从“数据库强制”退化成“应用层自觉”，这条不能让步。

因此 v1 自己实现窄接口 `AgentStateStore`，只做两件事，全部走 `tenant_scope()`（RLS 生效）：

```python
class AgentStateStore:
    def load(self, conversation_id) -> tuple[AgentState | None, int]: ...
    def save(self, conversation_id, state, expected_version) -> bool: ...
```

以后真上 Agent Service，再把这层升成 `StorageBase` 适配器。现在不为一个不用的抽象写 20 个空方法。

### 4.2 表结构

新增 `infra/sql/005_agent_state.sql`：

```sql
alter table conversations
  add column if not exists agent_state jsonb not null default '{}'::jsonb,
  add column if not exists agent_state_version integer not null default 0,
  add column if not exists agent_state_updated_at timestamptz;
```

- 不新增表；RLS 策略已覆盖 `conversations`，新列自动继承。
- `messages` 仍是会话事实源；`agent_state` 是可丢弃的加速层。

### 4.3 读写时机

- 读：请求开始，`tenant_scope` 内普通 `select`。
- 写：与 assistant message 同一事务：
  `update conversations set agent_state=:s, agent_state_version=agent_state_version+1, agent_state_updated_at=now() where id=:id and agent_state_version=:v`
- 影响行数 0 -> 并发冲突：记 `agent_state_conflict`，本次不重试、不报错给用户，下一轮从 `messages` 重建。

### 4.4 体积与失效

- 序列化收敛在 `state_to_json / state_from_json` 两个函数里（`state.model_dump(mode="json")`，具体 API 以 P0 实际包为准）。
- `AGENT_STATE_MAX_KB` 默认 512。超限先 `agent.compress_context()` 一次；仍超限就存 `{}` 并置 `meta.agent_state_skipped=true`。
- 读回失败（schema 漂移、字段缺失、JSON 损坏）-> 记日志、当 `None` 处理、从 `messages` 重建。
- JSON 顶层写 `schema_version`；与 `AGENT_STATE_SCHEMA_VERSION` 不匹配就丢弃重建。

### 4.5 重建路径

`agent_state` 为空时：

1. 读最近 `HISTORY_TURNS` 轮 `messages`。
2. `await agent.observe(...)` 注入 user / assistant 对。
3. 只注入正文，不注入历史 evidence id。

## 5. fact 编号必须按轮唯一（上线前置条件）

现状：每个 assistant message 的 evidence 都从 `E1` 开始（`app/agent/loop.py:465`、`app/tools/parser.py:396`）。

一旦 AgentState 长期保留历史消息，历史里的 `[E1-1]` 会和本轮新生成的 `[E1-1]` 撞号：模型引用上一轮数字时，verify 会拿本轮的 fact 比对并通过 —— 这是**静默错答**，比报错严重得多。

修法（最小改动）：

- evidence / fact 编号改为 `E{turn}-{seq}`，`turn` = 该 assistant 消息在会话内的序号（1 起）。
- `parser` 增加 `fact_prefix` 参数，`EvidenceCollector` 传入 `f"E{turn}"`。
- DB 的 `evidence.seq` 不变，仍用于排序。
- `verify` 的 `\[E\d+-\d+\]` 正则不用改。

这条不修，就不能开 AgentState 持久化。

## 6. AgentScope 装配

```python
agent = Agent(
    name="investment_research_agent",
    system_prompt=build_agent_system_prompt(run_context),
    model=OpenAIChatModel(
        credential=OpenAICredential(api_key=settings.llm_api_key, base_url=settings.llm_base_url),
        model=settings.llm_model,
        stream=settings.model_stream,
    ),
    toolkit=Toolkit(tools=allowed_tools, skills_or_loaders=[str(SKILLS_DIR)]),
    state=loaded_state or AgentState(),
    react_config=ReActConfig(max_iters=min(settings.max_steps, settings.max_tool_calls + 1)),
    context_config=ContextConfig(tool_result_limit=6000, trigger_ratio=0.7, compression_fallback_to_truncation=False),
)
```

> 注：上下文压缩口径已在 `v1.12-上下文压缩与降级策略讨论.md` 更新：`context_size=1000000`、`trigger_ratio=0.7`、触发阈值 `700000`，并启用 `ContextPruningMiddleware`；本节保留为 v1.4 设计基线。

模型说明：

- 复用现有 `.env` 的 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`，不新增供应商。
- `stream=True` 需要 P0 验证“tool calling + 流式”是否同时可用；不可用就退 `stream=False`。
- 因为答案本来就要校验后才发，`stream=False` 的用户体感损失只有首字延迟，可接受。
- 不再使用 `app/llm/client.py` 发起推理；它只在 P3 之前保留给未迁移的调用点。

## 7. SSE 事件桥接

对外事件名保持不变，前端零改动。

| AgentScope 事件 | SSE | 说明 |
|---|---|---|
| `ReplyStartEvent` | `meta` 补 `engine/reply_id` | 不新增必需事件 |
| `ModelCallStartEvent` | 不发，或 30s 一次 `ping` | 防刷屏 |
| `ToolCallStartEvent` | `tool_start` | 先发工具名 |
| `ToolCallEndEvent` | `tool_start` 补参数 | 以完整入参为准；或发 `decision`，前端会忽略 |
| `ToolResultEndEvent` | `tool_end` | 状态、耗时、错误码由 `EvidenceCollector` 提供 |
| `TextBlockDelta` | 缓冲 | verify 通过后才发 |
| `ThinkingBlockDelta` | 丢弃 | 不暴露思维链 |
| 最终 `Msg` | `usage` | token 汇总 |
| AnswerGuard 失败 | `verdict`（新增，前端忽略） | 便于排查 |
| 异常 | `error` + `done` | 统一错误码 |

`ANSWER_STREAM_MODE`：

- `verified`（默认）：答案校验后再发 `delta`
- `immediate`：边生成边发，校验失败时追加一条“更正”`delta`

v1 用 `verified`。投研场景里“先给错数字再更正”比“多等一次校验”代价大。

`delta` 建议按 40-80 字切分发送，保持现有逐字观感。

## 8. 异步 / 取消 / 超时

沿用 v1.3，补充三点：

- `TASK_TIMEOUT_SECONDS` 是整条链路（取数 + 成文 + 修订）的上限，不是单次模型调用。
- 客户端断开：取消 `reply_stream` 后**不写** `agent_state`，避免把半截状态存下来；assistant 标 `cancelled`。
- 状态与消息写入用 `asyncio.to_thread` 包同步 SQLAlchemy；正常完成路径可用 `asyncio.shield` 保证落库，取消路径不写 state。

## 11. 验收

v1.3 的 9 条继续有效，新增 6 条：

| 用例 | 输入 / 操作 | 期望 |
|---|---|---|
| 状态恢复 | 同会话先问“谷歌 2024 营收”，再问“它的净利润呢” | 第二轮继承实体，不重复追问；state 版本 +1 |
| 状态损坏 | 手动把 `agent_state` 改成 `{"bad":1}` | 自动从 `messages` 重建，回答正常，meta 有 `agent_state_rebuilt` |
| 状态并发 | 两个请求同时写同一会话 | 一个成功一个 conflict；两边回答都正常 |
| 直接成文 | 问茅台毛利率 | 四段格式齐全；每个数字带引用；无“我先查一下” |
| 修订轮 | 人为让首版漏引用 | 触发一轮修订后 ok，`meta.repaired=true` |
| 跨轮撞号 | 第二轮故意引用上一轮的 `[E1-1]` | verify 判为“引用不存在”，不得误通过 |

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 模型不守四段格式 | verify 失败 -> 修订轮 -> 模板降级；prompt 给 1 个 few-shot |
| Agent 边取数边写答案 | 只取最终 Msg + `extract_answer`；prompt 禁止过程输出 |
| 答案 token 变多（上下文含全部工具结果） | observation 压缩 + `tool_result_limit` + 压缩阈值 |
| AgentState 膨胀 | 512KB 上限 + `compress_context` + 丢弃重建 |
| 状态并发写 | 乐观版本号，冲突即跳过 |
| 历史引用撞号 | 第 5 节按轮编号，不修不上线 |
| 修订轮死循环 | 无工具 Agent + `max_iters=1` + 只跑一次 |
| 延迟上升 | 增量主要是答案 token；P2 用 P95 卡住 |
| 断连写坏状态 | 取消路径不写 state |
| 无 compose 后的文风退化 | `evidence_digest_answer` 保证结构完整，宁可难看不可错 |

## 13. 明确不做

Agent Service、Agent Team、Workspace 沙箱、RAG、用户自定义 skill/mcp、HITL、跨请求断点续跑、前端改造、评测平台。

不做 HITL 意味着 `finished_reason=None` 一律按失败处理。
