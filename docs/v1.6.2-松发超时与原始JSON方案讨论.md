# v1.6.2 松发超时与 iFinD 原始透传方案讨论

日期：2026-11-18
状态：已实现（v1.6.2 原始透传），待网页验收

> 2026-11-18 最新决定：按用户要求改为**原始透传**，程序不解析、不抽取 facts、不改写 iFinD 返回内容。第 3-6 节是上一版“业务原文 + facts”方案，已作废；以第 7 节为准。

## 1. 现象

问题：`深度分析下松发股份`

前端提示：`核对未通过 · timeout`

服务日志关键时间线：

- 12:17:19：模型调用返回。
- 12:17:23 至 12:17:30：iFinD 工具调用返回，取数阶段约 10 秒。
- 12:19:31：出现模型请求重试。
- 12:20:39：模型调用返回。
- 12:22:00：整轮任务触发 300 秒超时，进入证据摘要降级。

这不是工具取数失败，也不是解析失败，而是**成文阶段的模型调用与重试耗尽了整轮预算**。

## 2. “核对未通过 · timeout”的语义问题

当前 `agentscope_runtime.py` 在超时降级时写入：

```python
final_verify = VerifyResult(passed=False, issues=[answer_source])
```

但超时降级生成的摘要本身通常是可通过 fact 校验的。把 `timeout` 放进 `verify.issues`，前端就会把它显示成“核对未通过”，语义上不准确。

更合理的语义：

- `verify.passed=true`：摘要仍可校验。
- `degraded=true`：本轮没有完成完整生成。
- `degraded_reason=timeout`：降级原因是超时。
- 前端显示“生成超时，展示证据摘要”，而不是“核对未通过”。

## 3. 上一版方案：原始 JSON 与业务原文的边界（已作废）

结论：**Agent 必须看到 iFinD 返回的业务原文，但不应该看到 MCP/JSON-RPC 传输层信封。**

这里要区分三种东西：

1. **传输层原始 JSON**：`result.content[0].text` 外层还是 JSON 字符串，里面包含 `data.answer`、`data.tables`、`data.data` 等不同形态。
2. **业务原文**：财务 Markdown 表格、指标口径、新闻标题/日期/来源/正文、公告描述、行情表格。这是投研判断真正需要读的内容。
3. **facts**：从业务原文中抽取出的可校验数值锚点，用来支撑 `[E1-1]` 引用和防止模型编数字。

当前实现的问题不是“facts 不够多”，而是**业务原文没有进入 Agent 上下文**：`EvidenceCollector._observation()` 在工具成功且存在 facts 时只输出 facts，`raw_excerpt` 完全不输出；新闻又被压成一条约 500 字的 `unit=text` fact，正文和上下文大量丢失。Agent 只能看到数字，无法判断业务结构、事件含义、机构观点和风险。

### 3.1 实测体积

对松发股份分别调用四类工具，当前规范化 observation 与原始 JSON 的体积：

| 工具 | facts | 当前 observation | 原始 JSON |
|---|---:|---:|---:|
| `stock_financials` | 77 | 5622 字符 | 2277 字符 |
| `stock_quote` | 3 | 401 字符 | 568 字符 |
| `news_search` | 58 | 6008 字符 | 3996 字符 |
| `stock_events` | 9 | 851 字符 | 1031 字符 |
| 合计 | 147 | 12882 字符 | 7872 字符 |

原始 JSON 在这个样本里反而更短，但这是因为它把数据压成了嵌套字符串和二维数组，并不代表它更适合模型推理。真正应该比较的是“业务原文 + 精简 facts”与当前“只有 facts”的效果。

### 3.2 业务原文的优点

- 保留业务语义，Agent 能理解“公司靠什么赚钱、发生了什么、机构怎么看”。
- 财务表格和指标口径可以直接对照，不需要模型从 fact 行反推。
- 新闻标题、日期、来源和正文能支撑事件驱动判断。
- 公告描述和条件能支撑风险、催化剂和后续跟踪。
- 业务原文比展开后的 fact 行通常更短，信噪比更高。

### 3.3 直接塞传输层 JSON 的缺点

- MCP/JSON-RPC 信封不是研究内容，模型要花 token 解析嵌套结构。
- `result.content[].text` 是 JSON 字符串，内部还有多种 data 形态，字段名随工具变化。
- 原始 JSON 没有稳定的 `fact_id`，无法直接支撑当前的 `[E1-1]` 引用和数字校验。
- 无关字段、分页信息、内部状态会一起进入上下文，降低信噪比。
- 传输层 JSON 不能替代业务原文，也不能解决本次超时的根因。

因此：

- **Agent 推理**：必须看业务原文。
- **数字引用与校验**：继续用 facts 作为 sidecar。
- **审计/调试**：完整原始 JSON 落盘，记录 `raw_ref`，按需回查。
- **本次超时**：要同时修 deadline/重试和工具结果预算。

## 4. 上一版推荐方案（已作废）

### 4.1 主上下文：业务原文优先，facts 作为校验 sidecar

每个工具成功返回后，observation 同时包含两段：

```text
<tool_observation tool="ifind.stock_financials" status="ok" as_of="2026-09-30" raw_ref="E1">
<source_text>
|证券代码|证券简称|日期|营业收入（单位：元）|...|
|---|---|---|---|
|603268.SH|松发股份|20260930|...|...|
</source_text>
<facts>
[E1-1] entity=松发股份 | period=2026-09-30 | metric=营业收入 | value=123.45 | unit=亿元
[E1-2] entity=松发股份 | period=2026-09-30 | metric=归母净利润 | value=12.34 | unit=亿元
omitted: 37 facts
</facts>
</tool_observation>
```

各工具的业务原文取舍：

- `stock_financials`：保留 `data.answer` 的 Markdown 表格、`indicators_params` 里的指标口径/单位/币种/报告期；不要只输出数字行。
- `news_search` / `notice_search`：逐条保留标题、日期、来源、URL、正文或摘要；不要压成一条 500 字 text fact。
- `stock_events` / `global_events`：保留事件标题、日期、原始描述、条件、影响对象。
- `stock_quote`：保留 `data.tables` 的原始表格，不要只给 3 条 facts。
- 表格类原文优先保留完整表格；确实超预算时按行截断，并明确写 `source_truncated`。
- facts 只保留数值锚点和必要的文本锚点，建议每个工具最多 20-30 条，并标注 `facts_total` / `omitted`。
- 业务原文中的数字仍应尽量映射到 numeric fact；Agent 引用数字时必须引用 `[E1-1]`。
- 定性判断可以基于 `<source_text>`，但要在正文中说明依据；不要把原文里没有的数字写进答案。

工具结果预算也要同步调整：当前 `ContextConfig(tool_result_limit=6000)`，而松发新闻的当前 observation 已经是 6008 字符，刚好会被截断。建议把单工具结果上限提高到 12000-16000 字符，并在 observation 内明确标记截断位置；如果需要同时保留多工具原文，则由上下文压缩策略按“原文优先、facts 精简”处理，而不是优先丢原文。

系统提示词需要同步调整：

- `<source_text>` 是业务事实上下文，用于理解业务、事件和观点。
- `<facts>` 是数字引用和校验的唯一锚点。
- 数字必须来自 numeric fact 并带引用；定性结论必须能在 `<source_text>` 找到依据。
- 不得因为看到了原文就自行计算同比、环比、差值；需要计算时只引用已有变化 fact。

### 4.2 完整原始 JSON 只做“可回查的审计旁路”

- 将完整原始 JSON 落盘或入库，记录 `raw_ref`。
- Agent 主上下文只看到 `raw_ref`，不直接看完整 JSON。
- 需要细节时再调用 `ifind_raw_lookup(raw_ref, path, limit)`，按需取一个字段或一段表格。
- 这样既保留完整性和可审计性，又不把传输层结构塞进主上下文。

### 4.3 修 deadline 与重试

当前风险点：

- `LLM_TIMEOUT_SECONDS=120`
- `TASK_TIMEOUT_SECONDS=300`
- `MODEL_MAX_ATTEMPTS=4`

一次模型超时如果连续重试，很容易吃满 300 秒。建议：

- 每次模型调用的 timeout 取 `min(120, budget.remaining() - 15)`。
- 超时不要重试 4 次；最多重试 1 次，或只对连接错误/5xx 重试。
- 工具取数完成后，给最终成文保留明确时间窗；剩余时间不足时直接进入证据摘要，不再发起新的模型调用。

### 4.4 收口成文阶段

- 工具阶段结束后，强制进入“一次性成文”，不再允许继续调用工具。
- 公司研究类问题默认最多 4 个工具，避免 ReAct 循环继续膨胀上下文。
- 对“深度分析”类问题，优先生成结构化摘要，而不是追求一次覆盖所有细节。

### 4.5 修正前端语义

- 超时降级显示“生成超时，已展示证据摘要”。
- 只有真正的事实校验失败才显示“核对未通过”。
- `timeout` 放在 `degraded_reason`，不要混入 `verify.issues`。

## 5. 上一版实施顺序（已作废）

1. `parser.py` 增加 `source_text`：财务保留 Markdown 表格 + `indicators_params`，新闻/公告保留逐条标题、日期、来源、URL、正文，行情保留 `data.tables` 表格。
2. `evidence_collector._observation()` 改成 `<source_text>` + `<facts>` 双段输出，工具成功时不再跳过原文。
3. 调整 `tool_result_limit` 和 observation 截断策略，避免新闻原文刚好超过 6000 字符被截断。
4. 调整系统提示词和校验规则：`<source_text>` 用于业务理解，`<facts>` 用于数字引用；定性结论必须能在原文找到依据。
5. 增加 `raw_ref` 落盘与完整原始 JSON 审计记录；如确有需要，再加 `ifind_raw_lookup`。
6. 修 `timeout` 的 verify/UI 语义，以及模型调用的 deadline 与重试策略。
7. 用松发股份、安克创新、宁德时代做回归，重点检查业务分析是否有原文依据、数字是否仍可校验。

## 6. 上一版结论（已作废）

Agent 必须看到 iFinD 返回的**业务原文**，否则无法做业务结构、事件含义、机构观点和风险判断。正确的主链路不是“只给 facts”，也不是“把 MCP 原始 JSON 直接塞进去”，而是：

**Agent 看业务原文 + 精简 facts 校验旁路；完整原始 JSON 落盘为 `raw_ref`，用于审计和按需回查。**

本轮先改原文链路，再修超时和前端语义；在用户确认前不改代码。

## 7. 最新方案：原始透传，不解析、不抽取 facts

### 7.1 目标

Agent 看到的 observation 就是 iFinD 返回的数据本身。程序只负责：

- 选择工具、构造 MCP 请求、处理鉴权与传输。
- 原样取出响应内容。
- 加一个最小的 `<tool_observation>` 外壳，标明工具名和调用序号，方便模型知道数据来自哪次调用。
- 记录完整原始响应到数据库/审计日志，便于回查。

程序不再做：

- 不调用 `parse_ifind_response()` 抽取 `sections` / `facts`。
- 不生成 `fact_id`，不做数字归一化、单位换算、同比派生。
- 不把新闻压成 text fact，不截取 `raw_excerpt`。
- 不按业务字段重组财务表格或行情表格。

### 7.2 “透传哪一层”需要明确

iFinD 的返回实际有两层：

```text
JSON-RPC 响应
  └─ result.content[].text
       └─ 业务 JSON 字符串（内部可能还有 data.answer / data.tables / data.data）
```

推荐透传 **`result.content[].text` 原文**，并把多个 content 按原顺序拼接；不解析内部业务 JSON。这样既不做字段抽取，也避免把 `jsonrpc`、`id`、`session` 等传输层字段塞给模型。

如果要求“连 JSON-RPC 外壳也完全不动”，也可以直接序列化完整的 `raw` 响应；代价是模型要自己穿透 `result.content[].text` 的转义层，噪声更大、更容易误读。默认按前者实现，除非明确要求连外壳一起透传。

### 7.3 新的 observation 形态

```text
<tool_observation tool="ifind.stock_financials" status="ok" call="E1-1">
{"code":0,"msg":"success","data":{"answer":"|证券代码|...|","indicators_params":{...}}}
</tool_observation>
```

说明：

- `call="E1-1"` 只是来源级调用编号，不是 fact 编号。
- `<tool_observation>` 外壳是唯一新增内容，目的是让模型区分多次工具调用；不改变内部数据。
- 如果 `result.content[].text` 本身是 Markdown 或纯文本，也原样放入，不转成 facts。

### 7.4 校验与引用怎么处理

原始透传后，当前基于 `[E1-1]` 的 fact 级数字校验无法继续，因为程序不再生成 facts。第一版建议：

- 关闭硬性 fact 校验，`verify.passed` 只表示“有原始响应可读”，不再校验每个数字。
- 引用降级为来源级：模型可写 `[E1]` 表示“来自第 1 次工具调用”，但不强制每个数字都带引用。
- 前端不再显示“核对未通过”，改为显示“原始数据已返回 / 生成超时”等状态。
- 保留原始响应审计，后续如果需要，可以离线补一层 facts 做质检，但不进入主链路。

这会牺牲“数字可自动校验”的能力，换取模型能看到完整业务上下文。这个取舍需要在实现前确认。

### 7.5 上下文预算

当前 `ContextConfig(tool_result_limit=6000)` 会截断工具结果，和“原样透传”冲突。需要：

- 将单工具结果上限提高到至少 32000 字符，或按模型上下文窗口配置。
- 设置本轮总预算，例如 4 次工具调用合计不超过 100000 字符。
- 如果超限，优先减少工具调用次数，而不是截断单次原始响应。
- 模型侧仍要保留 `max_tokens=2048` 的输出限制，避免生成阶段过慢。

注意：原始数据变大后，模型首轮理解和生成可能更慢，所以 7.6 的超时修复仍然必须做。

### 7.6 超时与重试

本次 `核对未通过 · timeout` 的根因不是 parser，而是模型调用和重试耗尽整轮预算。透传后上下文更大，这个问题可能更明显。必须同时修：

- 每次模型调用 timeout 取 `min(120, budget.remaining() - 15)`。
- 模型超时最多重试 1 次；连接错误/5xx 才重试，超时不连续重试 4 次。
- 工具取数完成后给最终成文保留明确时间窗，剩余不足时直接返回原始证据摘要。
- 超时状态放 `degraded_reason`，不要放进 `verify.issues`。

### 7.7 实施顺序

1. `IfindGateway.call()` 成功路径保留 `raw`，新增 `raw_text`（`result.content[].text` 原样拼接），不再调用 parser。
2. `EvidenceCollector` 改为保存原始响应，`_observation()` 只加 `<tool_observation>` 外壳。
3. `public_evidences()` 保存原始响应和调用元数据，不再输出 facts；数据库字段可先复用 `raw_excerpt` 或新增 `raw_text`。
4. `agentscope_tools.py` 直接把原始 observation 返回给 AgentScope。
5. 关闭/降级 fact 校验和前端“核对未通过”语义。
6. 提高工具结果预算，修 deadline/重试。
7. 回归松发股份、安克创新、宁德时代，检查模型是否真正读到财务、新闻、公告、行情原文。

### 7.8 本轮结论

按用户要求，主链路改为：

**iFinD 返回什么，Agent 就看什么；程序不解析、不抽取 facts、不改写。**

需要接受的代价是：fact 级数字校验失效、上下文变大、生成更慢。超时修复和原始响应审计必须一起做。

### 7.9 实施记录（2026-11-18）

已完成第一版原始透传，核心改动：

- `config.py` 新增 `IFIND_RAW_PASSTHROUGH`（默认 `true`）和 `TOOL_RESULT_LIMIT`（默认 `32000`）。
- `ifind_gateway.py` 在 raw 模式下直接提取 `result.content[].text` 并原序拼接，不再调用 `parse_ifind_response()`；空内容视为 `NO_DATA:EMPTY_RAW`。
- `evidence_collector.py` 的 observation 只加 `<tool_observation>` 外壳，内部原样输出 iFinD 文本；`public_evidences()` 保留完整 `raw_text`。
- `context.py` 新增 raw 模式系统提示词，要求模型自行阅读原始 JSON/Markdown，不再要求 fact 级引用。
- `verify.py` / `answer_guard.py` 增加 `mode` 字段；raw 模式跳过数字校验，前端显示“原始数据模式 · 未经程序解析”。
- `persist.py` 将完整原文写入 `evidence.raw_excerpt`，`payload.mode="raw_passthrough"`，`facts=[]`。
- 模型调用超时最多重试 1 次；超时原因只写入 `degraded_reason`，不再写入 `verify.issues`。

回滚方式：`.env` 设置 `IFIND_RAW_PASSTHROUGH=false` 即恢复 parser/facts 路径。

验证：单元测试 `43 passed`；真实 iFinD 联网回归待在网页端执行（松发股份、安克创新、宁德时代）。
