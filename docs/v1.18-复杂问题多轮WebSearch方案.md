# v1.18 复杂问题多轮 Web Search：提示词 + 并发标记

> 创建：2026-11-25
> 关联：`app/agent/context.py`、`app/tools/agentscope_tools.py`、`app/tools/web_search.py`

## 一、结论

复杂问题检索不足，不是"次数配额"问题，也不是缺一个检索规划器，而是两件事同时成立：

1. **提示词把 web 定义成补充渠道**，模型按指令办事，自然不会多做检索；
2. **工具被标记为不可并发**，即使模型在一条回复里给出多条 `web_search`，框架也逐条串行执行。

本次只改这两处：提示词改成"按子问题拆查询、一条回复里一次发出多条"，工具标记改成"web 可并发"，再给上游加 4 路并发闸门。不新增意图识别模型、不新增检索规划器、不改 SSE、不改四段结构、不改 iFinD 透传。

## 二、现状诊断（全部来自库内实测）

### 2.1 提示词确实在压制检索（德业股份那轮）

问题：`估值德业股份的成本结构、近三年及未来两年毛利率走势，说明原因，对自给率做敏感性`

该轮 6 次工具调用：

| step | 工具 | 状态 | 耗时 |
|---|---|---|---|
| 1 | web.search（预检索） | network_blocked | 5671ms |
| 2 | ifind.stock_financials | ok | 875ms |
| 3 | ifind.stock_summary | ok | 452ms |
| 4 | ifind.news_search | upstream_error | 422ms |
| 5 | ifind.notice_search | ok | 485ms |
| 6 | web.search（补搜） | ok | 5766ms |

5 个子问题，只成功检索 1 次、拿回 5 条摘要。旧提示词写着"web_search 只补新闻、政策、行业动态"和"不要用 web_search 查行情、财报、股东、宏观"——模型没有偷懒，它在严格执行。

### 2.2 模型本来就会在一条回复里给多条 tool_call

`ToolCallStartEvent` 在模型流式输出阶段发出，因此两个相邻的 `tool_start` 时间戳就代表"模型在同一条回复里给了两个调用"：

```
21:49:42.555  tool_start  web.search  call_00_hv2wp33oic5cwmg6omau3ynk
21:49:43.032  tool_start  web.search  call_01_vvyl81agl7gkj440nfc7qsjv
21:49:59.915  tool_end    web.search  latency 14983ms
21:50:25.026  tool_end    web.search  latency 25109ms
```

第二个调用在第一个开始后 0.5 秒就发出了，所以"多发"这一侧不需要改造；需要改的是执行侧。

### 2.3 但执行是串行的

对库里 297 次真实 `web.search`（`parent_id is null`）做事件回放，统计"3 秒内连续 start"的批次：

| 指标 | 值 |
|---|---|
| 多调用批次 | 87 组，共 174 次检索 |
| 平均批次大小 | 2.00 |
| 单次平均耗时 | 3.6s |
| 串行总耗时（latency 之和） | 623.9s |
| 批次实际跨度（首个 start → 末个 end） | 698.1s |
| 跨度 − latency 之和 | **+852ms**（跨度大于耗时之和 = 串行签名） |
| 若并发（每批取 max） | 372.8s，**节省 251.1s / 40%** |

这也解释了瑞芯微对比那轮为什么跑满 200 秒：28 次检索、18 次模型调用，每一次检索都要等上一轮返回才能继续。

## 三、改动

### 3.1 工具并发标记（`app/tools/agentscope_tools.py`）

```python
self.is_concurrency_safe = spec.provider == "web"
```

只有 web 工具可并发，iFinD 保持串行，理由：

- 瓶颈在 web（单次 3.6s，历史最长 25s 超时），iFinD 单次多在 1s 内，并发收益小；
- iFinD 有上游频控，串行更稳；
- 混批 `[ifind, web, web]` 会被 AgentScope 拆成"串行批 + 并发批"，符合预期。

### 3.2 提示词（`app/agent/context.py`）

`AGENT_TOOL_RULES` 删除两条限制，新增：

```
- 结构化数字（行情、财报、股东、事件、宏观、指数）以 iFinD 为准；公开解读、行业供需、政策、供应链、竞品动态、机构观点和背景原因用 web_search，两者可以交叉验证。
- 复杂问题（多标的对比、竞争格局、产业链、敏感性、多因素归因）要做深度检索：先把问题拆成若干独立子问题，每个子问题写一条具体查询（带公司名/产品/时间/口径），在同一个回复里一次性发出多条 web_search，不要一条一条来回问。
- 同一条回复里可以给出多条工具调用，系统会并发执行；需要多个数据面时一次性都发出来，不要为了等某一条结果而逐条发起。
- 每条查询只指向一个事实面，不要用近义措辞重复同一问法；同一事实面拿到 2 个独立来源即可停止，不要为同一面继续加搜。
- 单轮深度检索上限 15 条；接近上限时先补最薄弱的子问题，仍未取到的写"未取到"。
- 单次 web_search 返回约 5-6 条摘要，每条最多 1200 字，是片段不是全文；需要更细的原文时换更具体的查询。
```

同步调整三处措辞，避免和上面的规则自相矛盾：

| 位置 | 旧 | 新 |
|---|---|---|
| `SYSTEM_PROMPT` 第 26 条 | web "只补新闻、政策…" | web 用于公开信息，结构化数字以 iFinD 为准 |
| `RAW_SYSTEM_PROMPT` 第 13 条 | "不得改用 web 数字" | 结构化数字以 iFinD 为准，冲突时说明差异 |
| 预检索说明 | "优先使用它，不足时再补充" | "它是起点不是全部：复杂问题按需拆成多条子查询并发补搜" |

上限为什么写 15：瑞芯微那轮模型自发搜了 28 条，第 23 条才出现 80% 的唯一 URL，后 5 条几乎全是重复措辞；库内另有两轮近重复 query 占比 47% / 29%。15 条足够覆盖一个 5 子问题的对比研究，又不会把时间耗在边际收益为零的检索上。

### 3.3 上游并发闸门（`app/tools/web_search.py`）

```python
MAX_INFLIGHT_REQUESTS = 4
_inflight = threading.BoundedSemaphore(MAX_INFLIGHT_REQUESTS)
```

`AuditedTool.call` 用 `asyncio.to_thread` 执行同步 HTTP，10 条并发就是 10 个线程同时打 Tavily，很容易撞 429。闸门只包住 `client.post` 本身，429/5xx 的既有重试逻辑保持原位；等不到槽位按 `RATE_LIMITED` 返回，不阻塞整轮。

## 四、并发安全性

| 共享状态 | 结论 | 依据 |
|---|---|---|
| `EvidenceCollector.records` / `_fact_seq` | 安全 | `add_outcome` 整体在 `await` 之后同步执行，事件循环单线程内不会穿插，`seq` 严格唯一（测试覆盖 4 路并发 → 1..4） |
| `Budget.take_tool()` | 安全 | 同步自增，调用点与 await 之间无线程切换 |
| `HybridCache` | 安全 | `TTLCache` 带 `threading.Lock`，redis 客户端线程安全 |
| `httpx.Client` | 安全 | 每次请求新建，不共享连接池 |
| 参数去重 | 保留 | `collector.lookup` 命中直接复用 observation，不重复扣预算（测试覆盖） |

副作用：同一批并发检索的 `seq` 顺序取决于完成时间，引用编号顺序会变。编号与证据一一对应，不影响引用正确性，历史消息的编号也不受影响。

## 五、成本与兜底

| 项 | 值 |
|---|---|
| 单轮 web.search 软上限 | 15 条（提示词约束） |
| 上游并发 | 4 路 |
| 单次返回 | ≤6 条摘要 × ≤1200 字，单次 raw_text 中位 8.0K 字符 |
| 最坏网络时间 | 15 条 ÷ 4 路 ≈ 4 波 × 3.6s ≈ 15s |
| 硬兜底 | `max_iters=50`、`TASK_TIMEOUT_SECONDS=300` 不变 |

15 条检索 ≈ 90 条摘要 ≈ 12 万字符原始文本（按单次 raw_text 中位 8.0K 计），不会一次性塞进提示词：`evidence_text` 的 fact 上限、AgentScope 的上下文压缩继续生效，模型看到的仍是按需读取的 observation。

## 七、未做与风险

- 不做意图识别模型 / 检索规划器：先验证"提示词 + 并发"这两个最小改动能否让模型自己拆问题；不够再上 B 方案。
- 不做结果过滤 / 全文抓取：Tavily 返回的就是 ≤1200 字片段，单次 raw_text 中位 8K 字符，当前上下文能承受。
- 15 条是软约束，模型可能超发；真正的硬边界仍是 300s 与 50 次迭代。
- 4 路闸门在极端情况下会让部分检索排队 ~十几秒，排队超 30s 直接返回 `RATE_LIMITED`，由模型按"未取到"处理。
