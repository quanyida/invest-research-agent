# v1.9 C 路线：持久化 Run 队列 + SSE 回放

## 目标

不整体重构为 AgentScope 官方 App，在现有工程内补齐三件事：

1. 同一会话的 run 串行化；
2. durable run queue：`POST /chat` 只入队，后台 worker 执行；
3. SSE 事件落库与 cursor 回放，浏览器断线后可续传。

核心原则：**HTTP 连接不再拥有 Agent 任务的生命周期**。客户端断开只停止读取，不取消执行。

## 请求生命周期

### 1. 入队

`POST /api/v1/chat`：

- 保留 Origin 校验、登录校验、分钟级限流、日额度、`client_request_id` 幂等检查；
- 在同一个数据库事务内写入：
  - `conversations`（新会话时）；
  - 用户消息，`status=done`；
  - 助手消息，`status=queued`；
  - `chat_runs`，`status=queued`；
- 同会话已有 `queued/running` 时，`chat_runs_one_active` 唯一索引直接拒绝，接口返回：
  - HTTP 409
  - `{"code":"CONVERSATION_BUSY","message":"该会话上一条回答仍在生成，请稍候再问"}`
- 入队成功后立刻返回 SSE，先发一条 `meta`（带 `conversation_id/message_id/request_id/turn`），再轮询 `session_events`。

### 2. 执行

`RunWorker` 在 FastAPI lifespan 中启停：

- `claim()` 使用 `FOR UPDATE SKIP LOCKED` 跨进程抢任务；
- 抢到后写 `worker_id/started_at/lease_until`，`attempt+1`；
- `load_chat_run()` 从数据库还原：
  - 本轮用户消息；
  - 排除本 `request_id` 的历史；
  - 重新计算 `turn`；
  - 助手消息切到 `running`；
- 调 `AgentScopeRunner`（或 legacy `AgentLoop`），每个事件写入 `session_events`；
- 收到 `done` 后 `chat_runs.status=done`。

### 3. 回放

`GET /api/v1/messages/{message_id}/events?after=<event_id>`：

- 支持 `Last-Event-ID` 请求头，取两者较大值；
- 先回放 cursor 之后的 `session_events`，再继续轮询；
- 每个 SSE 帧带 `id: <event_id>`，客户端据此续传；
- 已到终态但没有 `done` 事件时（例如 worker 租约过期），补发 `error` + `done`，避免客户端永久挂起。

前端 `static/assets/app.js` 已接入：

- 记录最后收到的 `event_id`；
- 流异常结束或尾超时后，自动请求 `/messages/{id}/events?after=...`；
- 连续恢复失败才把消息标记为失败。

## 数据模型

`infra/sql/006_run_queue.sql`：

### chat_runs

内部队列表，不含用户内容，**不启用 RLS**；所有查询显式带 `tenant_id`。

关键字段：

- `status`：`queued/running/done/failed/cancelled`
- `attempt`：已领取次数
- `worker_id`、`lease_until`
- `error_code`、`error_message`
- `created_at/started_at/finished_at`

关键索引：

```sql
create unique index chat_runs_one_active
  on chat_runs (conversation_id)
  where status in ('queued', 'running');
```

同会话串行由结构保证，不依赖应用层“先查再写”。

### session_events

事件日志，启用 RLS：

- `id bigserial` 作为 cursor；
- `message_id + id` 索引；
- 读写都走 `tenant_scope`，策略按 `tenant_id + user_id` 隔离。

## 失败与恢复

### Worker 崩溃

- `sweep()` 每轮回收 `lease_until < now()` 的 running 任务；
- 未超过 `RUN_MAX_ATTEMPTS`：回到 `queued`；
- 超过：置 `failed`，并把助手消息标记失败；
- 重试时 worker 会在 `meta` 里带 `attempt`；前端收到 `attempt > 1` 会清空半截答案再重建，避免新旧 `delta` 拼接。

### 事件流超时

- 单条 SSE 连接最长跟随 `EVENT_TAIL_TIMEOUT_SECONDS`；
- 超时只结束当前连接，任务继续；
- 客户端用 cursor 重连后继续收事件。

### 客户端断开

- `_stream_events` 捕获 `CancelledError` 后直接退出；
- 不再调用“把消息标记为 cancelled”的逻辑；
- 任务由 worker 持有，继续执行到终态。

## 配置

## 已知边界

1. `session_events` 目前只增不删，后续需要按天分区或 TTL 清理；
2. 单进程默认一个 worker；多实例可直接共享 PostgreSQL，靠 `SKIP LOCKED` 协作；
3. `POST /chat` 的即时 `meta` 与 worker 的 `meta` 各一条，前端按幂等处理；
4. 队列没有“排队位置”事件，客户端只能看到 `meta` 后等待；
5. 尚未做 run 取消接口（当前断线不等于取消）。
