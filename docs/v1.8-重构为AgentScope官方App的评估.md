# v1.8 全量重构为 AgentScope 官方 app 的评估

- 日期：2026-11-18
- 核对版本：AgentScope `v2.0.12`（commit `28ab5ef6`）
- 核对方式：`git show v2.0.12:<path>` 只读，未切分支、未改源码
- 结论：**不建议全量重构。建议借架构，不借代码。**

---

## 一、结论先行

官方 app 是一套成熟的「Agent 服务骨架」，但它解决的是**单租户、多用户**的问题，不是多租户。

它把租户隔离明确留给宿主：

- `get_current_user_id` 只读 `X-User-ID` 请求头，源码注释写明 "Temporary header-based identity; will be replaced by JWT auth"。
- `StorageBase` 全部方法按 `user_id: str` 分区，没有 `tenant_id`。
- `extra_agent_middlewares` / `extra_agent_tools` 的文档里，"tenant isolation" 被列为调用方责任。
- 跨 owner 访问只有 `ResourceAccessPolicyBase` 一个钩子，默认全拒绝，管的是 user 之间，不是 tenant 之间。

所以「全部重构成官方 app 来实现多租户」这句话，实际工作量是：**先 fork 官方 app，再自己补一层租户**。这不是"用官方能力"，而是"接管官方代码"。

---

## 二、官方 app 确实提供了什么

入口是 `create_app(...)`，三个必填依赖：

- `storage: StorageBase`：会话、消息、AgentState、credential、MCP、Skill、team、schedule、知识库
- `message_bus: MessageBus`：跨进程队列、replay log、pub/sub、分布式锁
- `workspace_manager: WorkspaceManagerBase`：每会话一个工作区，提供 Bash/Read/Write 等内置工具

已经实现、且我们目前缺的能力：

1. **会话串行化**：同一 session 同一时刻只有一个 run，靠分布式 session lock。
2. **durable trigger queue**：`POST /chat` 只入队，`WakeupDispatcher` 统一拉起，实例重启不丢触发。
3. **SSE replay**：事件先写 replay log 再广播，客户端带 cursor 重连可回放。
4. **HITL**：`AWAITING_PERMISSION` / `AWAITING_EXTERNAL_RESULT` 由持久化 AgentState 推导。
5. **team / subagent / SOP / schedule / knowledge base / channel（飞书、钉钉、Discord）/ realtime voice**。

扩展点也很完整：

- `extra_middlewares`：ASGI 中间件，可塞认证。
- `extra_agent_middlewares`：每次装配 Agent 时按 `(user_id, agent_id, session_id, workspace)` 生成中间件。
- `extra_agent_tools`：每次装配时按 `(user_id, agent_id, session_id)` 生成工具。
- `custom_agent_cls`、`resource_access_policy`、`extra_credentials`。

这些钩子够用，但都停在 user 粒度。

## 三、多租户缺口清单

| 能力 | 官方现状 | 缺口 |
|---|---|---|
| 租户身份 | 只有 `user_id` | 需要 tenant → user 映射，或把 tenant 编码进 user_id |
| 行级隔离 | 按 `user_id` 分区 | 没有 `tenant_id` 列，现有 RLS 策略无法直接复用 |
| 认证 | `X-User-ID` 头 | 没有 JWT / Cookie / CSRF，直连即越权，必须前置网关 |
| 配额 | 只有会话输入队列长度 | 没有日提问数、工具调用数、token 配额 |
| 审计 | 只有 `messages` | 没有 `evidence` / `tool_calls` / `llm_calls` / `usage_daily` |
| 存储表名 | `sessions` / `messages` / `agents` / `teams` | 与现有 PG 表**同名不同构**，同库启动即冲突 |
| workspace | 必填依赖 | `LocalWorkspaceManager` 是节点本地盘，多实例必须换 K8s / Daytona / E2B 或自建共享存储 |
| MessageBus | 必填依赖 | `InMemoryMessageBus` 只能单机，多实例必须 Redis |
| 模型配置 | 挂在 `SessionRecord.config.chat_model_config` 上 | 与现有 agent 级配置模型不同，需迁移 |
| HTTP 契约 | `queued` / `started` + `/session/{id}/events` | 与现有 `meta/plan/verify/delta/usage/done` 不同，前端要重写 |
| 工具面 | 默认带 Bash / Read / Write / Grep | 投研 C 端不能暴露文件系统工具，需白名单裁剪 |

结论：官方 app 的多租户改造量，约等于把现有后端重写一遍，再额外背一套上游代码的同步成本。

## 四、三条路线对比

### 路线 A：旁路部署（官方 app 独立服务 + 我们做 BFF）

- 官方 app 独立进程、独立 schema/DB，前面挂我们的认证中间件。
- `X-User-ID` 传 `{tenant_id}:{user_id}`。
- 我们的 `/api/v1/chat` 变成适配器：转发到官方 `/chat`，订阅 `/session/{id}/events`，映射成现有四段式 SSE。
- 领域审计通过 `extra_agent_middlewares` 回写我们自己的表。
- 工作量：约 1.5–2 周。
- 风险：中。两套会话/消息数据，需要一致性对账；workspace 仍要解决；工具面要裁剪。
- 适合：想快速拿到 HITL、schedule、team、知识库，且能接受双栈运维。

### 路线 B：全量替换（fork 官方 app + 加租户层）

- 给 `StorageBase` 全部方法加 `tenant_id`，或改用 RLS 策略。
- 给 `MessageBusKeys` 全部 key 加租户前缀，给锁加租户维度。
- 替换认证为现有 Cookie Session + CSRF。
- 移植 `evidence` / `tool_calls` / `llm_calls` / `usage_daily` / `verify` / `answer_guard` / 四段式契约。
- 重写前端。
- 工作量：约 4–6 周（单人），之后每次上游升级都要 rebase。
- 风险：高。上游 `app` 层迭代很快（v2.0.x 仍在变），fork 即锁定。
- 适合：确定要把 AgentScope app 当成长期产品底座，且有专人跟上游。

### 路线 C：借架构，不借代码（推荐）

保留现有 FastAPI、PG schema、前端契约，只把官方 app 的三条核心机制补进来：

1. 会话串行化：PG advisory lock 或 `select ... for update` 锁 conversation 行。
2. durable trigger queue：PG `SKIP LOCKED` 任务表 + 独立 worker，`POST /chat` 只入队返回。
3. SSE replay：`events` 表 + `after` cursor，断线可续。

工具层保持现状，但按官方的分层方式装配：内置 / iFinD MCP / iFinD Skill / 用户自定义。

- 工作量：约 3–5 天。
- 风险：低。不新增技术栈，不动现有表结构。
- 收益：拿到官方 app 80% 的工程价值（串行、可恢复、可扩展），不承担 fork 成本。
- 代价：team / SOP / scheduler / 知识库 / 语音这些能力要自己按需补，不能白拿。

## 五、推荐路线 C 的多租户落地

### 5.1 租户边界

现有 `tenants` / `users` / RLS 已经是对的，保留：

- 每条业务行带 `tenant_id` + `user_id`。
- 连接级 `set_config('app.tenant_id', ...)`，由 `tenant_scope` 统一设置。
- 所有跨表查询走 `tenant_scope`，不允许裸 `SessionLocal`。

需要补的一条：**后台任务也必须带租户上下文**。worker 从任务表取到 `(tenant_id, user_id, conversation_id)` 后，必须重新进入 `tenant_scope` 才能查库，不能复用请求线程的上下文。

### 5.2 会话串行化

```sql
select id from conversations
where id = :conversation_id
for update;
```

或

```sql
select pg_try_advisory_xact_lock(hashtextextended(:conversation_id, 0));
```

拿不到锁直接返回 `409 CONVERSATION_BUSY`，前端提示"上一条还在生成"。

这一条解决的是：同一会话并发双跑、AgentState 乐观锁静默失败、工具重复计费。

### 5.3 durable queue

新增 `chat_runs` 表：

- `id`, `tenant_id`, `user_id`, `conversation_id`, `message_id`
- `status`：`queued` / `running` / `done` / `failed` / `cancelled`
- `attempt`, `lease_until`, `created_at`, `started_at`, `finished_at`
- `error_code`, `error_message`

worker 用 `select ... for update skip locked` 取任务，带租约续期；实例崩溃后租约过期自动重取。

启动时补一条回收：

```sql
update messages set status = 'interrupted'
where status = 'running' and created_at < now() - interval '10 minutes';
```

### 5.4 SSE replay

新增 `session_events` 表：

- `id`（单调递增或 ULID）、`tenant_id`、`conversation_id`、`message_id`
- `event`, `data`（JSONB）、`created_at`

每次 `yield` 前先写库，再推给客户端。客户端重连带 `after=<last_event_id>`，服务端先回放再订阅。

v1 可以先只做"写库 + 重连回放"，不做多实例广播；单实例够用。多实例时再加 PG `LISTEN/NOTIFY` 或 Redis pub/sub。

### 5.5 工具分层

保持现有 `ToolBase`，但装配顺序对齐官方：

1. 内置工具（本轮业务必需，例如公司检索、财报口径）
2. iFinD MCP 工具
3. iFinD Skill
4. 用户自定义（v1 不做）

每层独立开关，重名 fail closed，不做静默覆盖。

## 六、如果坚持路线 B：分期与验收

### Phase 0：影子验证（约 1 周）

- 独立 DB/schema 起官方 app，只接一个测试租户。
- 验证：session 串行、断线重连、HITL、工具白名单。
- 验收：同一 session 并发 10 个请求，只有 1 个执行，其余排队；杀进程后任务能恢复。

### Phase 1：租户层（约 1–1.5 周）

- `tenant_id` → `user_id` 编码方案落地（建议 `t{tenant_uuid}:u{user_uuid}`）。
- 认证中间件把 Cookie Session 转成 `X-User-ID`。
- workspace manager 按租户分目录，或直接换 K8s/Daytona。
- 验收：租户 A 的用户无法通过任何 API 读到租户 B 的 session/agent/credential。

### Phase 2：领域迁移（约 1–2 周）

- `extra_agent_tools` 注入 iFinD 工具。
- `extra_agent_middlewares` 回写 `evidence` / `tool_calls` / `llm_calls` / `usage_daily`。
- 四段式答案校验、超时兜底、digest 降级，改造成 middleware 或 `custom_agent_cls`。
- 验收：同一问题在旧栈和新栈的 evidence 条数、引用编号、四段结构一致。

### Phase 3：灰度（约 1 周）

- BFF 双写/对比，按租户灰度。
- 验收：连续 3 天无一致性差异，再切主流量。

### 路线 B 的硬门槛

- 上游 `app` 层仍在快速迭代，fork 后每次升级都要 rebase。
- 官方表名与现有表冲突，必须独立库或独立 schema，跨库 join 只能应用层做。
- 官方默认工具面包含 Bash/Read/Write，C 端必须裁剪，否则是文件系统逃逸风险。
- 官方没有认证，直连即越权，必须前置网关。

## 七、风险清单

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 上游 rebase 成本 | 路线 B | 锁定 tag，diff 驱动升级，不跟 main |
| 表名冲突 | 同库启动官方 storage | 独立 schema `agentscope` 或独立 DB |
| 认证绕过 | 官方 app 直接暴露 | 只监听内网，前置 BFF |
| workspace 逃逸 | 默认工具面 | 工具白名单，禁用 Bash/Write |
| 连接池翻倍 | 同步 psycopg + 异步 asyncpg 并存 | 按实例数重算 `max_connections` |
| 双写不一致 | 路线 A | 以旧表为准，官方表只做运行态；定期对账 |
| 租户串数据 | 后台任务丢失上下文 | worker 强制 `tenant_scope`，RLS 兜底 |
