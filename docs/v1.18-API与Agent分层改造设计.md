# API / Agent 分层改造设计

> 日期：2026-11-25
> 状态：待评审
> 目标：拆分 API 层与 Agent Service 层，新增同步聊天与深度研究双路径

---

## 一、要解决的问题

### 1.1 现状

```
FastAPI 进程（:8000）
├─ /api/v1/chat          入队 → SSE 回放
├─ /api/v1/conversations 会话 CRUD
├─ /api/v1/auth          注册登录
└─ RunWorker             ← 同一个进程、同一个事件循环
```

**所有提问都走同一条重链路**：

```
入队 → Worker 轮询抢占 → ReAct 执行 → 落库 → 假流式回放（40 字/块）
```

### 1.2 三个具体问题

| #   | 问题                 | 表现                                  |
| --- | ------------------ | ----------------------------------- |
| 1   | **API 与 Agent 耦合** | Worker 的慢查询会拖累 API；无法独立扩缩容          |
| 2   | **没有同步路径**         | 「宁德时代毛利率多少」这种 5 秒能答的问题，也要走完整队列 + 回放 |
| 3   | **无法区分任务长度**       | 简单问答与深度研究共用同一个超时和优先级                |

### 1.3 目标

| 目标 | 衡量 |
|---|---|
| 分层清晰 | API 层不再 import AgentScope |
| 同步聊天真流式 | 用户看到逐字输出，不是 40 字一块 |
| 深度研究可离开页面 | 关掉浏览器再回来，进度还在 |
| 独立扩缩容 | Worker 与 API 分别加副本 |

### 2.2 职责边界（硬约束）

| 能力 | API 层 | Agent Service |
|---|---|---|

## 三、两条执行路径

### 3.1 路径对比

| 维度                 | `/chat`（同步）        | `/research`（异步）                  |
| ------------------ | ------------------ | -------------------------------- |
| 触发                 | 用户点发送              | 用户点「深度研究」                        |
| API 行为             | 转发给 Agent Service  | 写 `chat_runs`（`status='queued'`） |
| 执行者                | Agent Service（立即）  | Agent Service（队列消费）              |
| 响应                 | **真 SSE**，逐字推送     | 返回 `run_id`，前端连回放流               |
| 用户可否离开             | 否（但断连后 Agent 继续跑完） | ✅ 可以                             |
| 写 `session_events` | ⚠️ 待定（见 6.2）       | ✅ 必须                             |
| 超时                 | 60 秒               | 300 秒                            |
| 优先级                | `priority=10`（高）   | `priority=100`                   |

### 3.2 前端契约

```typescript
interface ChatBody {
  conversation_id?: string;
  message: string;
  mode: "chat" | "research";   // ← 新增，前端显式指定
  client_request_id?: string;
}
```

**前端两个入口**：

- 主输入框 → `mode: "chat"`
- 「深度研究」按钮 → `mode: "research"`

**不自动判定**：判错代价高（简单问题排 5 分钟队，或深度问题被 60 秒截断）。

### 3.3 `/chat` 的 SSE 契约

```http
POST /api/v1/chat
Content-Type: application/json

{"conversation_id": "...", "message": "...", "mode": "chat"}
```

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no

id: 1
event: meta
data: {"message_id":"...","mode":"chat","turn":3}

id: 2
event: tool_start
data: {"tool":"ifind.stock_financials"}

id: 3

data: {"text":"宁德时代"}

...

id: 42

```

**注意没有 `X-Run-Id`** —— 因为 `/chat` 不写 `chat_runs`（见 6.1），且刷新后不连流回放（见 6.2/6.3）。前端只靠 `messages.status` 判断。

### 3.4 `/research` 的契约

```http
POST /api/v1/research
{"conversation_id":"...","message":"...","mode":"research"}
```

```json
{"run_id":"7a3f...","message_id":"...","stream_url":"/api/v1/research/7a3f.../stream"}
```

**回放**：

```http
GET /api/v1/research/{run_id}/stream?after=42
```

## 四、SSE 转发实现（关键）

### 4.1 必须照 BISHENG 的三点做

`app-proxy/sse.py` 的 `authorized_events` 提供三个我原本会漏的实现：

```python
async def proxy_chat(request, body):
    async with client.stream("POST", AGENT_URL, json=...) as upstream:
        iterator = upstream.aiter_raw().__aiter__()
        pending = None
        try:
            while True:
                if pending is None:
                    pending = asyncio.create_task(anext(iterator))
                # ① asyncio.wait + timeout：上游卡住时能中断
                done, _ = await asyncio.wait({pending}, timeout=REAUTH_INTERVAL)
                if pending in done:
                    try:
                        chunk = pending.result()
                    except StopAsyncIteration:
                        break
                    pending = None
                    yield chunk
        finally:
            # ② finally 里必须关上游，否则连接泄漏
            if pending is not None:
                pending.cancel()
                await asyncio.gather(pending, return_exceptions=True)
            await upstream.aclose()
```

| # | 要点 | 不做的后果 |
|---|---|---|
| 1 | `asyncio.wait` + timeout | 上游卡住时永久阻塞，无法中途处理 |
| 2 | `finally` 里 `aclose()` | 上游连接泄漏 |
| 3 | 流式期间重新鉴权 | 长连接期间权限变更不生效 |

### 4.2 第 3 点本项目的选择

**不做流式重新鉴权。**

理由：本项目没有「踢出团队」场景，权限在会话期间不变。

**代价**：如果将来加了团队协作，需要在 `REAUTH_INTERVAL`（如 60 秒）后断开流。

### 4.3 断连策略

**前端断开时，API 不取消到 Agent Service 的请求。**

```python
except asyncio.CancelledError:
    # 只断自己这一端；上游继续跑完并落库
    logger.info("client disconnected; agent keeps running to completion")
    raise
```

**理由**：

| 对比 | 硬中断 | 不中断（采用） |
|---|---|---|
| 算力 | 省一半（但前面白烧） | 跑完 |
| 数据 | 答案不完整 | 答案完整 |
| 用户体验 | 刷新后无内容 | 刷新后可见 |

**同步聊天只有 5-15 秒**，用户在这个窗口内刷新的概率低；跑完落库对用户更有利。

### 4.4 超时

| 路径 | 超时 | 由谁控制 |
|---|---|---|
| `/chat` 同步 | **60 秒** | Agent Service 内部 `asyncio.timeout` |
| `/research` 异步 | **300 秒** | 队列的 `TASK_TIMEOUT_SECONDS` |

**API 层不设超时** —— 它不知道 Agent 要跑多久；`httpx` 的 `timeout=None`，由 Agent Service 主动结束。

**60 秒超时后**：返回 `degraded` 答案 + 提示「问题较复杂，建议使用深度研究」。

## 五、数据模型变更

### 5.1 `conversations` 加两个摘要字段

```sql
alter table conversations
  add column if not exists last_message_preview text,
  add column if not exists message_count int not null default 0;
```

| 字段 | 用途 | 借鉴自 |
|---|---|---|
| `last_message_preview` | 会话列表显示最后一条，**不用 join messages** | chat-demo 的 `sessionSummaries` |
| `message_count` | 列表显示消息数 | 同上 |

**为什么冗余**：50 个会话 × 100 条消息，列表页 join 全量会让查询变慢。

**注意**：不加 `active_run_id` —— 因为 `/chat` 不写 `chat_runs`（见 6.1），没有 run_id 可返回；且刷新后不连流（见 6.3）。

### 5.2 `messages` 加 `updated_at`

```sql
alter table messages
  add column if not exists updated_at timestamptz not null default now();

create index if not exists messages_orphan_idx
  on messages (status, updated_at)
  where status = 'running';
```

**用途**：

1. **孤儿检测**（见 6.4）—— 判断「running 多久没更新」
2. 消息状态变化的时间戳，排查必需

**现状**：`messages` 只有 `created_at`，状态从 `running` 变 `done` 时无法知道何时变的。

**索引只覆盖 `running`**：这是唯一需要按时间扫描的状态，部分索引比全表索引小两个数量级。

### 5.3 `session_events` 加清理标记

```sql
alter table session_events
  add column if not exists expires_at timestamptz;
```

**当前问题**：`session_events` 只增不删（待办 P3）。

**清理策略**：

```
任务终态（done/degraded/failed/cancelled）时
  → 设置 expires_at = now() + interval '24 hours'

定期任务
  → delete from session_events where expires_at < now()
```

**为什么保留 24 小时**：

- 用户当天刷新还能看到执行过程
- 第二天清理，存储不无限增长
- 按 10k DAU × 5 次 × 30 事件 × 24 小时留存 ≈ **36 万行**（而非无限增长）

### 5.4 `chat_runs` 不加 `mode`

**原因**：`/chat` 不写 `chat_runs`（见 6.1），所以这张表只服务队列任务，**无需区分模式**。

**推论**：现有 `sweep()` 逻辑完全不变 —— 它只处理 `chat_runs`，而那张表现在只有 research 任务。

## 六、已定的四个决策

> 决策依据来自对 BISHENG 源码的实测：
> `common/chat/manager.py`（消息落库条件）、`worker/workflow/redis_callback.py`（超时判定）。

### 6.1 `/chat` 不写 `chat_runs`

**BISHENG 没有独立任务表** —— `message_session` 就是会话，没有「任务」概念，因为同步执行不需要队列。

本项目采用同样语义：

| 路径 | 是否写 `chat_runs` |
|---|---|
| `/chat`（同步） | ❌ **不写** |
| `/research`（异步） | ✅ 写 |

**推论**：`chat_runs` 只服务队列，**因此不需要 `mode` 字段**（见 5.3）。

### 6.2 `/chat` 不写 `session_events`

**BISHENG 的代码证据**（`common/chat/manager.py`）：

```python
if chat_id and (message.message or message.intermediate_steps or message.files) \
        and message.type != "stream":
    #                    ↑ 中间步骤永远不落库
    session.add(db_message)
```

**工具输入/输出（`type="stream"`）只推 WebSocket，不写数据库。**

本项目对应语义：

| 数据 | 去向 |
|---|---|
| 工具调用、delta 块（过程） | 只推 SSE，**不写事件表** |
| 最终答案（结果） | ✅ 写 `messages` |

**代价**：`/chat` 刷新后**无法回放执行过程**，只能查 `messages` 看结果。

**收益**：事件表不因同步聊天膨胀。按 10k DAU × 5 次/天 × 30 事件估算，**每天少写 150 万行**。

### 6.3 前端靠 `messages.status` 判断，不加 `active_run_id`

**BISHENG 用 `message_session.status`**（`Running` / `completed` / `Stoped`）。

本项目已有 `messages.status`，直接复用：

```
GET /conversations/{id}/messages
  ↓
[{ id, role, content, status, ... }]
  ↓
status === 'running'         → 显示「正在生成…」，轮询等待
status === 'done'|'degraded' → 正常展示
status === 'failed'          → 显示错误 + 重试按钮
```

**为什么不用 `active_run_id`**：

- 6.1 决定 `/chat` 不写 `chat_runs`，**没有 run_id 可返回**
- 6.2 决定刷新后不连流，**有 run_id 也没用**

**代价**：用户看不到「正在执行第几步」，只有「正在生成」。

**这符合 BISHENG 的选择** —— 它也不重建中间步骤。

### 6.4 孤儿消息回收：读取时检测 + 后台兜底

**问题**：`/chat` 不写 `chat_runs`，现有 `sweep()` 覆盖不到。

```
Agent Service 崩溃
  ↓
messages 留下 status='running'
  ↓
没有 chat_runs 记录 → sweep 扫不到
  ↓
用户永远看到「正在生成…」
```

**BISHENG 的解法**（`redis_callback.py`）：

```python
if status_info["status"] in [WAITING, INPUT_OVER] and time.time() - status_info["time"] > 10:
    set_workflow_status(FAILED, "workflow task execute busy")
    yield Error("over", WorkFlowTaskBusyError)
elif time.time() - status_info["time"] > 86400:
    yield Error("over", "workflow status not update over 1 day")
```

**关键洞察：它没有后台 sweep，全靠「读取时判断」** —— 因为前端一直连着 WebSocket。

**但本项目前端可能已断开**，所以需要两层。

#### 第一层：读取时检测（学 BISHENG）

位置：`app/api/conversations.py` 的 `read_messages`

```python
ORPHAN_THRESHOLD_SECONDS = 90   # /chat 超时 60s + 30s 缓冲

def _mark_orphan_messages(db, rows: list[Message]) -> None:
    """把超时的 running 消息就地标为 failed。

    只处理没有 chat_runs 的记录：research 任务由 sweep 按租约处理。
    """
    now = datetime.now(timezone.utc)
    for row in rows:
        if row.status != "running":
            continue
        if (now - row.updated_at).total_seconds() <= ORPHAN_THRESHOLD_SECONDS:
            continue
        has_run = db.scalar(
            select(func.count()).select_from(ChatRun).where(ChatRun.message_id == row.id)
        )
        if has_run:
            continue          # research 任务，跳过
        mark_assistant_failed_in_session(
            db, row.id, "failed", "CHAT_ORPHANED", "执行中断，请重试。",
        )
```

**效果**：用户刷新即看到真实状态，不用等后台任务。

#### 第二层：`sweep()` 兜底

位置：`app/agent/run_queue.py`，在主 `sweep()` 之后调用

```python
def sweep_orphan_messages(timeout_seconds: int = 3600) -> int:
    """清理长期孤儿：超过 1 小时仍 running 且无 chat_runs。

    读取时检测覆盖不到「用户再也没回来」的会话，需要这层兜底。
    """
    with session_scope() as db:
        result = db.execute(
            text(
                "update messages set status = 'failed',"
                "       meta = meta || '{\"error_code\": \"CHAT_ORPHANED\"}'::jsonb"
                " where status = 'running'"
                "   and updated_at < now() - make_interval(secs => :timeout)"
                "   and not exists ("
                "       select 1 from chat_runs r where r.message_id = messages.id"
                "   )"
            ),
            {"timeout": timeout_seconds},
        )
        return int(result.rowcount or 0)
```

**关键条件 `not exists chat_runs`**：

| 情况 | 是否处理 |
|---|---|
| 同步聊天孤儿（无 `chat_runs`） | ✅ 标 failed |
| research 任务（有 `chat_runs`） | ❌ 跳过，由现有 `sweep()` 按租约处理 |

#### 两级阈值

| 层 | 阈值 | 理由 |
|---|---|---|
| 读取时检测 | **90 秒** | `/chat` 超时 60 秒 + 30 秒缓冲 |
| 后台兜底 | **1 小时** | 只清「确定不会再回来」的；避免误伤长查询 |

**为什么差这么多**：90 秒是用户体验阈值（快速反馈）；1 小时是数据卫生阈值（防误伤）。BISHENG 用 24 小时，但本项目不需要等那么久。

## 八、验收标准

### 8.1 分层边界

| 检查 | 命令 | 期望 |
|---|---|---|
| API 不依赖 AgentScope | `grep -r "agentscope" app/api/ app/main.py` | 空 |
| Agent Service 不被外部访问 | 端口绑定 `127.0.0.1:8001` | 外部不可达 |

### 8.2 功能

| # | 检查 | 期望 |
|---|---|---|
| 1 | `/chat` 的 SSE 是逐字的 | `delta` 事件 > 20 条（当前假流式是 40 字/块）|
| 2 | `/research` 返回 `run_id` | 存在 |
| 3 | 深度研究关页面后重连 | 不丢事件（`session_events` 回放） |
| 4 | `/chat` 不写 `session_events` | 该 run 在事件表里 0 行 |
| 5 | `/chat` 不写 `chat_runs` | 该消息在 `chat_runs` 里 0 行 |
| 6 | 会话列表有 `last_message_preview` | 非空（有消息时） |
| 7 | `/chat` 刷新后看到 `status='running'` | 不连流，只轮询 |

### 8.3 可靠性

| # | 检查 | 期望 |
|---|---|---|
| 1 | 前端断连后 Agent 继续跑完 | 刷新后 `messages` 有完整答案 |
| 2 | `/chat` 超 60 秒 | 返回 degraded + 建议深度研究 |
| 3 | API 层重启不影响正在跑的任务 | Worker 进程继续 |
| 4 | **杀掉 Agent Service（同步聊天中断）** | **刷新后 90 秒内看到 `status='failed'`** |
| 5 | **孤儿消息 1 小时后被 sweep 清理** | `messages` 里长期 `running` 归零 |
| 6 | research 任务不受孤儿回收影响 | `sweep()` 按租约处理，不被误标 failed |
| 7 | 事件 24 小时后被清理 | `session_events` 行数下降 |

---

## 九、不做的事

| 不做 | 理由 |
|---|---|
| 后端自动判定 `mode` | 判错代价高于用户手动选择的成本 |
| 流式期间重新鉴权 | 本项目无权限变更场景 |
| 跨进程 HTTP 落库 | 破坏事务边界（见 `agentscope-durable` 的论证） |
| 微服务拆到 MCP / RAG 独立服务 | 当前只有 iFinD + Tavily，无自建 MCP |
| 前端状态本地化（IndexedDB） | 需要多设备同步，不能像 chat-demo 那样纯本地 |

---

## 十、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **SSE 双连接** | 前端连 API + API 连 Agent，连接数翻倍 | 监控连接数；必要时用 HTTP/2 多路复用 |
| **代理层缓冲 SSE** | 用户看不到流式 | 显式 `X-Accel-Buffering: no` + Nginx `proxy_buffering off` |
| **孤儿消息残留** | 同步聊天崩溃后 `status='running'` 永久卡住 | 读取时检测（90 秒）+ `sweep_orphan_messages`（1 小时）双层兜底（见 6.4） |
| **事件清理误删** | 用户正在看时被删 | 只删 `expires_at < now()`，且终态后才设 |
| 60 秒超时误判 | 正常问题被截断 | 只对 `mode=chat` 生效；日志记录超时率 |
