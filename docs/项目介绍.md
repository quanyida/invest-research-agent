# 投研 Agent 项目介绍

> 面向 C 端的垂直投研 Agent。多租户、可追溯、原文透传。
> 最后更新：2026-11-23

---

## 一、项目介绍

### 1.1 一句话说明

用户在网页上提问 A 股、港股、美股的投研问题，系统调用同花顺 iFinD 的
17 个结构化数据工具和 Tavily 公开网页搜索，由 ReAct Agent 自主规划取数，
输出自由 Markdown 研报：结构由模型按问题性质组织；历史四段格式仍可兼容渲染。

每个数字后面都跟一个来源标记，点击可定位到原始数据。

### 1.2 解决什么问题

市面上的通用 AI 助手能写投研报告，但有一个共同问题：**你不知道哪句话是编的。**

投研场景对可信度的要求远高于一般问答。一个数字错了，整份分析的结论就可能相反；
一个来源虚构了，用户无法判断该不该采信。

本项目的核心目标不是「答得漂亮」，而是**「答得能查」**：

| 能力 | 实现 |
|---|---|
| 每个数字可追溯 | 引用编号 `[E轮次-序号]` + 来源药丸 |
| 每条证据可回溯 | 点击药丸定位到证据卡片，含原始返回片段 |
| 降级必须可见 | 校验未通过的引用会被移除，并在界面标注 |
| 没数据就说没数据 | 提示词强制要求「宁可写未取到，不要编造」 |

### 1.3 与常见方案的区别

| 维度 | 常见 RAG 方案 | 本项目 |
|---|---|---|
| 数据获取 | 向量检索文档切片 | **结构化工具调用**（不建向量库） |
| 数据加工 | 程序解析、抽取字段、算指标 | **原文直接透传给模型** |
| 答案约束 | 提示词要求 | **校验器逐条核对引用存在性** |
| 失败处理 | 返回错误或空 | **四层降级，最低也给证据摘要** |

### 1.4 规模

| 项 | 数量 |
|---|---|
| 后端 Python | 49 个文件，约 9,950 行 |
| 前端 | 5 个文件，约 2,170 行（原生 JS，零构建） |
| 测试 | 27 个文件，**181 个用例** |
| 数据库 | 12 张表，7 个手写 SQL 迁移 |
| 接入工具 | 17 个 iFinD + 1 个网页搜索 |
| 设计文档 | 17 篇（记录每次架构决策的背景与取舍） |

### 1.5 明确不做的

| 项 | 原因 |
|---|---|
| 研报全文 / 会议纪要 | 版权与授权问题，需商务采购 |
| 文件上传 / PDF 解析 | v1 非目标 |
| 向量检索 / RAG | 结构化数据不需要语义检索 |
| 移动端 / 小程序 | 只做网页端 |

## 二、项目架构

### 2.1 整体结构

```
┌──────────────────────────────────────────────────┐
│  浏览器（原生 JS，SSE 接收）                        │
└────────────────────┬─────────────────────────────┘
                     │ POST /api/v1/chat
                     ↓
┌──────────────────────────────────────────────────┐
│  FastAPI 应用层                                    │
│  鉴权 → 限流 → 日配额 → 入队 → 返回 SSE            │
└────────────────────┬─────────────────────────────┘
                     │ 仅通过 chat_runs 表耦合
                     ↓
┌──────────────────────────────────────────────────┐
│  RunWorker（asyncio task）                        │
│  循环：sweep 扫尾 → claim 抢占 → execute          │
└────────────────────┬─────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────────┐
│  AgentScopeRunner                                 │
│  载入状态 → 预检索 → ReAct 循环 → 校验兜底 → 落库   │
│                    ↓                              │
│              工具层：iFinD MCP / Tavily            │
└────────────────────┬─────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────────┐
│  PostgreSQL（12 张表，业务表启用 RLS）             │
└──────────────────────────────────────────────────┘
```

### 2.2 请求生命周期

一次提问跨越 10 个以上独立事务：

| 阶段 | 动作 | 涉及表 |
|---|---|---|
| 1 | 鉴权 | `sessions` UPDATE |
| 2 | 入队 | `messages` ×2 + `conversations` + `chat_runs` |
| 3 | Worker 抢占 | `chat_runs` UPDATE |
| 4 | 载入上下文 | `messages` UPDATE |
| 5 | 读 Agent 状态 | `conversations` SELECT |
| 6…N | **每条 SSE 事件一个事务** | `session_events` INSERT |
| N+1 | **落库 + 收尾（同一事务）** | 4 张表 INSERT + 3 张表 UPDATE |
| N+2 | done 事件 | `session_events` INSERT |

**为什么不是一个事务**：SSE 需要事件逐条可见（前端要实时看到进展），
而落库必须原子（要么全成功要么全回滚）。两者可靠性要求相反。

### 2.3 两条独立的数据通路

```
ReAct 循环产生的 AgentScope 事件
    ↓ EventBridge 翻译成项目事件
    ↓ 逐条写入 session_events
前端 SSE 按 cursor 增量回放

工具执行时写入内存 EvidenceCollector
    ↓ 循环结束后一次性读取
    ↓ persist_turn 单事务写 4 张表
evidence / tool_calls / llm_calls / usage_daily
```

**两条通路是平行的，不是上下游。**

| 通路 | 完整性 | 用途 |
|---|---|---|
| `session_events` | 裁剪版（原文截 1200 字） | 前端实时展示 |
| `persist_turn` | 完整原文 | 事后审计与追溯 |

### 2.5 并发模型

**三道保护，逐层收紧**：

**第一道：同会话串行（数据库结构保证）**

```sql
create unique index chat_runs_one_active
  on chat_runs (conversation_id)
  where status in ('queued', 'running');
```

同一会话最多一个活跃任务。`enqueue` 冲突时转 409 `CONVERSATION_BUSY`。
**靠索引，不靠应用层判断。**

**第二道：多 Worker 协作（SKIP LOCKED）**

```sql
select id from chat_runs
where status = 'queued' order by created_at
for update skip locked limit 1
```

多个 Worker 可同时抢占不同任务，互不等待。

**第三道：写入者校验（fencing）**

```sql
update chat_runs
   set status = :status, finished_at = now(), lease_until = null
 where id = :id and status = 'running'
   and worker_id = :worker_id and attempt = :attempt
```

**为什么需要第三道**：租约误判时（原 Worker 停顿但没死），
两个 Worker 可能同时落库。证据唯一约束能挡住「都写了证据」的情况，
**但挡不住零证据覆盖**——后提交者如果这轮工具全失败，
会用空证据覆盖前者的正文，造成「正文来自 A、证据来自 B」的错配。

校验不通过时抛异常，**整个落库事务回滚**。

### 2.6 崩溃恢复

| 崩溃点 | 数据状态 | 恢复方式 |
|---|---|---|
| 入队前 | 无任务 | 客户端重试 |
| 抢占后、落库前 | `chat_runs=running`，租约未过期 | 900 秒后 sweep 重排 |
| 落库事务中 | PostgreSQL 回滚 | 同上，不产生半截数据 |
| 落库提交后 | 业务数据与任务终态已同事务提交 | 无需恢复 |

**关键设计：落库与收尾合并进同一事务。**

```
要么「业务数据 + 任务状态」一起成功，
要么一起回滚（租约过期后正常重试，且不会撞唯一约束）。
```

## 四、技术选型说明

### 4.1 为什么用 PostgreSQL 做任务队列，不用 Celery / RabbitMQ

**选择**：`chat_runs` 表 + `FOR UPDATE SKIP LOCKED`

**理由**：

1. **少一个中间件**。任务数据和业务数据在同一个库里，
   排查时一条 SQL 就能看到「任务状态 + 消息内容 + 证据」的全貌；
2. **事务边界清晰**。落库和任务收尾可以在同一事务里，避免不一致窗口；
3. **SKIP LOCKED 已经够用**。队列并发量级不高（单机几十 QPS），
   不需要专业消息队列的吞吐。

**代价**：没有死信队列、没有优先级、没有延迟任务。当前场景用不到。

### 4.2 为什么用 SSE，不用 WebSocket

**选择**：SSE + 事件表回放

**理由**：

1. **断线续传天然支持**。客户端重连带 `?after=cursor`，服务端从该位置补发；
   WebSocket 需要自己实现重连协议和消息序号；
2. **单向推送足够**。前端只需要接收，不需要服务端主动双向通信；
3. **走 HTTP，穿透性好**。不需要额外配置。

**代价**：不支持二进制、不支持客户端推送。当前场景用不到。

**注意**：这不是 token 级流式。答案先生成完整、校验、落库，
再按 40 字块回放——本质是「假流式」，换取「用户看到的内容一定已经过校验」。

### 4.3 为什么不用向量库 / RAG

**选择**：纯结构化工具调用

**理由**：

1. **数据本身是结构化的**。行情、财报、股东、宏观都有明确 schema，
   精确查询 > 语义检索；
2. **RAG 引入不确定性**。向量召回的相关性不可控，
   而投研场景需要「查什么就返回什么」；
3. **引用链更清晰**。工具调用天然有「参数 → 结果」的对应关系，
   而 RAG 需要额外做 chunk 溯源。

**代价**：无法处理非结构化文档（研报全文、会议纪要）。
这是后续要补的，但会走「文档入库 + 切片」的独立链路，不改变主流程。

### 4.4 为什么 iFinD 原文直接透传，不解析

**选择**：`_result_payload_text()` 原样返回 content 字段

**理由**：

程序一旦开始「解析」，就会在某个环节出错——单位换算、报告期口径、字段映射。
**而这些错误模型看不出来，用户更看不出来。**

对比：

| | 程序解析 | 原文透传 |
|---|---|---|
| 解析错误 | 可能发生且隐蔽 | 不存在 |
| token 消耗 | 低（只传抽取的字段） | 高（传完整原文） |
| 数字校验 | 可以做 | 只能校验引用存在性 |
| 模型负担 | 轻 | 重（自己读原始表格） |

**代价用提示词和上下文管理来消化**：
- `TOOL_RESULT_LIMIT=32000` 限制单次上限；
- 提示词明确禁止自行算同比/环比；
- 跨轮丢弃工具原文，避免上下文膨胀。

### 4.5 为什么前端零构建

**选择**：原生 HTML/CSS/JS

**理由**：

1. **页面简单**。只有三个页面：登录、对话、用量；
2. **部署简单**。复制静态文件即可，无 npm、无打包、无 node_modules；
3. **改完刷新即可**。不需要等热更新。

**代价**：没有组件化，复用靠函数。页面超过 10 个时就该考虑迁移了。

### 4.6 为什么用 AgentScope 而不是 LangChain

**选择**：AgentScope 2.0.12

**理由**：

1. **ReAct 实现更贴近原始论文**。事件流设计清晰，能拿到
   `ToolCallStartEvent` / `ModelCallEndEvent` 等细粒度事件；
2. **状态对象可注入**。`AgentState` 允许外部加载和保存，
   这是跨轮上下文延续的基础；
3. **中间件机制**。`on_compress_context` / `on_model_call` 等公开钩子，
   能在不改框架源码的前提下干预。

**局限**：它只负责「生成回答」，不知道有数据库这回事。
落库、重试、事务边界全是应用层的责任。

### 4.7 为什么用 PostgreSQL RLS 做多租户隔离

**选择**：行级安全策略 + `tenant_scope()` 注入

**理由**：

1. **在数据库层强制**，不依赖每个查询都记得加 `tenant_id`；
2. **`force row level security`** 让表 owner 也受约束，
   防止运维误操作跨租户读数据；
3. **代价小**。每次请求多一次 `set_config`，可忽略。

**例外**：`chat_runs` 不启用 RLS（内部表，不含用户内容），
但所有查询必须显式带 `tenant_id`——这是硬约束。

## 五、后续优化方向

### 5.1 体验层（不依赖外部决策）

| 项 | 现状 | 目标 |
|---|---|---|
| **长任务进度可见** | 只有一行状态文字，覆盖式更新 | 累加展示「已完成的取数步骤」 |
| **降级提示说人话** | 暴露 `timeout`、`[E1-25]` 等内部术语 | 描述对用户的影响，技术详情折叠 |
| **超时兜底** | 把原始 JSON 当答案展示 | 输出可操作摘要，不显示原始数据 |
| **追问引导** | 答案结束后页面空白 | 给出 2-3 个追问建议 |

### 5.2 数据准确性

| 项 | 问题 |
|---|---|
| `degraded` 被计为 failed | 降级回答在统计里算失败，用量报表失真 |
| 失败轮次不计配额 | 用量数据系统性偏低 |
| 时区口径不一致 | 配额检查用应用时区，写入用数据库时区 |
| `meta.evidence_count` 与实际不符 | 前端显示的证据数可能与实际行数不一致 |

### 5.3 数据源扩展（需商务决策）

| 项 | 状态 | 前置条件 |
|---|---|---|
| **研报**（标题 + 摘要 + 链接） | 未开始 | **需采购授权**。优先问 iFinD 能否加购 |
| **公告原文库** | 未开始 | 巨潮/交易所公开数据，技术可行 |
| 会议纪要 | 未开始 | 授权成本高，待评估 |

**研报是关键**：它决定「事件点评范式」「可比公司对比范式」等思维链能否落地。

### 5.4 思维链体系

**目标**：在自由 Markdown 基础上沉淀可复用的研报骨架（历史四段格式仍兼容）。

| 步骤 | 内容 |
|---|---|
| 1 | 把 24 份框架（进门投研 8 + Alpha派 16）结构化成模板 |
| 2 | 实现路由：按问题类型自动匹配 |
| 3 | 支持用户 @ 手动指定 |

**前置问题**：思维链是「提示词工程」还是「数据处理」？
划在提示词工程是安全的；如果涉及字段抽取或计算，会违反原文透传的红线。

### 5.5 模式区分（规划中）

参考进门的三栏结构（聊天 / 研究 / 任务），未来分两种模式：

| 维度 | 聊天窗口 | 研究窗口 |
|---|---|---|
| 耗时 | 几秒到十几秒 | 几十秒到几分钟 |
| 工具调用 | 1-3 次 | 8-20 次 |
| 是否异步 | 同步等待 | **应可离开页面** |
| 配额 | 独立计数 | 独立计数 |

**这个改动涉及异步任务、独立配额、可能独立的结果表，工作量较大。**

### 5.6 基础设施

| 项 | 现状 | 目标 |
|---|---|---|
| 监控 | 无 metrics / tracing | 接入 Prometheus + 结构化日志 |
| 事件清理 | `session_events` 只增不删 | 引入 checkpoint cursor + 定期裁剪 |
| 限流 | 进程内状态 | 迁到 Redis，支持多实例 |
| 迁移管理 | 手写 SQL 按序执行 | 引入 Alembic（或至少加版本校验） |
| 依赖锁定 | `requirements.txt` 缺 agentscope、openai | 补全并锁定版本 |

## 六、总结

这个项目解决的核心问题是**「让 AI 的回答经得起查」**。

技术上做了三个关键选择：

1. **任务队列建在数据库上** —— 少一个中间件，事务边界清晰；
2. **iFinD 原文不解析直接透传** —— 避免程序加工引入的隐蔽错误；
3. **落库与收尾合并进同一事务** —— 消除并发下的数据不一致窗口。

代价是复杂度：一轮请求跨 10 个以上事务，
需要 fencing、租约、缺口检测等多道保护。

**但这些复杂度换来的是：用户看到的每个数字，都能追到原始数据。**
