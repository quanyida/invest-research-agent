# AgentScope 压缩策略源码分析

> 分析对象：AgentScope `v2.0.12`（项目内副本 `agentscope/`）
> 归档时间：2026-11-21
> 关联：`docs/v1.12-上下文压缩与降级策略讨论.md`、`投研Agent-V2待办.md` 附录 D

---

## 1. 三层触发机制

AgentScope 的压缩不是单一机制，而是三层配合：

| 层级 | 触发方式 | 默认阈值 |
|---|---|---|
| **自动压缩** | 每次模型调用前自动检查 token | `context_size × trigger_ratio`（0.8） |
| **提前预警** | 注入提示，告知模型"接近阈值" | `trigger_ratio - context_buffer_ratio`（0.6） |
| **模型自主** | 模型主动调用压缩工具 | 同上，单次降低阈值 |

第三层需要模型自己判断"当前工作告一段落、可以压缩了"。工具描述里写明了适用时机：

> Call it between tasks, where the completed work can be preserved accurately
> in a summary, rather than in the middle of a task. Keep the current context
> when the exact earlier details are still needed.

**这意味着框架设计者认为：压缩时机应该由模型判断，而不是纯靠阈值。**

## 2. 核心配置（`ContextConfig`）

源码位置：`agentscope/agent/_config.py`

| 参数 | 默认 | 约束 | 含义 |
|---|---|---|---|
| `trigger_ratio` | 0.8 | >0, ≤0.9 | 超过该比例触发压缩 |
| `reserve_ratio` | 0.1 | >0, <0.9 | 压缩后保留最近多少比例的上下文 |
| `context_buffer_ratio` | 0.2 | ≥0, ≤1 | 提前预警的缓冲带 |
| `compression_fallback_to_truncation` | True | — | 摘要失败时是否回退到截断 |
| `tool_result_limit` | 见源码 | — | 单次工具结果进入上下文的上限 |

**约束关系**：

- `reserve_ratio < trigger_ratio`（否则无法压缩）
- `context_buffer_ratio < trigger_ratio`（否则预警失效）

`trigger_ratio` 上限 0.9 的原因写在注释里：

> To reserve the context for context compression, the maximum ratio is 0.9.

**必须给压缩请求本身留出空间**——压缩也是一次模型调用，它的输入也要塞进同一个上下文窗口。

## 3. 压缩执行流程

源码位置：`agentscope/agent/_agent.py::_compress_context_impl`

```
1. 限制上下文中的图片数量
2. 估算 token（system prompt + summary + context + tools schema）
3. 若 < 阈值 → 直接返回，不做任何事
4. 若 context 为空 → 抛 RuntimeError
      （说明 system prompt 或 summary 本身就超了，无法再压缩）
5. 按 reserve_ratio 切分：
     msgs_to_compress  ← 较早的部分
     msgs_to_reserve   ← 较近的部分
6. 若 to_compress 为空（reserve 太大）→ 把 reserve_ratio 降为 0 重切
7. 组装压缩请求：
     SystemMsg(system prompt)
     + UserMsg(旧 summary, 若存在)      ← 注意：旧摘要会一起送入
     + msgs_to_compress
     + AssistantMsg(instructions, 若传入)
     + UserMsg(compression_prompt)
8. 用 structured output 生成摘要
9. 成功后：
     state.summary = 新摘要
     state.context = msgs_to_reserve
```

### 3.1 第 4 步的特殊处理

```python
if len(self.state.context) == 0:
    raise RuntimeError(
        f"The system prompt ... exceed(s) the compression threshold "
        f"({threshold} tokens), cannot be compressed.",
    )
```

**这是一个显式的「无法压缩」信号**，交给开发者处理。框架不假装能解决。

### 3.2 第 7 步：旧 summary 会重复送入

```python
if self.state.summary:
    msgs_system.append(UserMsg("user", self.state.summary))
```

**多次压缩后，早期信息会经历「摘要的摘要」**，逐层衰减。

这是框架明知的有损设计——压缩本质就是有损的。

---

## 4. 摘要的结构化约束

压缩不是让模型自由发挥，而是**强制输出固定结构**：

```python
summary_template = (
    "<system-info>Here is a summary of your previous work\n"
    "# Task Overview\n{task_overview}\n\n"
    "# Current State\n{current_state}\n\n"
    "# Important Discoveries\n{important_discoveries}\n\n"
    "# Next Steps\n{next_steps}\n\n"
    ...
)
```

四个字段：**任务概览、当前状态、重要发现、下一步**。

用的是 `generate_structured_output`，带 JSON Schema 约束，不是普通文本生成。

### 4.1 压缩提示词的设计意图

`compression_prompt` 里有几段值得注意的要求：

> This summary may itself be summarized again later, and the conversation
> history it refers to will be gone, so every reference must be self-contained
> — resolve anything that depends on the vanished context into an absolute,
> fully-qualified form

具体三条：

| 要求 | 说明 |
|---|---|
| **时间绝对化** | "今天""最近"必须转成绝对日期，因为未来没人知道"今天"是哪天 |
| **指代具体化** | 不能用"这个文件""上面的方法"，必须写全路径、符号名、ID、URL |
| **在途工作留痕** | 后台任务要记 id 和状态，标注归属（用户要求 vs 自己决定） |

**这说明框架作者踩过坑**——摘要丢失上下文后，模型无法理解自己的摘要。

## 5. 失败处理的三种路径

### 5.1 情况 A：压缩请求本身超限

```python
if estimated_compression_tokens > self.model.context_size:
    context_overflow = True
```

进入「逐条丢弃最老消息再试」的循环：

```python
for i in range(1, len(msgs_to_compress) + 1):
    messages = msgs_system + msgs_to_compress[i:] + ... 
    if estimated_compression_tokens < ctx.context_size * trigger_ratio:
        break
```

**注意判据用的是 `trigger_ratio` 而不是 1.0**——留 10% 给模型输出。

### 5.2 情况 B：摘要生成抛异常

```python
if res is None:
    if not cfg.compression_fallback_to_truncation:
        raise error
    logger.warning("Summary generation failed, falling back to truncation")
```

**两条分支**：

| 配置 | 行为 |
|---|---|
| `True`（默认） | 静默截断，保留 `reserve_ratio` 部分 |
| `False` | 抛异常，交给上层处理 |

**本项目设成 `False`**，所以会抛异常。

### 5.3 情况 C：摘要有返回但内容为空

```python
new_summary = self.state.summary or (
    "<system-info>Some earlier messages were truncated for "
    "limited context.</system-info>"
)
```

**保留旧 summary**，或写入一个固定标记字符串。

**这个标记就是本项目 `agent_state_store.py` 里 `TRUNCATED_MARKER` 检测的对象。**

## 6. 本项目与上游默认值的差异

| 项 | 上游默认 | 本项目 | 影响 |
|---|---|---|---|
| `trigger_ratio` | 0.8 | **0.7** | 阈值从 80 万降到 70 万 token |
| `compression_fallback_to_truncation` | True | **False** | 失败时抛异常，不静默截断 |
| `context_size` | 模型默认（通常 128k） | **1,000,000** | 阈值提高 7.8 倍 |
| 压缩前预处理 | 无 | **`ContextPruningMiddleware`** | 先裁旧工具原文再摘要 |
| 落库体积检查 | **无** | **512KB** | 项目自设 |
| 会话状态持久化 | 交给 Storage | **JSONB 列 + 乐观锁** | 项目自设 |

### 6.1 最关键的差异

**上游没有任何针对 `AgentState` 体积的限制。**

我核实了两个存储后端：

**SQL 版**（`app/storage/_sql/_storage.py:1288`）：

```python
async def update_session_state(self, user_id, agent_id, session_id, state):
    """Read-modify-write on the payload; raises if absent."""
    row = await sess.get(SessionRow, session_id)
    if row is None:
        raise KeyError(...)
    record.state = state
    row.payload = new_row.payload      # 直接写，不检查大小
    await sess.commit()
```

**Redis 版**（`app/storage/_redis_storage.py:969`）：同样不检查。

**结论：512KB 这个限制完全是项目自加的，不是框架要求。**

## 7. 场景匹配度分析

### 7.1 上游压缩机制的设计前提

从参数和提示词看，框架假设的使用场景是：

- **长任务**：一个任务跨越多轮工具调用，可能持续几十次迭代
- **上下文必然膨胀**：因为工具结果累积
- **压缩是常态而非异常**：`trigger_ratio` 0.8、`reserve_ratio` 0.1 都是为了频繁压缩而调
- **模型需要判断压缩时机**：所以提供了压缩工具

### 7.2 本项目的实际场景

| 维度 | 上游假设 | 本项目实际 |
|---|---|---|
| 单轮工具调用 | 可能几十次 | **最多 4 次** |
| 单轮上下文峰值 | 接近 context_size | 约 20 万 token |
| 触发阈值 | 128k × 0.8 ≈ 10 万 token | 1M × 0.7 = **70 万 token** |
| 是否够得到阈值 | 是 | **否，差 2.8 倍** |

**结论：本项目的使用强度远低于上游设计目标，压缩机制基本不会触发。**

### 7.3 真正会触发的是 512KB 落库检查

按 `compact_agent_state` 剥掉工具块后的体积估算：

- 每轮约 2000 字问答 ≈ 6000 字节
- 10 轮 ≈ 60KB
- **离 512KB 差 8 倍，需要约 80 轮才会触发**

但这条路径**是项目独有的、上有没有对应机制的**。

---

## 8. 归档结论

1. **AgentScope 的压缩是「token 驱动 + 结构化解摘要 + 有损丢弃」**，
   设计目标是长任务场景，本项目场景强度不足，几乎不触发。

2. **本项目自设的 512KB 落库检查是另一套独立机制**，
   与框架压缩无直接关系，但它的失败降级写错了（写空 payload）。

3. **两套机制都应该重新评估**：
   - 框架压缩：既然不触发，是否要在配置上做适配（降低 `context_size` 或
     引入单轮预算），让它重新有效？
   - 自设检查：保留的话必须修好失败降级；废弃的话要确认没有它会导致什么问题。

4. **上游保留了一份重要设计思想值得借鉴**：
   摘要的「自包含」要求（时间绝对化、指代具体化、在途工作留痕）。
   如果本项目要做历史摘要重建，这些约束必须继承。
