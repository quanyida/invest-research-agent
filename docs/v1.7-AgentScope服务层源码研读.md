## 0. 一句话结论

AgentScope v2 的“智能体服务”不是把 Agent 常驻在内存里，而是：

**FastAPI 控制面 + 无状态 Agent 运行时 + 存储做事实源 + MessageBus 做实时协调。**

每次 `POST /chat` 只负责“把一次运行请求放进队列”，真正执行由进程内的 `WakeupDispatcher` 拉起 `ChatService.run`；`ChatService` 在**分布式 session 锁**下，按本次 session 动态装配 middleware、toolkit、model 和 Agent，然后调用 `Agent.reply_stream()`；执行过程中每个事件同时写入**可回放的 session event log** 并广播给 SSE 订阅者；最后在**shielded task**里统一落库 messages、AgentState 和 checkpoint cursor。

这套设计的关键不是“Agent 怎么写”，而是**把一次 Agent 运行当成一个可排队、可恢复、可取消、可回放、可观测的任务**。

## 1. 服务层分层

目录在 `src/agentscope/app/`：

| 层 | 目录/文件 | 职责 |
|---|---|---|

## 3. 一次 chat 的完整时序

### 3.1 `POST /chat` 是 fire-and-forget

入口：`src/agentscope/app/_router/_chat.py:409 chat(...)`

它不直接在 HTTP 请求里跑 Agent，而是分三种输入：

1. **普通 `Msg` / `list[Msg]`**
   - 校验 session 归属
   - `enqueue_chat_input(...)` 进入 per-session FIFO
   - 返回 `status="queued"`
   - 同一路径同时覆盖 idle 和 busy，避免 check-then-spawn 竞态，也保证快速连发的顺序

2. **HITL 结果**（`UserConfirmResultEvent` / `ExternalExecutionResultEvent`）
   - 先通过 `SubagentHitlProjector.resolve(...)` 找到真正 owning 的 worker session
   - 向该 session 入队 `resume` 触发器
   - 返回 `status="started"`
   - 这样 leader 只是前门，worker 的 resume 不会占用 leader 的 run slot

3. **`None`**
   - 从当前状态继续，直接 spawn

对应返回：`queued` / `started`。HTTP 响应体不承载 Agent 事件，事件走 SSE。

### 3.2 WakeupDispatcher 是唯一的 spawn 点

`src/agentscope/app/_manager/_wakeup_dispatcher.py`

- 每个进程一个 asyncio task
- 订阅共享 trigger signal
- 每次 signal drain 最多 64 条 durable trigger
- 按 `kind` 分派：
  - `wake`：idle session 唤醒，跑 `input_msg=None`，忙时跳过
  - `resume`：HITL 恢复，忙时不能丢，0.1s 后退避重入队
  - `message`：带真实用户消息，忙时也不能丢
  - `queued_message`：从 per-session FIFO 取普通输入，忙或 parked 时延后
- 只有这里调用 `ChatRunRegistry.spawn(...)`，从结构上消灭“两个 writer 同时抢一个 session run slot”的竞态

### 3.3 ChatRunRegistry 保证进程内一个 session 只有一个 run

`src/agentscope/app/_manager/_chat_run_registry.py:39 spawn(...)`

- `dict[session_id, asyncio.Task]`
- 同 session 已有未完成 task 时直接拒绝并 `coro.close()`
- task 完成自动摘除
- 进程关闭时统一 cancel 并 await，确保 `finally` 和锁释放执行

跨进程的互斥不靠它，靠 MessageBus 的 session lock。

### 3.4 ChatService.run 在 session 锁下装配并执行

入口：`src/agentscope/app/_service/_chat.py:296 run(...)` → `:908 _run_impl(...)`

整个 `_run_impl` 包在：

```python
async with self._message_bus.acquire_lock(
    MessageBusKeys.session_lock(session_id),
    ttl_secs=MessageBusKeys.SESSION_RUN_TTL_SECS,
):
```

锁内先装配，再执行。装配顺序：

1. 解析 agent / session record
   - `resolve_agent` 支持自己的 agent 和共享 agent
   - `get_session` 取 session
2. 解析 team 身份
   - leader / worker
   - worker 失败也要能通知 leader
3. `WorkspaceManager.get_workspace(...)`
   - 把 workspace workdir 加入 permission context
4. 解析 channel binding
   - 群聊里“以用户身份读”的工具只允许私聊，避免权限串用
5. 组装 middleware 链
6. 组装 toolkit
7. 构建 model + fallback model
8. 构造 `Agent(...)`

middleware 顺序（`_chat.py:1110` 起）：

```text
SteeringMiddleware
InboxMiddleware
StateChangeMiddleware
ToolOffloadMiddleware（可选）
TeamMemberLoopMiddleware（仅 worker）
SOPStepSubmitMiddleware（仅 SOP 派发）
extra_agent_middlewares（调用方扩展）
TTSMiddleware（有 TTS 配置时）
RAGMiddleware（有 KB 时）
```

Agent 构造（`_chat.py:1325`）：

```python

    name=...,
```

### 3.5 执行循环：`agent.reply_stream`

`_chat.py:1392` 起：

- Case A：新回复
  - 先 `upsert_message` 保存用户输入
  - `async for event in agent.reply_stream(inputs=input_msg)`
  - `ReplyStartEvent` 创建 `AssistantMsg`
  - 后续事件 `append_event`
- Case B：续跑
  - 从 storage 取回原 reply
  - 把 HITL 结果 append 进去
  - 发布一个 synthetic `ReplyStartEvent`，前端据此识别“续跑”而不是新回复

每个事件做三件事：

1. `publish_session_event(...)`：写 replay log + 广播
2. `_project_event(...)`：做跨 session UI 投影（如 subagent HITL）
3. 更新 `checkpoint_cursor`

事件处理中如果 `CancelledError` 落在 publish 的 await 上，会重新 `current.cancel()`，把中断重新投递到下一次 `__anext__`，确保 Agent 的 interruption cleanup 一定执行，而不是丢事件后直接放弃生成器。

一轮结束后：

- 检查 inbox 是否还有积压
- 有积压且 Agent 没有 parked 在 awaiting tool call，就继续 `input_msg=None` 再跑一轮
- 没有积压就释放 inbox consumer 并退出

### 3.6 持久化：shielded task，锁释放前必须写完

`_chat.py:1675` 起：

```python
async def _persist():
    async with session_event_checkpoint_lock:
        for msg in reply_msgs:
            await storage.upsert_message(...)
        await storage.update_session_state(...)
        if checkpoint_cursor:
            await bus.registry_set(session_event_checkpoint(...), cursor)
            await bus.log_trim(session_events(...), before_id=cursor)

persist_task = asyncio.create_task(_persist())
await asyncio.shield(persist_task)
```

为什么必须 shield：

- 外层可能被 cancel
- 但 messages / AgentState / cursor 必须写完
- 而且必须在 session lock 释放前写完，否则下一个 worker 可能读到旧 state

`finally` 里还会：

- `finish_active_chat_reply`
- worker 失败时通知 leader（ERROR / INTERRUPTED）
- 自动命名 session
- SOP 续跑推进

## 4. Toolkit 装配：真正的“工具分层”

入口：`src/agentscope/app/_service/_toolkit.py:46 get_toolkit(...)`

装配顺序：

1. workspace builtins
   - `Bash` / `Read` / `Write` / `Grep` 等
2. planning tools
   - `TaskCreate` / `TaskList` / `TaskGet` / `TaskUpdate`
3. background task control
   - `ToolStop`
4. schedule control
   - `ScheduleCreate` / `ScheduleView` / `ScheduleDelete` / `ScheduleList`
   - 只有 session 有 model config 才挂，因为 schedule 要能发起新 chat
5. team tools
   - worker：只有 `TeamSay`
   - leader / 非 team：`TeamCreate`、`AgentCreate`、`TeamSay`、`TeamDelete`
   - `AgentInvite` 仅在存在可邀请 agent 时挂，避免空 enum 破坏 tool schema
6. SOP submit
   - 根据步骤是否已提交，挂 `SubmitHandover` 或 `SubmitVerdict`
7. caller extras
   - `extra_factory(user_id, agent_id, session_id)`
8. middleware tools
   - `for mw in middlewares: tools.extend(await mw.list_tools())`
9. channel tools
10. client builtin tools
    - 如 `AskUser`
11. client external tools
    - 最后追加；与 server tool 重名直接 `ValueError` fail closed

最后：

```python
Toolkit(
    tools=tools,
    skills_or_loaders=await workspace.list_skills(agent_id=...),
    mcps=await workspace.list_mcps(agent_id=..., session_id=...),
    tool_groups=tool_groups,
)
```

注意：**Skill 和 MCP 不是拍平成普通 tool，而是作为 Toolkit 的 `skills_or_loaders` / `mcps` 参数传入**，由 Toolkit/Agent 内部再展开。这一点对我们接 iFinD Skill/MCP 很关键：内置工具、领域工具、Skill、MCP 是四层，不是混在一个 list 里。

## 5. Model 装配：凭据也走统一访问控制

入口：`src/agentscope/app/_service/_model.py:11 get_model(...)`

流程：

1. `ResourceAccessService.resolve_credential(user_id, credential_id)`
   - 自己的凭据或共享给自己的凭据
   - 返回 raw record，不是 masked view
2. `CredentialFactory.from_dict(record.data)`
3. 如果配置了 `model_class`，在 credential 支持的 chat model classes 里找
4. 否则取默认 class
5. `model_cls.Parameters(**config.parameters)`
6. 构造 model
7. 用内置 model card 覆盖 `context_size` 和 `formatter.input_types`

```python

```

然后通过 `ModelConfig(fallback_model=fallback_model)` 注入 Agent。

## 6. 并发、队列与取消

### 6.1 三种 MessageBus 语义

`src/agentscope/app/message_bus/_base.py`

| 模式 | 方法 | 语义 |
|---|---|---|
| drain queue | `queue_push` / `queue_drain` | 单消费者、读即删、ack-on-read，TTL 兜底 |
| replay log | `log_append` / `log_read` / `log_trim` | 多消费者、各自 cursor、可 trim |
| pub/sub | `publish` / `subscribe` | fire-and-forget，只发给当前订阅者 |

另有：

- `registry_*`：持久 hash/字段
- `acquire_lock` / `acquire_lock_bounded`：分布式锁
- `is_locked`：锁状态查询

设计上刻意不提供“计数广播 / consumer group”，需要 fan-out 就写时给每个 recipient 的 inbox 各推一条。

### 6.2 per-session FIFO 与 at-most-once

`src/agentscope/app/_manager/_chat_input_queue.py`

`drain_chat_inputs(...)`：

1. 先拿 `chat_input_dispatch_lock`
2. 检查 session 是否 running
3. 检查是否 parked
4. 先写 durable claim，再 destructive dequeue
5. 消息先持久化，再开始执行

崩溃语义：

- 持久化前崩：claim 可安全重试
- 持久化后崩：发布 terminal failure，不重放 Agent 工具（避免未知副作用）

这就是“至少一次投递 + 最多一次执行”的工程取舍。

### 6.3 inbox consumer 防止丢唤醒

`src/agentscope/app/_bus_ops.py`

- run 开始时 `register_inbox_consumer`
- 运行期间 producer 看到已有 consumer，就不重复唤醒
- run 结束时 `has_pending_inbox_or_release`
  - 还有积压：保持注册，继续跑
  - 没有积压：释放注册，下一个 producer 自己唤醒
- 异常退出：`abandon_inbox_consumer`，如果还有积压就重新 enqueue wake

### 6.4 取消

`src/agentscope/app/_service/_session.py:257 cancel_session_run(...)`

1. 向 `session_cancel_channel` 广播 `{session_id}`
2. 每个进程的 `CancelDispatcher` 收到后取消本地持有的 chat / realtime task 和 background task
3. 发布方轮询 `session_lock` 是否释放
4. 超时返回 `False`，调用方可以继续做 cascade delete

取消是跨进程的，不依赖“知道哪个 worker 在跑”。

### 6.5 删除级联

`_session.py:327 delete_session(...)`：

1. cancel run
2. 删 session record（storage 层级联 message、schedule index、team dissolution）
3. purge bus 状态（events log、inbox）
4. drop workspace 状态

team / agent / schedule 的删除都委托到这里，cancel + purge 逻辑只有一份。

## 7. 状态机与 SSE

### 7.1 四态 SessionStatus

`src/agentscope/app/_service/_session.py:62`

```text
RUNNING
IDLE
AWAITING_PERMISSION
AWAITING_EXTERNAL_RESULT
```

优先级：

1. 先看分布式 session lock
   - 被任何 worker 持有 → `RUNNING`
2. 没有 run 时，才看持久化 `AgentState.context` 尾部
   - 有 tool call 在等用户确认 → `AWAITING_PERMISSION`
   - 有 tool call 已派发给外部执行器等结果 → `AWAITING_EXTERNAL_RESULT`
   - 否则 → `IDLE`

这样前端只需要渲染一个 indicator，不用自己合并多个 boolean。

### 7.2 SSE 回放

`src/agentscope/app/_router/_session.py:841 stream_session_events(...)`

关键顺序：

1. 先订阅 `session_events(session_id)`
2. 再 `log_read(since=after)` 回放
3. 两边都可能收到同一事件，用 `_entry_id` 去重
4. 投影 subagent HITL 卡片，并 reconcile 已失效的卡片
5. 30s 无事件发 `:\n\n` 心跳
6. 响应头 `Cache-Control: no-cache`、`X-Accel-Buffering: no`

先订阅再回放是为了覆盖“订阅建立”和“历史读取”之间的缝隙；去重保证不重复渲染。

### 7.3 messages 分页

`GET /sessions/{id}/messages`：

- `before` cursor 向前翻
- 返回 `event_cursor` / `is_running` / `has_more`
- 前端拿 `event_cursor` 作为 SSE 的 `after`，实现“先拉历史，再续流”

## 8. 存储模型

`src/agentscope/app/storage/_sql/_tables.py`

所有业务表基本是：

```text
id
created_at
updated_at
payload JSON
+ 少量提升为列的索引字段
```

例如：

- `credentials(user_id, payload)`
- `agents(user_id, source, payload)`
- `sessions(user_id, agent_id, source, source_schedule_id, team_id, payload)`
- `sops` / `sop_runs`
- `schedules`
- `teams`
- `knowledge_bases` / `knowledge_documents`
- `mcps` / `skills` / `channels`
- `messages` 单独表：`(session_id, msg_id, payload)` 复合主键

设计取舍：

- 跨 SQLite / Postgres / MySQL 可移植
- 只用普通 `JSON`，不用 JSONB
- 不用 generated column，不用 `FOR UPDATE`
- 原子 upsert 通过 dialect-native `ON CONFLICT` / `ON DUPLICATE KEY UPDATE` 显式分派

`SessionRecord` 里有：

- `origin`：user / schedule / channel / team / sop
- `state: AgentState`

这使“一次 session 从哪来、当前 Agent 状态是什么”都在一条记录里。

## 9. 这套设计最值得借鉴的点

### 9.1 必借

1. **HTTP fire-and-forget + SSE 分离**
   - 请求只负责入队，长任务不占 HTTP 连接
   - 事件通过 replay log + pub/sub 回放
2. **per-session 分布式锁**
   - 同一 session 永远只有一个 run
   - 锁内加载 state、装配 Agent、执行、落库
3. **单一 dispatcher**
   - 所有 run trigger 只从一个地方 spawn
   - 从结构上消灭并发 spawn 竞态
4. **事件 replay cursor**
   - 断线重连不丢事件
   - 前端先拉 messages 再续 SSE
5. **四态 status**
   - RUNNING 看锁，AWAITING_* 看持久化 context 尾部
   - 前端不用猜
6. **工具分层**
   - builtins / planning / domain / middleware / channel / client / skill / MCP 分开
   - 重名 fail closed
7. **落库 shielded + checkpoint lock**
   - 取消不等于丢状态
   - 锁释放前必须写完

### 9.2 可以借，但 v1 不必照搬

1. **Redis MessageBus**
   - 单机 v1 用 in-memory 实现即可
   - 但接口按 drain queue / replay log / pub-sub / registry / lock 抽象，后面换 Redis 不改业务
2. **Workspace 沙箱**
   - 投研 Agent v1 不需要 Bash/文件系统工具
   - 但保留 `workspace` 概念，后面接用户 PDF/图片时有地方放
3. **Team / SOP / Channel**
   - 当前 v1 不需要
   - 但 `origin`、`session_id`、`run trigger kind` 这些模型可以先留好
4. **多进程 / 多节点**
   - v1 单机可以只跑一个进程
   - 但 session lock、run registry、cancel 语义最好一开始就有，避免后面重构

### 9.3 不要借

1. **为每个 session 常驻一个 Agent 对象**
   - AgentScope 是每次 run 动态装配
   - 常驻对象会带来状态污染、内存泄漏、并发复用问题
2. **把 skill/MCP 拍平成普通 tool**
   - 会丢失 skill 的加载语义和 MCP 的生命周期
3. **在 HTTP handler 里直接跑 Agent**
   - 超时、断连、重试都会让状态不可控

## 10. 对投研 Agent v1 的落地建议

按优先级：

1. **先做 session 串行化**
   - 一个 session 同时只允许一个 run
   - 单机可以用 `asyncio.Lock` + DB 状态，接口保持 `acquire_lock`
2. **把 `POST /chat` 改成入队**
   - 返回 `queued`
   - 后台 worker 消费
3. **把事件写入 replay log**
   - 即使 v1 只用内存，也保留 `entry_id` + cursor
   - SSE 先订阅再回放
4. **把 status 做成四态**
   - 尤其是 `AWAITING_PERMISSION`，为后面 HITL 留口
5. **toolkit 分层**
   - 内置工具 / iFinD MCP / iFinD Skill / 用户自定义 分开注册
   - 不要把所有 tool 塞进一个 list
6. **落库统一走一个 checkpoint**
   - messages + AgentState + cursor 一次写完
   - 取消时 shield
