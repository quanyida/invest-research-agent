# v1.13 一轮对话的事务与落库拓扑

> 只记录一件事：一轮对话中，每张表的哪些字段在哪个事务、被什么操作写入。
>
> 结论：一轮对话不是一个事务。`messages`（助手正文）与 `conversations.agent_state` 在同一个事务；`chat_runs` 不在其中。

## 1. 时序

```text
T0 鉴权     sessions: auth_session_resolve + auth_session_touch
T1 请求     conversations + messages(U1) + messages(A1占位) + chat_runs(queued)
T2 claim    chat_runs: queued -> running（attempt+1、lease）
T3 装载     messages: A1 -> running（attempt>1 时清空 content/meta）
T4 读状态   conversations: select agent_state / agent_state_version（只读）
T5 事件     session_events: 每个 SSE 事件一条
T6 落库     messages(A1正文) + evidence + tool_calls + llm_calls
            + conversations(updated_at/title/agent_state) + usage_daily
T7 收尾     chat_runs: running -> done
```

事务边界：`app/db.py` 的 `tenant_scope()` / `session_scope()`，退出时 `db.commit()`，异常时 `db.rollback()`。

## 2. 逐事务

### T0 鉴权（独立事务）

入口：`app/api/deps.py`。

| 表 | 操作 | 字段 |
|---|---|---|
| `sessions` | SELECT（security definer） | `token_hash`, `user_id`, `tenant_id`, `expires_at`, `revoked_at` |
| `sessions` | UPDATE（`auth_session_touch`） | `last_seen_at` |

### T1 提交提问（请求线程）

入口：`app/api/chat.py:101`。

| 表 | 操作 | 字段 |
|---|---|---|
| `conversations` | INSERT（仅新会话） | `id`, `tenant_id`, `user_id`, `title`；其余用默认值（`agent_state='{}'`、`agent_state_version=0`） |
| `conversations` | UPDATE（已有会话） | `updated_at`；标题为空时写 `title` |
| `messages` | INSERT（用户消息 U1） | `id`, `tenant_id`, `user_id`, `conversation_id`, `request_id`, `client_request_id`, `role='user'`, `content=问题`, `status='done'`, `meta={}`, `created_at` |
| `messages` | INSERT（助手占位 A1） | 同上，`role='assistant'`, `content=''`, `status='queued'`, `created_at=U1+1µs` |
| `chat_runs` | INSERT（`run_queue.py:43`） | `id`, `tenant_id`, `user_id`, `conversation_id`, `message_id`, `request_id`；`status/attempt/created_at` 用默认值 |
| `usage_daily` | SELECT（配额检查） | `questions`, `tool_calls` |

U1、A1 占位、`chat_runs` 三者同事务；唯一索引 `chat_runs_one_active` 冲突时整笔回滚，返回 409 `CONVERSATION_BUSY`。

### T2 认领任务（worker）

入口：`app/agent/run_queue.py:75`。

| 表 | 操作 | 字段 |
|---|---|---|
| `chat_runs` | UPDATE | `status='running'`, `attempt=attempt+1`, `worker_id`, `started_at=now()`, `lease_until=now()+lease`；条件 `status='queued'`，`FOR UPDATE SKIP LOCKED` |
### T3 装载本轮（worker）

入口：`app/agent/run_worker.py:34`。

| 表 | 操作 | 字段 |
|---|---|---|
| `messages` | SELECT | 助手行（按 `id`）；不存在则 `finish(failed, RUN_NOT_FOUND)` |
| `messages` | SELECT | 用户行（按 `request_id` + `role='user'`），得到本轮问题 |
| `messages` | SELECT | 最近 6 条 `status in (done, degraded)` 的消息，仅用于 `agent_state` 缺失时重建 |
| `messages` | SELECT | `count(*) where role='assistant'`，算出 `turn` |
| `messages` | UPDATE | `status='running'`；`attempt>1` 时同时 `content=''`, `meta={}` |

### T4 读取 AgentState（只读）

入口：`app/agent/agent_state_store.py:86`。

| 表 | 操作 | 字段 |
|---|---|---|
| `conversations` | SELECT | `agent_state`, `agent_state_version` |

读出后只在内存里 `compact_agent_state()`：丢弃 `tool_call` / `tool_result` / `thinking` / `hint` 块，并剥离助手文本中的 `[E..]` 引用；这些改动到 T6 才落库。

### T5 事件追加（每个 SSE 事件一次）

入口：`app/agent/run_worker.py:181` → `run_queue.py:151`。

| 表 | 操作 | 字段 |
|---|---|---|
| `session_events` | INSERT | `tenant_id`, `user_id`, `conversation_id`, `message_id`, `event`, `data`；`id` 用 bigserial，`created_at` 默认 `now()` |

事件含 `meta/plan/tool_start/tool_end/evidence/verify/delta/usage/done`。每个事件独立提交，所以一轮的提交次数是 N+6 量级（`delta` 每 40 字一片）。
### T6 落答案、状态与任务终态（核心事务）

入口：`app/agent/agentscope_runtime.py:409` → `app/agent/persist.py:143`（`tenant_scope` 在 `persist.py:167`）。

| 表 | 操作 | 字段 |
|---|---|---|
| `messages` | UPDATE（A1） | `content=最终答案`, `status=done/degraded/failed`, `meta`（含 `engine`、`turn`、`verify`、`agent_state_saved` 等） |
| `evidence` | INSERT（N 条） | `id`, `tenant_id`, `user_id`, `message_id`, `seq`, `tool`, `server`, `upstream_tool`, `args`, `args_hash`, `query_text`, `period_end`, `data_as_of`, `as_of_label`, `fetched_at`, `payload`, `facts`, `raw_excerpt`, `truncated`, `parse_quality`, `parser_version`, `tool_schema_hash`, `source_title`, `source_url`, `source_publisher`, `source_published_at`, `channel` |
| `tool_calls` | INSERT（主行 + 子行） | `id`, `tenant_id`, `user_id`, `message_id`, `conversation_id`, `request_id`, `parent_id`, `step`, `tool`, `server`, `upstream_tool`, `args`, `args_hash`, `query_text`, `status`, `cached`, `latency_ms`, `error_code` |
| `llm_calls` | INSERT（每次模型调用一条） | `id`, `tenant_id`, `user_id`, `message_id`, `request_id`, `purpose`, `model`, `prompt_version`, `temperature`, `max_tokens`, `prompt_tokens`, `completion_tokens`, `reasoning_tokens`, `finish_reason`, `latency_ms`, `status` |
| `conversations` | UPDATE | `updated_at`；标题为空时写 `title` |
| `conversations` | UPDATE | `agent_state=:json`, `agent_state_version=agent_state_version+1`, `agent_state_updated_at=now()`；条件 `id=:id and agent_state_version=:v` |
| `usage_daily` | UPSERT | `questions+1`, `tool_calls+=n`, `llm_calls+=n`, `failed+=0/1`, `prompt_tokens+=`, `completion_tokens+=`, `total_latency_ms+=`；`ON CONFLICT (tenant_id, user_id, day)` |
| `chat_runs` | UPDATE（仅当传入 `run_id`） | `status=done/failed`, `finished_at=now()`, `lease_until=null`, `error_code=null`, `error_message=null`；条件 `id=:run_id and tenant_id=:tenant_id and status='running'` |

补充：

- raw 模式下 `evidence.facts=[]`、`raw_excerpt` 存原文、`parse_quality=1.0`、`parser_version='raw-passthrough'`。
- `tool_calls` 主行 `parent_id=null`；每个 upstream 一条子行，`parent_id=主行 id`。
- `llm_calls.prompt_version` 目前硬编码 `'v1'`。
- `agent_state` 影响 0 行 → `state_saved=False`、`usage.agent_state_conflict=true`，不重试；下一轮仍读到旧版本 state，只有 load 返回空/损坏/truncated 时才从 `messages` 重建。
- 体积超过 `AGENT_STATE_MAX_KB=512` 时先压缩一次，仍超限存 `{}` 并置 `meta.agent_state_skipped=true`（版本不递增）。
- `persist_turn(..., run_id=...)` 在同一个 `tenant_scope` 事务末尾推进 `chat_runs`，返回 `(state_saved, run_finalized)`。`run_finalized=True` 表示本次事务真正把任务从 `running` 推到终态；重复执行时条件不满足，返回 `False`，不会覆盖终态。
- 状态映射：`status in ('done','degraded') -> chat_runs.status='done'`，其它 -> `'failed'`。`degraded` 只表示部分引用无法核实，不是运行失败。

### T7 收尾兜底（仅异常路径）

入口：`app/agent/run_worker.py` → `run_queue.finish()`。

正常路径不再调用 T7：`T6` 已把 `chat_runs` 推进到终态，`done` 事件里的 `run_finalized=true`，Worker 直接返回。

只有以下情况才单独调用：

| 场景 | 表 / 字段 |
|---|---|
| 落库未执行（异常在 `persist_turn` 之前抛出） | `chat_runs`: `finish(failed)`；`messages`: `mark_assistant_failed()` |
| 流结束但没有 `done` 事件（落库未完成） | 先补 `done(error)` 事件，再 `mark_assistant_failed()` 与 `finish(failed)` |
| 兜底 | `finish(done)` 仅当任务仍是 `running` 时生效，否则是 no-op |

`finish()` 自身带 `status='running'` 条件，因此与 T6 的收尾互斥：谁先成功谁生效，后执行者为 0 行。

### 失败与回收（各自独立事务）

| 场景 | 表 / 字段 |
|---|---|
| 流内异常 | `chat_runs`: `finish(failed)` 写 `status/finished_at/error_code/error_message`；`messages`: `mark_assistant_failed()` 写 `content`（四段兜底文案）、`status='error'`、`meta={error, failed_at}` |
| 租约过期 | `chat_runs`: `sweep()` 改 `status`（`queued` 或 `failed`）、清 `worker_id`/`lease_until`、写 `finished_at`、`error_code='LEASE_EXPIRED'` |
| 回收回队列 | `messages.status`: `running -> queued` |
| 回收判失败 | `messages`: `mark_assistant_failed()` |

## 3. 原子性边界

- **原子**：T1（U1 + A1 占位 + 入队）；T6（A1 正文 + 证据/审计/用量 + `agent_state` + `chat_runs` 终态）。
- **不再存在 T6/T7 之间的成功窗口**：答案与任务终态在同一事务提交。崩在 T6 提交前 → 两者都未完成，租约过期后正常重试；崩在 T6 提交后 → 两者都已完成，重跑不会被触发。
- 重跑时 `attempt>1` 会清空 A1 的 `content/meta`，但只会在 T6 未提交时发生；若上一次 T6 已提交，任务已被推进为终态，不会被 `sweep` 重新入队，因此不会撞 `evidence` 的 `unique(message_id, seq)`。

## 4. 原子过程与宕机恢复

### 4.1 恢复模型

机器宕机后，进程内的 AgentScope Agent、工具调用栈、SSE 生成器和未提交的内存状态全部丢失。能用于恢复的只有 PostgreSQL 中已经 `commit` 的数据。

| 持久状态 | 作用 | 是否可作为恢复依据 |
|---|---|---|
| `chat_runs.status` / `attempt` / `lease_until` | 任务是否在队列、是否被占用、还能重试几次 | 是，队列恢复的主依据 |
| `messages.status` / `content` | 用户看到的助手消息状态和最终正文 | 是，但必须与 `chat_runs`、`evidence` 交叉判断 |
| `evidence` | 最终答案引用的证据 | 是，`T6` 已提交时与答案同时可见 |
| `session_events` | SSE 回放日志 | 仅用于展示和断线重连，不是最终答案的权威来源 |
| `conversations.agent_state` | 下一轮对话的 AgentScope 上下文 | 是；缺失、损坏或带截断标记时可从最近消息重建 |
| `tool_calls` / `llm_calls` / `usage_daily` | 审计与用量 | 与 `T6` 同事务，不能单独作为恢复入口 |

恢复由 `RunWorker` 驱动。worker 启动后每轮循环执行：

```text
sweep()  ->  claim()  ->  execute()
```

当前配置来自 `.env`：

```text
RUN_LEASE_SECONDS=900
RUN_MAX_ATTEMPTS=2
RUN_QUEUE_POLL_SECONDS=0.2
```

`lease_until` 只在 `claim()` 时写入一次，运行期间没有心跳续租。`sweep()` 只处理同时满足以下条件的行：

```text
status = 'running' and lease_until is not null and lease_until < now()
```

因此进程崩溃后，`running` 任务不是立刻恢复，而是要等租约过期；默认最长约 900 秒。启动时没有额外的全量对账逻辑，恢复仍然走 `sweep -> claim`。

SSE 连接不是任务执行者：POST /chat 返回的流只读 session_events，任务由 worker 独立执行，客户端断线不会取消 run。当前 EVENT_TAIL_TIMEOUT_SECONDS=600，短于默认 900 秒租约，因此 worker 崩溃后原 SSE 往往先结束，需要前端 resume 或刷新后继续读事件。

### 4.2 原子单元

| 原子单元 | 一次 `commit` 覆盖的写入 | 宕机发生在提交前的结果 |
|---|---|---|
| `T0` 鉴权 | `sessions.last_seen_at` | 只影响最后访问时间，不影响会话和对话数据 |
| `T1` 提交提问 | `conversations`（新建时）+ `messages` U1 + `messages` A1 占位 + `chat_runs(queued)` | 整笔回滚：不会留下“有用户消息但没有任务”或“有任务但没有助手占位”的半成品 |
| `T2` 认领 | `chat_runs`：`queued -> running`、`attempt+1`、`worker_id`、`started_at`、`lease_until` | 回滚为 `queued`，可被重新认领 |
| `T3` 装载 | `messages` A1：`status='running'`；重试时清空 `content/meta` | 回滚为 `queued` 或保持上一次状态，下一次 `claim` 会重新装载 |
| `T4` 读状态 | 无写入 | 不影响数据 |
| `T5` 事件 | 每条 `session_events` 独立提交 | 只丢当前未提交的那一条事件，之前事件仍在 |
| `T6` 落答案 | `messages` A1 + `evidence` + `tool_calls` + `llm_calls` + `conversations` 标题/时间/`agent_state` + `usage_daily` | 整笔回滚：答案、证据、审计、上下文、用量不会出现半套数据 |
| `T7` 收尾 | `chat_runs`：`running -> done/failed`、`finished_at`、清租约 | 回滚后仍是 `running`，等待租约回收 |
| 失败分支 A | `messages` 改为 `error`/`failed` | 回滚后仍为 `running`，等待租约回收 |
| 失败分支 B | `chat_runs` 改为 `failed` | 若 A 已提交、B 未提交，会出现“消息 error、任务 running”的中间态 |

`T1` 和 `T6` 是数据一致性的两个核心原子边界。`T5`、`T7` 与 `T6` 都不在同一个事务里，所以事件日志和任务终态允许短暂滞后。

### 4.3 宕机点矩阵

| 宕机时点 | 数据库中已提交的状态 | 重启后的自动恢复 | 结果与边界 |
|---|---|---|---|
| `T0` 鉴权事务中 | 可能没有 `last_seen_at` 更新 | 用户重新请求或重新登录 | 不影响对话数据 |
| `T1` 提交前 | 没有本轮数据 | 客户端重试 | 无脏数据 |
| `T1` 提交后、`T2` 前 | U1、A1 占位、`chat_runs(queued)` 全部可见 | worker 下一轮 `claim()` | 正常执行；即使原 SSE 客户端已经断开，任务仍会继续 |
| `T2` 事务中 | `claim` 未提交则仍是 `queued`；已提交则是 `running` | `queued` 直接认领；`running` 等租约过期后回收 | `T2` 自身不会产生半条任务 |
| `T2` 后、`T3` 前 | `chat_runs(running)`，A1 仍是 `queued` | 租约过期后 `sweep` 回队列，下一次 `claim` 执行 `T3` | 最多等待一个租约周期 |
| `T3` 后、`T6` 前 | `chat_runs(running)`，A1 为 `running`，可能已有部分 `session_events` | 租约过期后 `sweep` 回队列；`attempt>1` 时 `T3` 清空 A1 的 `content/meta` 后重跑 | 答案尚未落库，可以重跑；旧 attempt 的事件不会被删除 |
| `T5` 任一事件提交前后 | 之前的事件已提交，当前事件可能丢失 | 继续重跑或继续追加事件 | `session_events` 可能包含上一 attempt 的残留，回放时可能出现重复事件 |
| `T6` 事务中、提交前 | A1 仍是 `running`；`evidence/tool_calls/llm_calls/agent_state/usage_daily` 均未变 | 回滚后重跑 | `T6` 是整笔事务，不会留下半套答案或半套证据 |
| `T6` 已提交、`T7` 前 | 答案、证据、审计、`agent_state`、用量全部已提交；`chat_runs` 仍是 `running` | 当前代码会在租约过期后把它当作未完成任务重跑 | **高风险窗口**：`T3` 会因 `attempt>1` 清空已提交的 A1 正文；重跑写入相同 `evidence.seq` 会撞唯一约束，随后失败分支把消息改成 `error`。已提交答案可能被覆盖 |
| `T7` 事务中 | `finish` 未提交则仍是 `running`；已提交则为 `done`/`failed` | 未提交时回到上一行；已提交则不再被认领 | `finish` 的条件是 `status='running'`，重复调用不会把终态改回去 |
| `T7` 已提交后 | `chat_runs` 终态、A1 终态、答案和证据均已提交 | 不需要恢复 | 稳定终态；若 `done` 事件缺失，SSE 可能直接结束，但最终答案仍可从 `messages` 读取 |
| 失败分支 `mark_assistant_failed` 后、`finish` 前 | A1 已是 `error`/`failed`，`chat_runs` 仍是 `running` | 租约过期后仍可能回队列并重跑 | 消息先显示失败、任务后收尾；若随后重跑成功，消息会从失败变为成功 |
| `sweep()` 已提交、`_after_sweep()` 前 | `chat_runs` 可能已是 `queued` 或 `failed`，A1 状态尚未同步 | `queued` 会在下一次 `claim` 被 `T3` 修正；`failed` 没有后续 `claim` | **高风险窗口**：`sweep` 判失败但 `_after_sweep` 未执行时，A1 可能永久停在 `running`，需要人工修复 |
| PostgreSQL 宕机或整机断电 | 已提交事务按 PostgreSQL WAL 恢复；未提交事务回滚 | 数据库恢复后 worker 重新 `sweep -> claim` | 应用层不负责数据库备份；磁盘损坏或数据目录丢失必须依赖 PostgreSQL 备份/PITR |

### 4.4 重启后的判定顺序

不要只看 `messages.status`。按 `chat_runs`、`messages`、`evidence` 三者一起判断。下面查询以某条助手消息为例：

```sql
select
  r.id as run_id,
  r.status as run_status,
  r.attempt,
  r.lease_until,
  r.error_code,
  m.status as message_status,
  length(m.content) as answer_len,
  (select count(*) from evidence e where e.message_id = r.message_id) as evidence_count,
  (select max(s.id) from session_events s where s.message_id = r.message_id) as last_event_id
from chat_runs r
join messages m on m.id = r.message_id
where r.message_id = :message_id
order by r.created_at desc
limit 1;
```

`messages`、`evidence`、`session_events` 启用了 RLS；用应用账号排查时要先设置租户上下文，或使用具备相应权限的数据库账号。

| 查询结果 | 判定 | 处理 |
|---|---|---|
| 没有 `chat_runs` | `T1` 没有提交 | 客户端重新提问 |
| `run_status='queued'` | 任务已入队、尚未被执行 | 等待 worker `claim`；不要手工改消息 |
| `running` + `message_status='running'` + 租约未过期 | worker 可能仍在执行，或进程已死但租约未到 | 等待租约到期后由 `sweep` 回收 |
| `running` + `message_status='running'` + 租约已过期 | 典型的执行中宕机 | 让 `sweep` 回队列并重试；`attempt` 达到上限后转 `failed` |
| `running` + `message_status in ('done','degraded')` + `evidence_count>0` | `T6` 已成功，只差 `T7` | 停止 worker，按人工恢复流程补 `T7`；不要让租约自动重跑 |
| `failed` + `message_status='running'` | `sweep` 已判失败，但 `_after_sweep` 未完成 | 手工把消息标记为失败，避免僵尸 `running` |
| `done` + `message_status in ('done','degraded')` | 正常终态 | 不需要恢复 |
| `failed` + `message_status in ('error','failed')` | 正常失败终态 | 不需要恢复；由用户决定是否重试 |

### 4.5 历史数据：修复前已存在的 T6/T7 缺口

本节的恢复方案只适用于**本次修复之前**已经产生的数据。修复后 T6 已包含任务终态，新请求不会再出现该窗口。

如果仍发现旧记录满足 `messages.status in ('done','degraded')` 且 `chat_runs.status='running'`：

1. 先停止 worker，或将 `RUN_WORKER_ENABLED` 置为 `false`，避免 `sweep` 在租约到期后抢先重跑；
2. 确认答案与证据已提交：`messages.content` 非空、`evidence_count > 0`；
3. 在同一事务里把 `chat_runs` 改为 `done`，清空 `lease_until`，写 `finished_at`；
4. 如 `session_events` 缺少该消息的 `done`，补一条；
5. 恢复 worker。

示意 SQL（仅用于旧数据，执行前按实际租户和 `run_id` 替换参数）：

```sql
begin;

update chat_runs
set status = 'done',
    finished_at = now(),
    lease_until = null
where id = :run_id
  and status = 'running';

insert into session_events
  (tenant_id, user_id, conversation_id, message_id, event, data)
select
  r.tenant_id,
  r.user_id,
  r.conversation_id,
  r.message_id,
  'done',
  jsonb_build_object(
    'status', m.status,
    'message_id', r.message_id,
    'conversation_id', r.conversation_id,
    'request_id', r.request_id,
    'recovered', true
  )
from chat_runs r
join messages m on m.id = r.message_id
where r.id = :run_id
  and not exists (
    select 1
    from session_events s
    where s.message_id = r.message_id
      and s.event = 'done'
  );

commit;
```

不要通过删除 `evidence` 或清空 `messages` 来“修复”旧窗口；那会丢失已经提交的答案和引用。

### 4.6 数据一致性结论

- `T1` 保证“用户消息 + 助手占位 + 入队任务”不会半提交。
- `T6` 保证“答案 + 证据 + 工具/模型审计 + `agent_state` + 用量 + `chat_runs` 终态”不会半提交。
- `T5` 是逐事件提交，允许丢最后一条事件，也允许上一次 attempt 的事件残留；它只影响 SSE 回放，不应覆盖最终答案。
- 修复后 `T6` 与任务终态原子；`T7` 只做异常路径兜底。`chat_runs` 与 `messages` 不会再出现“一个完成一个运行中”的新记录。
- `agent_state` 与答案同在 `T6`：`T6` 回滚则保留旧上下文；`T6` 提交但 `agent_state` 乐观锁更新 0 行时，答案仍成功，下一轮会读到旧版本 state，不会自动从消息重建。只有 state 为空、schema 不匹配、校验失败或带截断标记时，才从最近 6 条消息重建。
- `usage_daily` 与 `T6` 同事务：成功提交一次计一次；`T6` 失败回滚不会计数。`T6` 已提交后任务已是终态，不会被重跑，因此不会重复计费，也不会撞 `evidence` 唯一约束。
- PostgreSQL 已提交事务的恢复依赖 WAL 和数据库自身的持久化配置；仓库内没有应用层的数据库备份/PITR 实现。
- 当前没有租约心跳续租。单实例 worker 顺序执行，不会自己扫掉自己；多实例部署时，单次 run 超过 900 秒可能被另一实例误判为过期并重跑，这是水平扩展前必须处理的边界。

### 4.7 取消保护与完成事件时序

`persist_turn` 在 `_persist()` 里通过 `asyncio.create_task` + `asyncio.shield` 执行。外层取消（超时、断线、进程信号）不会取消写任务；`_await_write` 捕获取消后先 `await persist_task`，等事务提交或回滚完成，再向外抛出 `CancelledError`。

因此：

- 取消发生在落库前 → 事务未开始，工具结果会丢失，但任务保持 `running`，租约过期后可重试；
- 取消发生在落库中 → 事务继续跑完，已采集的工具结果不会半途丢弃；
- 完成事件 `done` 只在 T6 提交后发出。前端收到 `done` 时，数据库已是终态。

对前端的影响：页面使用 `fetch` + `ReadableStream`，不是 `EventSource`，没有自动重连。`done` 稍晚只会让“进行中”多停留一个事务提交的时间，不会造成提前重连或状态错乱。若 T6 已提交但 `done` 事件未落库，`GET /messages/{id}/events` 会根据 `chat_runs.status='done'` 与消息终态合成一条 `done`，避免前端一直等待。

> 三副本部署下的逐场景宕机推演、残留并发窗口与加固建议，见 `docs/v1.14-三副本宕机场景归档.md`。本文只定义事务边界，不重复展开多实例竞争。

## 5. U11 的上下文加载与 AgentState 陈旧值

### 5.1 结论

是，但只针对“历史上下文”：U11 本身仍然作为当前问题单独传入；U1-A10 的历史上下文，正常情况下直接从 `conversations.agent_state` 加载。

- 系统不会把 `agent_state` 和 `messages` 历史合并使用。
- 只有 `agent_state` 缺失、为空、损坏或被标记为截断时，才会用 `messages` 最近几条消息重建。
- “过了几天”不会让 state 自动失效；对话 state 没有 TTL。
- 当前代码只判断 state 的格式有效性，不判断 state 是否对应当前最新一轮消息。

### 5.2 U11 的加载顺序

1. `POST /chat` 的 `T1` 写入 U11、A11 占位和 `chat_runs(queued)`。
2. worker 执行 `T3`，从 `messages` 取出 U11 的问题，并额外查最近 6 条 `done/degraded` 消息，作为 `run.history`。入口见 `app/agent/run_worker.py:54`。
3. `AgentScopeRunner` 调用 `AgentStateStore.load()`，读取 `conversations.agent_state` 和 `agent_state_version`。入口见 `app/agent/agentscope_runtime.py:253`。
4. 如果 state 有效，直接传给 `Agent(state=state)`，不会执行 `agent.observe(run.history)`。见 `app/agent/agentscope_runtime.py:319`。
5. 如果 state 无效，创建空的 `AgentState`，再把 `run.history` 注入 Agent。见 `app/agent/agentscope_runtime.py:329`。
6. 本轮结束后，答案和新的 `agent_state` 在同一个 `T6` 事务里提交。见 `app/agent/persist.py:212`。

正常情况下，U11 看到的是截至 A10 的 AgentState。这个 state 已经被 `compact_agent_state()` 处理过：工具调用、工具结果、thinking、hint 和正文引用标记会被剥离，不是完整的原始消息流水。见 `app/agent/agent_state_store.py:30`。

### 5.3 缺失或旧值怎么处理

| 情况 | 当前行为 |
|---|---|
| `agent_state='{}'`、字段为空、没有记录 | `load()` 返回 `None`，创建空 state，然后用最近 6 条消息重建 |
| `schema_version` 不匹配、JSON 校验失败 | 返回 `None`，重建 |
| state 里带 `Some earlier messages were truncated` 标记 | 主动丢弃 state，重建 |
| state 是合法 JSON，但内容是上一轮的旧值 | **直接使用旧值，不重建** |
| `T6` 整体失败，A10 没有保存成功 | `agent_state` 仍是 A9 的值；U11 直接加载 A9 的旧上下文 |
| `T6` 的答案提交成功，但 `agent_state` 乐观锁更新 0 行 | 答案已提交，state 仍是旧版本；U11 直接使用旧 state |
| state 序列化异常，没有生成新 payload | 本次不更新 state，下一次仍读旧值 |
| state 超过大小限制且压缩失败 | 可能写入空 payload；下一次 `load()` 视为无状态并重建 |

`AgentStateStore.load()` 没有检查 `agent_state_updated_at`，也没有比较“state 对应的最后一条消息”和 `messages` 表里的最新消息。`agent_state_version` 只用于保存时的乐观锁，不用于判断读取到的 state 是否过期。代码见 `app/agent/agent_state_store.py:86`。

### 5.4 重建的局限

缺失时并不是恢复完整的 10 轮，而是：

- 只取最近 6 条 `status in ('done','degraded')` 的消息；
- 失败的助手消息不会进入 history；
- 最终可能只有 U10 而没有 A10，或者更早的轮次直接丢失；
- 代码里是硬编码 `.limit(6)`，配置项 `HISTORY_TURNS` 当前没有真正被使用。见 `app/agent/run_worker.py:62` 和 `app/config.py:154`。

### 5.5 优化方案：基于水位线的 AgentState 新鲜度校验

> 本节只讨论方案，尚未改代码。

#### 5.5.1 目标与非目标

目标：

- 能区分 state 的四种状态：新鲜、陈旧、缺失、损坏。
- 陈旧但只落后少量轮次时，增量补齐，不丢弃已有 state。
- 落后过多或无法判断水位时，做有上限的重建。
- 不改变 `T6` 的原子性：答案、证据、`agent_state`、水位仍然一次提交。
- 水位只能由系统写入，不能由模型生成。

非目标：

- 不解决第 4.5 节 `T6` 已提交、`T7` 未提交导致的重跑覆盖问题；那个需要单独修队列收尾逻辑。
- 不把工具调用、工具结果重新塞回 state；这些仍然留在 `evidence` / `tool_calls`。
- 不在每轮加载时重放完整会话历史。

#### 5.5.2 数据模型

在 `conversations` 增加一列：

| 字段 | 类型 | 含义 |
|---|---|---|
| `agent_state_message_id` | `uuid null` | 当前 `agent_state` 已经包含到的最后一条助手消息 ID |

不把水位塞进 JSONB，原因是加载时要拿它和 `messages` 做等值比较，独立列更直接，也方便排查。`agent_state_version` 继续只做保存时的乐观锁，不承担新鲜度判断。

现有 `agent_state_updated_at` 保留，用于运维观察，不作为唯一判断依据。

#### 5.5.3 保存路径

`T6` 的 `conversations` 更新增加水位：

```sql
update conversations
set agent_state = cast(:state as jsonb),
    agent_state_version = agent_state_version + 1,
    agent_state_updated_at = now(),
    agent_state_message_id = :state_message_id
where id = :id
  and agent_state_version = :version
```

规则：

- state payload 非空且成功序列化：写 state + 本轮助手消息 ID 作为水位。
- 主动写入空 payload（例如压缩失败或明确跳过）：写入空 state，并将水位置 `null`；下一轮按“缺失”处理，走重建。
- state payload 没有生成（序列化异常）：不更新 state 和水位，保留旧 state；本轮答案如果已提交，下一次加载会因为水位落后于最新完成消息而判定为陈旧。
- 乐观锁更新 0 行：答案仍然提交，但水位保持旧值；下一轮会被判定为陈旧。
- `AGENT_STATE_SAVE=false` 时不写 state，也不推进水位；加载侧应直接按“不启用持久化上下文”处理。

#### 5.5.4 加载路径

`AgentStateStore.load()` 返回 state 时，同时返回 `agent_state_message_id`。加载流程：

1. 读取 `agent_state`、`agent_state_version`、`agent_state_message_id`。
2. 查询当前会话最后一条已完成的助手消息，状态限定 `done` / `degraded`，并排除当前 `request_id`。
3. 按下面规则判断。

| 条件 | 判定 | 动作 |
|---|---|---|
| state 不存在、为空、schema 不匹配、校验失败 | 缺失/损坏 | 用最近消息做有上限重建 |
| state 带截断标记 | 损坏 | 重建 |
| 水位为 `null` | 未知 | 重建 |
| 水位等于最后一条已完成助手消息 ID | 新鲜 | 直接使用 state |
| 水位存在，但落后于最新已完成消息 | 陈旧 | 增量补齐；补齐量超限则重建 |
| 水位指向的消息不存在或不属于该会话 | 不可信 | 重建 |
| 会话没有任何已完成助手消息 | 无可用锚点 | 空 state；不注入历史 |

这里的“已完成”指助手消息为 `done` 或 `degraded`。失败的助手轮次不会成为水位锚点；是否把失败轮次的用户问题补进上下文，是单独的产品决策，不在本方案默认行为内。

#### 5.5.5 增量补齐与重建

增量补齐：

- 以水位的 `created_at` 为锚点，查询其后的 `done/degraded` 消息。
- 必须排除当前 `request_id`，避免把 U11 重复注入。
- 查询上限 `AGENT_STATE_CATCHUP_MAX_MESSAGES`，默认 12 条。
- 数量在上限内：通过 `agent.observe()` 追加到已加载 state。
- 超过上限：放弃增量补齐，转为全量重建。

全量重建：

- 取最近 `AGENT_STATE_REBUILD_MAX_MESSAGES` 条 `done/degraded` 消息，默认 20 条，约 10 轮。
- 排除当前 `request_id`。
- 先创建空 `AgentState`，再 `agent.observe()`，避免旧 state 和新历史混在一起。
- 仍沿用现有的引用剥离逻辑，不把 `[E..]` 带回下一轮。
- 超过字符预算时，从最旧消息开始丢弃；预算可配置为 `AGENT_STATE_REBUILD_MAX_CHARS`。

现有代码硬编码 `.limit(6)`，且 `HISTORY_TURNS` 没有真正生效。建议新增语义明确的配置，不继续复用含义不清的 `HISTORY_TURNS`。

#### 5.5.6 迁移策略

新增迁移 `infra/sql/008_agent_state_watermark.sql`：

```sql
alter table conversations
  add column if not exists agent_state_message_id uuid;
```

迁移默认不自动回填，所有历史会话的水位保持 `null`：

- 第一次在新版本下提问时，按“未知水位”触发一次重建。
- 对 10 轮左右的会话，20 条消息窗口基本能覆盖 U1-A10 的对话文本。
- 更早轮次如果已经被 AgentScope 压缩成摘要，重建无法完全恢复摘要内容，这是安全换一致性的代价。
- 不建议用 `agent_state_updated_at` 自动回填：`messages.created_at` 来自应用时钟，`agent_state_updated_at` 来自数据库时钟，时钟偏差可能把旧 state 误认成新 state。

#### 5.5.7 可观测性

在 `meta` 中增加：

```text
agent_state_recovery = fresh | missing | invalid | truncated | stale_catchup | stale_rebuild
agent_state_watermark
agent_state_latest_message_id
agent_state_catchup_messages
agent_state_rebuild_messages
```

`state_rebuilt` 保留，兼容现有前端和日志。`stale_*` 场景打 WARNING 日志，便于确认优化是否真的生效。

恢复失败时不让整轮回答失败：增量补齐或重建异常时，退回空 state，标记 `agent_state_recovery='rebuild_failed'`，本轮继续回答，但上下文质量下降。

#### 5.5.8 测试与验收

至少覆盖：

- 水位等于最新完成消息：直接使用 state，不注入历史。
- 水位落后一轮：只补 U10/A10，不补 U11。
- 水位落后很多：转为全量重建，且不超过消息上限。
- state 缺失、损坏、截断：走重建。
- state 为空但水位存在：判为不可信并重建。
- `agent_state` 更新 0 行：下一轮能发现水位落后。
- `T6` 回滚：旧 state 和旧水位保留；如果之后已有新的 `done/degraded` 助手消息，下一轮能发现水位落后；如果只是当前轮失败，则不把该失败回答当作上下文是预期行为。
- A10 失败、A9 成功：不应把 A10 当作已完成锚点。
- 当前 U11 不得在补齐或重建中重复注入。
- 迁移后水位为 `null` 的旧会话，首次提问能正常重建。

验收标准：

- 正常连续对话不重复注入历史，不增加额外模型调用。
- `T6` 答案提交成功但 state 未更新时，下一次提问能发现并补齐 A10。
- 无法补齐时，最多使用配置上限内的最近消息重建。
- `T1`、`T6` 的原子性不变，现有引用校验和 raw 透传不回归。

#### 5.5.9 分阶段落地

1. 只加水位列和写入逻辑，加载仍按旧逻辑，先观察 `watermark` 与最新消息的偏差。
2. 加载侧启用“发现陈旧但只记录日志”，确认误判率。
3. 开启增量补齐与有上限重建。
4. 观察 `agent_state_recovery` 分布，再调整补齐/重建上限。

这样可以把“数据结构变更”和“上下文行为变更”分开验证，避免一次改动同时引入两类问题。
