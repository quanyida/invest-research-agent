# v1.14 三副本宕机场景归档

> 归档时间：2026-11-21。对应讨论：N+1 落库、N+2 完成事件、N+3 收尾合并后的宕机行为。
> 相关实现：app/agent/persist.py、app/agent/run_worker.py、app/agent/run_queue.py、app/api/chat.py。

## 1. 前提与术语

- 部署按 3 台应用机器、每台一个 FastAPI + RunWorker、共享 1 个 PostgreSQL 主库推演。
- 默认参数：RUN_LEASE_SECONDS=900、RUN_MAX_ATTEMPTS=2、TASK_TIMEOUT_SECONDS=180、RUN_QUEUE_POLL_SECONDS=0.2。
- N+1：persist_turn 事务提交，包含消息、证据、工具审计、模型审计、用量、agent_state、chat_runs 终态。
- N+2：done 事件插入 session_events。
- N+3：旧的独立 finish 收尾，现已合并进 N+1；只在异常路径保留。

## 2. N+1 前宕机

| 崩溃点 | 数据库状态 | 接手方式 | 结果 |
|---|---|---|---|
| 任务还在 queued，未被领取 | 消息 queued，chat_runs queued，无租约 | 另外两台机器 claim 用 SKIP LOCKED 立即抢到 | attempt=1 正常执行，无重复数据 |
| 已 claim，还没开始落库 | chat_runs running，lease_until 已写，消息 running | 另外两台先忽略；租约到期后 sweep 改回 queued | 再被 claim，attempt=2，重新执行 |
| 落库事务执行到一半，未提交 | PostgreSQL 回滚，消息、证据、审计、用量都不变 | 同上，等租约过期 | 不会留下半条证据，不会撞唯一约束 |
| 落库已发出 COMMIT，但提交结果未知 | 可能已提交，也可能未提交 | 异常路径查 chat_runs.status | 已 done 就不重试；仍 running 就等租约重试 |
| HTTP 入队事务 T1 未提交 | 会话、消息、chat_runs 都没有 | 无任务 | 客户端收到连接错误，重试即可 |
| 入队已提交，但 HTTP 响应丢失 | 任务已在队列 | Worker 正常领取 | 同一 client_request_id 重试会得到 409，需要刷新会话查看结果 |

结论：N+1 之前崩溃，业务数据要么全没有，要么全是旧状态；不会出现消息完成、任务还在运行。

## 3. N+1 成功后、N+2 前宕机

| 项目 | 状态 |
|---|---|
| messages | done 或 degraded，正文完整 |
| chat_runs | done，lease_until 为空，finished_at 已写 |
| 证据、工具审计、模型审计、用量 | 已随同一事务提交 |
| session_events | 可能没有 done，但可能有之前的 plan 或 tool 事件 |

- 其他两台机器不会重跑：sweep 只处理 status 为 running 且 lease_until 小于当前时间的任务。
- 不会撞 evidence 的 message_id 加 seq 唯一约束，因为不会再次落库。
- 客户端如果还连着存活的 API 副本，事件读取查不到 done 时，会看到任务和消息都已终态，合成一条 done 返回。
- 客户端如果连的是宕机副本，连接断开后前端会走 resume 重连；重连仍走同一个合成逻辑。
- 即使没有重连，刷新历史会话也能看到完整答案。
- 如果 done 事件已插入但客户端没收到，重连会从 session_events 回放。

这个窗口现在只会导致完成事件晚到或由服务端补发，不会导致整轮重跑。

## 4. 其他具体场景

| 崩溃点 | 行为 | 风险 |
|---|---|---|
| N+2 已插入后宕机 | 任务和消息都已终态，事件也在 | 无数据风险；客户端重连可回放 |
| 异常路径 mark_assistant_failed 成功后、finish 前宕机 | 消息 error，任务仍 running，租约未清 | 租约到期后可能被重新入队并重跑；attempt 达到上限时任务转 failed |
| sweep 已提交、_after_sweep 前宕机 | 任务已 queued 或 failed，消息可能还是 running | queued 情况会被下一次 claim 修正；failed 情况消息可能永久停在 running |
| 租约到期，但原 Worker 其实还活着 | 另一台机器 sweep 后重新领取，两个 Worker 同时执行同一轮 | 无 fencing token，可能重复调用模型和工具 |
| 两个 Worker 同时落库且都有证据 | 先提交者成功；后提交者撞唯一约束，整笔回滚 | 最终答案一致，但重复消耗成本 |
| 两个 Worker 同时落库，其中一方没有证据 | 没有唯一约束可挡，后提交者可能覆盖正文 | 可能出现正文来自 B、证据来自 A 的错配 |
| 重试时上一 attempt 已写过部分 SSE 事件 | 新 attempt 继续向同一 message_id 追加事件 | 回放时可能出现重复的工具事件，正文不受影响，但事件日志会膨胀 |
| PostgreSQL 主库宕机 | 入队、领取、落库、事件全部失败 | 应用层无法继续；恢复后按租约和重试处理 |
| 客户端断开 | Worker 不受影响，落库有取消保护 | 重连后按 cursor 补事件 |
| 进程收到 SIGTERM | Worker 取消，persist_turn 被 shield 保护 | 落库中会跑完；落库前取消则等租约重试 |

## 5. 三副本并发边界与残留窗口

- claim 用 FOR UPDATE SKIP LOCKED，同一时刻只有一个 Worker 能拿到同一条 queued 任务。
- chat_runs_one_active 保证同一会话最多一个 queued 或 running。
- sweep 的 UPDATE 只有一个事务能命中；其他事务等待后会重新判断条件。
- 残留窗口 1：sweep 与 _after_sweep 分属两个事务。sweep 只改 chat_runs，_after_sweep 才改 messages。如果扫尾 Worker 在两者之间宕机，且最终状态是 failed，消息会停在 running，没有任务再处理它。
- 残留窗口 2：没有租约心跳续租。单次 run 超过 900 秒，或多实例部署时原 Worker 发生长时间停顿，另一实例会判定租约过期并重新领取。默认 TASK_TIMEOUT_SECONDS 为 180，正常执行不会触发；如果租约小于任务超时，就必然出现双 Worker。
- 残留窗口 3：没有 fencing token。persist_turn 更新 chat_runs 的条件只有 status 为 running，没有校验 worker_id 或 attempt。租约误判时，旧 Worker 仍可能提交。证据唯一约束能挡住大多数冲突，但挡不住零证据覆盖：后提交者没有证据，不会撞唯一约束，却可能覆盖先提交者的正文，并留下先提交者的证据。
- session_events 不是按 attempt 隔离的。重试会向同一 message_id 追加新事件，旧 attempt 的部分事件仍然存在；前端按 id 顺序回放，可能出现重复的工具事件。它不影响最终答案表，但会影响事件日志和页面过程展示。

以上三点曾是需要加固的边界。2026-11-21 已修复残留窗口 1 与残留窗口 3（见 5.1）；租约心跳与事件重复仍未处理。

### 5.1 本次修复（2026-11-21）

- 残留窗口 1（sweep 与消息状态分属两个事务）：已修复。`sweep()` 现在在同一个事务内更新 `chat_runs` 并同步 `messages`；扫尾 Worker 在中间宕机时两者一起回滚，不再产生「任务失败、消息仍为运行中」的孤儿。
- 残留窗口 3（缺少 fencing）：已修复。`QueueTicket` 带回 `worker_id`，`persist_turn` 收尾 `chat_runs` 时同时校验 `worker_id` 与 `attempt`；影响行数为 0 时抛出 `RunFenced`，整个落库事务回滚，不会留下部分写入。
- 残留窗口 2（无租约心跳）：未修复，仍按效率问题处理。fencing 生效后，即使租约被误判，旧 Worker 的提交也会被拒绝，不会产生脏数据。
- 事件重复：未修复，仍只影响过程展示，不影响最终答案。



## 6. 如果 3 副本指 PostgreSQL 副本

- 只有主库接受写入；应用层看到的仍是单主语义。
- 同步复制下，N+1 的提交取决于同步副本 quorum；异步复制下，主库故障切换可能丢失最后一段 WAL。
- 应用层的 N+1 原子性不能超过数据库的持久化配置；如果需要收到 done 就一定不丢，必须使用同步提交并确认副本策略。

## 7. 异常路径缺陷与回归

本次源码核对发现 app/agent/run_worker.py 原来调用：

    run_status(ticket.run_id)

但函数签名是 run_status(tenant_id, run_id)。这会导致异常路径直接 TypeError：

- N+1 已提交、done 事件写入失败时：数据仍然安全，但异常处理不会正常返回；
- N+1 未提交、Agent 抛异常时：mark_assistant_failed 和 finish 都不会执行，任务只能等租约过期。

已改为 run_status(ticket.tenant_id, ticket.run_id)，并新增 tests/test_run_worker_finalize.py 两个回归用例：

- 提交后迟到异常：识别为已终态，不再收尾；
- 提交前异常：正常标记消息失败、任务失败。

当前全量测试：151 passed（2026-11-21 复核）。

## 8. 结论

- N+1 前宕机：安全，最多重跑一轮，不会留下半提交数据。
- N+1 后、N+2 前宕机：安全，消息和任务同终态，不重跑；done 由事件回放合成。
- 3 副本下的三个残留点：sweep 与消息状态分属两个事务、缺少 worker_id 与 attempt 的 fencing 已在 2026-11-21 修复；租约心跳续租仍未实现，属于效率优化，fencing 已能保证其不产生脏数据。
