## 1. 结论先行

**上下文组装只有一个核心位置：AgentScope 的 `_prepare_model_input()`。**

它是私有方法，**没有中间件钩子**。项目能干预的是「喂进去的原料」，
而不是「组装的逻辑」。

---

## 2. 组装逻辑

位置：`agentscope/agent/_agent.py:3355`

```python
async def _prepare_model_input(self) -> dict[str, Any]:
    """A unified method to prepare the chat model input according to
    the current context."""

    # 1. System prompt
    messages = [
        SystemMsg(name="system", content=await self._get_system_prompt()),
    ]

    # 2. 压缩摘要（如果有）
    if self.state.summary:
        messages.append(
            UserMsg(name="user", content=self.state.summary),
        )

    # 3. 对话上下文（全部）
    messages.extend(self.state.context)

    # 4. 工具 schema
    tools = await self.toolkit.get_tool_schemas(
        self.state.tool_context.activated_groups,
    )

    return {"messages": messages, "tools": tools}
```

**只有四步，顺序固定：**

```
[SystemMsg]        ← system prompt
[UserMsg]          ← summary（可选，插在 system 之后、context 之前）
[Msg, Msg, ...]    ← state.context 全部
tools              ← 工具 schema
```

### 2.1 关键特征

| 特征 | 说明 |
|---|---|
| **summary 位置固定** | 在 system prompt 之后、context 之前 |
| **context 全量拼接** | `messages.extend()`，无截断、无过滤 |
| **工具 schema 同时组装** | 不只拼消息，还取工具定义 |
| **无中间件钩子** | 私有方法，中间件链在 `_call_model` 里 |

## 3. 三个调用点

`_prepare_model_input()` 被调用三次，用途不同：

| 行号 | 用途 |
|---|---|
| **509** | 压缩前**估算 token**（`_compress_context_impl` 内部） |
| **1591** | ReAct 循环里**检查上下文长度**，决定是否注入预警提示 |
| **1755** | **实际调模型前** |

**三次调用同一份逻辑**，保证「估算的 token」与「实际发送的 token」一致。

### 3.1 第二次调用的作用

位置：`_agent.py:1589-1609`

```python
if self.state.cur_iter == 0:          # 仅在一个 reply 的开始
    kwargs = await self._prepare_model_input()
    input_tokens = await self.model.count_tokens(**kwargs)

    trigger_tokens = int(
        self.context_config.trigger_ratio * self.model.context_size,
    )
    if input_tokens > (
        (self.context_config.trigger_ratio
         - self.context_config.context_buffer_ratio)
        * self.model.context_size
    ):
        hint = (
            f"Your current context contains {input_tokens} "
            f"tokens. When reaching {trigger_tokens} tokens, "
            f"your context will be compressed."
        )
        ...
```

**这是「提前预警」机制**：当 token 超过 `(trigger_ratio - buffer_ratio)` 时，
注入提示告知模型「快到压缩阈值了，你可以自己决定何时压缩」。

按本项目配置（`trigger_ratio=0.7`、`buffer_ratio` 默认 0.2）：
- 预警阈值 = 50 万 token
- 压缩阈值 = 70 万 token

**两个都够不到。**

## 4. system prompt 的独立组装

位置：`_agent.py:3330`

```python
async def _get_system_prompt(self) -> str:
    prompt = [self._system_prompt]              # 1. 基础 prompt

    skill_instructions = await self.toolkit.get_skill_instructions(
        self.state.tool_context.activated_groups,
    )
    if skill_instructions:
        prompt.append(skill_instructions)       # 2. 技能说明

    if isinstance(self.offloader, WorkspaceBase):
        offload_instructions = await self.offloader.get_instructions()
        if offload_instructions:
            prompt.append(offload_instructions) # 3. 工作区说明

    result = "\n".join(prompt)

    # 4. 中间件链（transformer 模式，非洋葱模式）
    for mw in self._system_prompt_middlewares:
        result = await mw.on_system_prompt(self, result)

    return result
```

**与 messages 组装分开**，是独立的四段拼接 + 中间件转换。

### 4.1 两种中间件模式的区分

| 钩子 | 模式 | 说明 |
|---|---|---|
| `on_system_prompt` | **transformer** | 逐个变换，前一个的输出是后一个的输入 |
| `on_compress_context` | **onion** | 可调用 `next_handler()` 决定是否继续 |
| `on_model_call` | onion | 同上 |

## 5. 本项目在组装上的干预

### 5.1 干预 A：`build_agent_system_prompt()`

位置：`app/agent/context.py`

```python
Agent(
    system_prompt=build_agent_system_prompt(ctx),
    ...
)
```

这个函数在**项目侧**拼出完整 system prompt：

```
RAW_SYSTEM_PROMPT / SYSTEM_PROMPT
  + SECTION_RULES
  + "当前是会话第 N 轮。本轮可用工具：..."
  + prefetch_section
  + AGENT_REACT_RULES.format(max_tools=..., turn=...)
  + AGENT_TOOL_RULES
```

**这是项目对上下文的最大干预**——把领域规则、轮次信息、工具清单、
预检索结果全部塞进 system prompt。

### 5.2 干预 B：技能注入

```python
def _toolkit(self, ctx) -> Toolkit:
    skill_paths = [str(SKILLS_DIR)] if SKILLS_DIR.exists() else []
    return Toolkit(tools=create_tools(ctx), skills_or_loaders=skill_paths)
```

`SKILLS_DIR` 指向 `skills/ifind-finance-data`，
框架会在 `_get_system_prompt()` 里把技能说明拼进去。

### 5.3 干预 C：状态注入

```python
Agent(state=state, ...)
```

`state.context` 和 `state.summary` 由项目从数据库加载后传入。

**`_prepare_model_input` 里那三步的数据，全部由项目提供。**

### 5.4 干预 D：探针（只观测）

位置：`app/agent/context_probe.py`

```python
async def on_model_call(self, agent, input_kwargs, next_handler):
    messages = list(input_kwargs.get("messages") or [])   # ← 组装结果
    ...
```

`input_kwargs["messages"]` 就是 `_prepare_model_input()` 的输出。

**这是唯一能验证「实际送进模型多少内容」的地方。**

## 6. 完整链路

```
项目侧
├─ build_agent_system_prompt(ctx)     → system_prompt
├─ AgentState.context / summary       → 从数据库加载
└─ Toolkit(tools, skills)             → 工具与技能
         ↓
     Agent(...)  构造
         ↓
AgentScope 侧
├─ _get_system_prompt()
│    ├─ base prompt
│    ├─ 技能说明（从 Toolkit）
│    ├─ 工作区说明（若有 offloader）
│    └─ system_prompt 中间件链（transformer）
│
└─ _prepare_model_input()
     ├─ SystemMsg(system prompt)
     ├─ UserMsg(summary)            ← 若存在
     ├─ state.context（全部）
     └─ tools schema
         ↓
     on_model_call 中间件链（onion）
         ↓
     实际调模型
```

## 7. 一个关键发现：context 是「全量拼接」

```python
messages.extend(self.state.context)     # 无截断、无过滤
```

**含义：**

- 如果 `state.context` 有 100 条消息，**全部塞进 prompt**；
- 框架不会在组装时做任何过滤；
- 体积控制完全依赖**组装前**的压缩；
- 压缩失败 → context 保持原样 → 组装时超限 → 模型报错。

**所以压缩和组装是解耦的：**

```
压缩：负责「减小 context 体积」
组装：负责「全量拼接」
```

这也解释了 `ContextProbeMiddleware` 的价值——
**它是唯一能验证「实际送进去多少」的地方**，
而不是靠推断 `state.context` 应该有多大。

## 8. 如果要干预组装

| 想做什么 | 切入点 | 侵入性 |
|---|---|---|
| 改 system prompt 内容 | `build_agent_system_prompt()`（项目侧） | 无 |
| 改 system prompt 处理链 | `on_system_prompt` 中间件 | 低 |
| 增删 context 里的消息 | 改 `state.context`（压缩时） | 中 |
| 改工具 schema | `Toolkit` 或 `on_acting` 中间件 | 低 |
| 只观测不改 | `on_model_call` 中间件（已验证可用） | 无 |
| **改 messages 组装顺序** | **只能重写 `_prepare_model_input`** | **高** |

## 9. 待验证的一个可能性

`_prepare_model_input()` 是私有方法，**没有中间件钩子**。

理论上想改组装逻辑只有两条路：

1. **重写 Agent 子类**（侵入性高，依赖私有方法）；
2. **在 `on_model_call` 里修改 `input_kwargs["messages"]`**。

**第 2 条尚未验证。**

需要确认的问题：

- `input_kwargs` 的修改是否会传递到实际模型调用？
- 还是 `next_handler()` 会重新读取原始参数？

如果第 2 条可行，那就是一个**干净的组装干预点**——
不用碰私有方法，只靠公开钩子就能改变送进模型的消息序列。

**验证方法**：写一个最小中间件，在 `on_model_call` 里往 `messages` 追加一条消息，
然后在模型实际收到的内容里检查该消息是否存在。

**这个验证尚未执行，结论待定。**
